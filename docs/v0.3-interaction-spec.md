# WorkspaceLens v0.3 Interaction and Information Architecture Specification

Status: Interaction specification draft for v0.3. This document refines `v0.3-product-spec.md` into navigation, user journeys, states, actions, feedback, and recovery behavior. It intentionally does not choose the visual design system, frontend framework, HTTP framework, process topology, credential store, or operating-system integration mechanism.

## 1. Interaction Goal

The v0.3 WebUI is a local control surface for WorkspaceLens context connectivity.

Its job is to make the following actions obvious and low-friction:

1. complete first-time setup;
2. authorize and manage multiple local workspaces;
3. understand whether the local context connection is usable;
4. recover common failures without reconstructing CLI knowledge;
5. copy optional workspace-targeting/reasoning helpers.

The WebUI is not a daily development dashboard. When WorkspaceLens is healthy, the ideal daily experience is that the user does not need to open it.

This leads to a core interaction principle:

> Show only the state and actions needed to configure, verify, or recover local context connectivity. Do not invent work-management features merely to fill the UI.

## 2. Information Architecture

v0.3 should use four persistent primary sections:

```text
Workspaces
Connection
Diagnostics
Settings
```

There is no separate `Overview` or `Dashboard` page in v0.3.

### 2.1 Default destination

After onboarding, opening the WebUI lands on **Workspaces**.

Reasoning:

- workspace authorization is the primary product object users intentionally manage;
- healthy connection state can be summarized globally without a dashboard;
- detailed connection/recovery actions already have a dedicated page;
- an additional overview page would mostly duplicate information.

### 2.2 First-run destination

When WorkspaceLens has not completed basic local setup, opening the WebUI enters the guided **Setup** experience.

Setup is a temporary guided flow rather than a fifth permanent primary section.

The user may leave Setup and configure later. Incomplete setup must remain clearly visible as an actionable global state.

After setup, the Connection page may expose a `Run setup guide` / `Review setup steps` action without restoring Setup as primary navigation.

### 2.3 Workspace detail

Each workspace has a dedicated detail surface reachable from Workspaces.

Conceptually:

```text
Workspaces
  `-- Workspace Detail
```

Whether this is implemented as a full page, route, or equivalent navigable detail surface is a UI/technical decision. It must support direct return to the workspace list and must not rely on hover-only interaction.

## 3. Global Interaction Model

### 3.1 Global status entry point

The persistent application shell should expose a compact product status entry point.

It should summarize the most important locally observable state with one of the following product-level labels:

- **Healthy** — machine-verifiable local runtime/configuration and configured integration layers required for ordinary use are healthy;
- **Action required** — setup is incomplete or a recoverable user action is required;
- **Problem** — a configured local layer is failing or invalid;
- **Checking** — state is being refreshed and no previous result should be treated as current.

Selecting the global status opens the most relevant Connection or Diagnostics context.

The summary label must not be `ChatGPT connected` unless a supported provider signal actually proves that claim.

### 3.2 Status precedence

When several states coexist, the UI should surface the most actionable blocking state first.

Recommended precedence:

```text
Problem
  > Action required
  > Healthy
```

Workspace-specific warnings should not make the entire product appear broken when other workspaces and the connection remain usable.

### 3.3 Machine-verified versus user-confirmed state

Provider-side steps that WorkspaceLens cannot observe must never be presented as machine-verified.

The UI may distinguish:

- **Verified** — WorkspaceLens observed sufficient local/provider-integration evidence;
- **User confirmed** — the user states that an external provider-side step was completed;
- **Not verified** — WorkspaceLens has no reliable proof;
- **Action required** — a known step is incomplete.

A user-confirmed provider step is useful onboarding state, but it is not equivalent to a verified remote MCP request.

## 4. First-run Setup Flow

Setup should be state-driven rather than page-count-driven. Reloading the UI must reconstruct progress from current configuration and observable state rather than blindly resuming a stored wizard step.

The recommended five-stage interaction is:

```text
1. System
2. First Workspace
3. Tunnel
4. ChatGPT
5. Verify
```

### 4.1 Stage 1 — System

Goal: establish whether the local product has the prerequisites needed for the expected ChatGPT path.

The UI checks and reports at least:

- WorkspaceLens local runtime/configuration validity;
- Git availability;
- official `tunnel-client` availability.

Behavior:

- successful checks proceed without requiring the user to understand implementation details;
- a missing required prerequisite shows one primary next action;
- a missing `tunnel-client` offers a link to the official installation source rather than an invented third-party installer in v0.3;
- failures show `Retry` after the user performs the external fix;
- diagnostics details remain available but should not dominate the primary flow.

If a prerequisite is optional for a particular capability, the UI should label it as a warning rather than block all setup.

### 4.2 Stage 2 — First Workspace

Goal: authorize at least one useful local project before remote verification.

Flow:

```text
Choose local folder
      |
      v
Derive suggested display name + workspace_id
      |
      v
User reviews/edits identity
      |
      v
Validate root and identity
      |
      v
Add and enable workspace
```

Rules:

- folder/path acquisition is one user-visible action; the technical mechanism is deferred to the Technical RFC;
- canceling folder selection causes no state change;
- the suggested `workspace_id` is editable before creation;
- duplicate roots and duplicate IDs are blocking validation errors;
- invalid/unreadable roots are blocking errors;
- a readable non-Git root may be added with a warning rather than being rejected solely for not being a Git repository;
- a successfully added workspace is enabled by default.

### 4.3 Stage 3 — Tunnel

Goal: configure the local side of the ChatGPT tunnel integration and make local tunnel readiness understandable.

The step should separate provider-owned resource creation from WorkspaceLens-owned local profile configuration.

Conceptual flow:

```text
Open provider tunnel settings
      |
      v
User creates/selects required provider resource
      |
      v
Provide tunnel identifier and required runtime credential through the supported secure mechanism
      |
      v
WorkspaceLens creates/validates local profile
      |
      v
Start tunnel runtime
      |
      v
Local tunnel health check
```

Rules:

- exact credential storage/input behavior is deferred to the Technical RFC;
- secrets must never be echoed back in ordinary UI or copied into diagnostics;
- the UI may automate local profile creation because that state is WorkspaceLens-owned;
- if an existing profile is valid, the step should recognize it rather than recreate it;
- if an existing profile points to an incompatible command/configuration, the UI should present `Repair local profile` with an explicit explanation;
- local tunnel health must be presented separately from provider-side ChatGPT App setup.

### 4.4 Stage 4 — ChatGPT

Goal: guide the user through provider-side setup that WorkspaceLens cannot perform itself.

The page should provide concise steps and direct links where supported, for example:

1. enable the provider feature required for custom MCP Apps;
2. create/select the WorkspaceLens App/connection;
3. select the configured tunnel;
4. scan/refresh tools.

These are provider-owned actions.

The UI may allow the user to mark the checklist as **User confirmed** so that they can progress, but it must not silently convert those confirmations into machine-verified state.

Browser automation that clicks through ChatGPT settings is not part of v0.3.

### 4.5 Stage 5 — Verify

Goal: prove that the configured reasoning-client path can reach WorkspaceLens.

The UI provides a short verification instruction such as:

```text
Call WorkspaceLens `workspace_list` from ChatGPT and confirm that your workspace appears.
```

Preferred completion behavior:

- if WorkspaceLens can safely attribute an inbound MCP request to the configured tunnel/provider integration, observing the verification call marks the connection **Verified**;
- if that attribution cannot be made reliably, the UI must not infer it from unrelated local MCP activity;
- in that case, the user may confirm successful verification manually and the UI must label the result **User confirmed**, not machine-verified.

A verification timeout is not treated as a fatal setup error. It should show the likely next checks and offer `Retry verification`.

### 4.6 Leaving Setup early

The user may choose `Configure later` after basic local product startup.

Leaving early:

- does not discard completed local configuration;
- returns to the normal application shell;
- leaves global status at `Action required`;
- makes the incomplete setup step reachable from Connection.

## 5. Workspaces

Workspaces is the primary landing page after onboarding.

### 5.1 Workspace list

Each workspace entry should show only information useful for identity and authorization management in v0.3:

- display name;
- stable `workspace_id`;
- local root;
- enabled/disabled state;
- validation state;
- Git capability available / unavailable where useful.

Branch, HEAD, dirty summary, and historical last-access context belong to the richer v0.4 context/observability surface and are not required on the v0.3 workspace list.

Primary list actions:

- `Add workspace`;
- open workspace detail;
- enable/disable where the interaction remains unambiguous.

### 5.2 Empty state

If no workspaces exist, Workspaces should show one primary action:

`Add workspace`

The empty state should explain that adding a workspace authorizes read-only context access; it must not imply that files are uploaded or modified.

### 5.3 Add Workspace

The add interaction follows the same identity/validation rules as Setup Stage 2.

Recommended sequence:

```text
Select root
  -> review name + workspace_id
  -> validate
  -> add enabled workspace
```

No provider/tunnel/App setup should appear in this flow.

After success, the user lands on the new workspace detail or receives an immediate success state with optional helper actions.

### 5.4 Workspace detail

Workspace detail should expose:

- display name;
- stable `workspace_id`;
- canonical local root;
- enabled/disabled authorization state;
- current validation result;
- basic Git capability availability;
- optional helper actions;
- authorization management actions.

#### Editable fields in v0.3

- display name may be edited;
- `workspace_id` is immutable after creation;
- root authorization is immutable after creation in v0.3.

Keeping identity/root changes explicit avoids silently redirecting an existing external Project Instruction to a different local directory.

If the root moves or becomes invalid, v0.3 should guide the user to remove the old authorization and add the intended root explicitly. A future `Reauthorize root` action may be added only if repeated friction justifies it.

### 5.5 Enable / Disable

Disabling a workspace is reversible and should not require a destructive confirmation dialog.

After disable succeeds:

- the UI immediately shows `Disabled`;
- the workspace is unavailable to subsequent MCP requests;
- a concise success message explains that no local files were changed.

Enabling must revalidate the configured root before success. If validation fails, the workspace remains disabled and the error is shown inline.

### 5.6 Remove authorization

Removing a workspace requires confirmation because it changes authorization and may break external Project Instructions that reference the workspace ID.

The confirmation must state clearly:

- only WorkspaceLens authorization/configuration is removed;
- local files and the Git repository are not deleted or modified.

The action label should be explicit, such as `Remove workspace authorization`, rather than `Delete project`.

Typing the workspace name/ID is not required in v0.3 because the action is recoverable by re-adding the same local root and does not delete user data.

### 5.7 Invalid workspace state

For a missing or inaccessible root, the workspace detail should offer clear next actions:

- retry validation;
- disable workspace;
- remove authorization.

v0.3 does not silently remap the workspace ID to another directory.

## 6. Workspace Identity Helpers

Workspace detail may provide three optional convenience actions:

- `Copy Project Instructions`;
- `Copy Review Prompt`;
- `Copy Plan Prompt`.

### 6.1 Helper content rules

Generated helpers should:

- reference the stable `workspace_id` explicitly;
- remain concise;
- instruct the reasoning client not to guess another workspace if the target is unavailable/ambiguous where relevant;
- avoid embedding volatile repository state;
- avoid creating WorkspaceLens-owned workflow semantics.

### 6.2 Copy interaction

On successful copy, show lightweight feedback such as `Copied`.

If browser clipboard access is unavailable, provide a selectable text fallback rather than failing silently.

v0.3 does not provide:

- saved custom prompt templates;
- prompt editing/version history;
- prompt marketplace/library behavior;
- automatic invocation of review or planning workflows.

## 7. Connection

Connection explains and controls the locally observable provider-integration path.

It should present the connection as layers rather than one opaque `Connected / Disconnected` switch.

Recommended layers:

```text
Local Runtime
Tunnel Client
Local Tunnel Profile
Tunnel Runtime / Health
Provider-side Setup
Verification
```

### 7.1 Layer behavior

Each layer should show:

- current status;
- concise reason when not ready;
- one primary next action when possible.

Examples:

- `Tunnel client — Missing` -> `Install` / open official source;
- `Local profile — Missing` -> `Configure`;
- `Tunnel runtime — Stopped` -> `Start`;
- `Tunnel runtime — Unhealthy` -> `Restart` plus diagnostics link;
- `Provider setup — Not verified` -> `Review ChatGPT setup`;
- `Verification — User confirmed` -> clear user-confirmed label rather than `Connected`.

### 7.2 Start / Stop / Restart

Start and restart should be direct actions with visible pending states.

Stopping the tunnel/runtime is reversible and normally does not require confirmation.

If WorkspaceLens can observe active MCP requests, stopping/restarting while requests are active should warn that those requests may fail and require explicit confirmation before interrupting them.

The UI must prevent duplicate start/stop actions while a transition is already in progress.

### 7.3 Repair / Reconfigure local connection

A locally invalid profile should offer a guided repair action.

Reconfiguration must:

- explain what local integration state will change;
- preserve workspace authorization/configuration;
- never imply that provider-side ChatGPT settings were automatically changed.

If changing the tunnel/profile may interrupt an active connection, require confirmation.

### 7.4 Unknown provider state

If all locally observable layers are healthy but ChatGPT-side setup cannot be verified, display language such as:

`Local connection is ready. ChatGPT setup has not been verified.`

Do not collapse this into either `Connected` or `Disconnected`.

## 8. Diagnostics

Diagnostics is a troubleshooting surface, not a log analytics dashboard.

### 8.1 Diagnostic groups

At minimum, group checks into:

- Local Runtime / Configuration;
- Workspaces;
- Provider Integration / Tunnel.

Each check should have:

- pass / warning / fail / unknown state;
- concise explanation;
- actionable next step where one exists.

### 8.2 Refresh behavior

Opening Diagnostics should run or refresh inexpensive checks automatically.

A `Run again` / `Refresh diagnostics` action should be available after external fixes.

Long-running checks should show per-check progress rather than freezing the whole page.

### 8.3 Copy diagnostic report

The user may copy a sanitized diagnostic report for support/review.

By default the report must not include:

- provider API keys or secret values;
- credential contents;
- sensitive file contents;
- full absolute workspace paths when those paths are unnecessary for diagnosis.

If including local paths is diagnostically useful, it should require a separate explicit opt-in such as `Include local paths` and must still exclude secrets.

### 8.4 Last-known errors

v0.3 may show the last relevant local runtime/connection error needed for recovery.

It must not turn this into a historical MCP Activity / Access Log. Historical request observability remains a v0.4 feature.

## 9. Settings

Settings should remain small in v0.3.

Required settings include:

### 9.1 Start WorkspaceLens at login

An explicit user-controlled toggle.

Behavior:

- turning it on explains that WorkspaceLens will become locally available after login;
- success/failure is confirmed visibly;
- operating-system permission/integration failures are actionable;
- turning it off removes the startup behavior without removing workspaces or provider configuration.

The implementation mechanism is deferred to the Technical RFC.

### 9.2 Expose absolute workspace paths to MCP clients

This maps to the existing local security/configuration choice and remains **off by default**.

Turning it on should explain that MCP clients may receive local absolute path information.

Because this changes information exposure, enabling it should require explicit confirmation. Disabling it should be immediate.

### 9.3 Version / product information

The UI may show the installed WorkspaceLens version and basic local product information for diagnostics.

v0.3 does not require a general preferences system, themes, account settings, or provider-account management page.

## 10. Feedback and Confirmation Rules

### 10.1 Use inline errors for fixable form/state problems

Examples:

- invalid workspace ID;
- duplicate root;
- unreadable folder;
- missing tunnel ID;
- failed validation.

Do not hide these errors behind transient toasts.

### 10.2 Use lightweight success feedback for reversible actions

Examples:

- copied helper;
- workspace enabled/disabled;
- diagnostics refreshed;
- tunnel started/restarted when successful.

### 10.3 Confirmation dialogs are reserved for meaningful side effects

Require confirmation for at least:

- remove workspace authorization;
- reconfigure/replace a working local tunnel profile when it will change connection identity;
- enabling additional information exposure such as absolute paths;
- interrupting active MCP requests when stopping/restarting, if active requests are observable.

Do not require confirmation for ordinary navigation, copy actions, refresh, or a simple reversible disable with clear feedback.

### 10.4 Pending state must be explicit

Actions such as start, stop, restart, add, remove, or save must:

- show that the operation is in progress;
- prevent accidental duplicate submission;
- finish in a visible success or actionable failure state.

## 11. Loading, Empty, Error, and Stale States

### 11.1 Initial loading

The UI should render the application shell promptly and load current state without presenting guessed status as fact.

Use `Checking` / skeleton equivalents until machine state is known.

### 11.2 Control service unreachable

If the already-loaded WebUI cannot reach its local control service:

- show a clear local-service-unavailable state;
- do not display stale state as currently healthy;
- provide `Retry`;
- preserve enough previously rendered context to explain what failed where safe.

The exact recovery mechanism depends on the process model and is deferred to the Technical RFC.

### 11.3 Configuration changed outside the WebUI

CLI and WebUI share the same underlying configuration.

If the configuration changes externally while a form/detail view is open:

- the WebUI must not silently overwrite newer state with stale form data;
- refresh current state;
- inform the user that configuration changed outside this view;
- require the user to reapply edits if necessary.

The technical concurrency-control mechanism is deferred to the Technical RFC.

### 11.4 Unknown is a valid state

When WorkspaceLens cannot verify a fact, display `Unknown` / `Not verified` with explanation rather than inferring success or failure.

## 12. Interaction Safety and Multi-workspace Isolation

The interaction model must never introduce a global active workspace.

Consequences:

- workspace selection in the WebUI is for management only;
- opening Workspace A's detail page does not make Workspace A the MCP default;
- copying a helper does not change runtime routing;
- one chat accessing Workspace A does not change what another chat accessing Workspace B sees;
- no UI control named `Set active workspace` exists in v0.3.

Every workspace-targeting helper uses explicit identity instead of hidden selection state.

## 13. Accessibility and Input Principles

Detailed visual/accessibility specification belongs to the UI Spec, but the interaction contract requires:

- every essential action works by click/tap and keyboard; no essential hover-only controls;
- destructive/reconfiguration confirmations receive focus predictably and can be canceled;
- status is conveyed by text/semantics, not color alone;
- loading and asynchronous completion produce perceivable status updates;
- copy actions have non-clipboard fallbacks;
- error messages identify both the problem and the next action when known.

## 14. Explicit Interaction Non-goals

The v0.3 WebUI does not add interactions for:

- browsing source files;
- viewing code diffs;
- editing repository files;
- running shell commands;
- running builds/tests/debug sessions;
- selecting or managing ChatGPT conversations;
- mapping ChatGPT conversation IDs to workspaces;
- setting a global/current workspace;
- CR/Plan session tracking;
- CR/Plan completion statistics;
- task management;
- historical MCP activity analytics;
- prompt library management;
- agent orchestration;
- coding-harness control.

## 15. Interaction Acceptance Criteria

The v0.3 interaction design is complete when:

1. A first-time user can move through System -> First Workspace -> Tunnel -> ChatGPT -> Verify without needing to understand MCP transport internals.
2. Every provider-owned step is visibly distinguished from WorkspaceLens-owned local actions.
3. The UI never presents user-confirmed provider state as machine-verified state.
4. The normal post-onboarding landing page is Workspaces, with no redundant dashboard required.
5. A user can add another workspace without encountering tunnel/App setup again.
6. Workspace identity is stable and usable in copied Project Instructions / Review / Plan helpers.
7. Disable and remove behavior clearly changes WorkspaceLens authorization without implying local file deletion.
8. Connection failures resolve to a specific layer and next action rather than a generic `Disconnected` state whenever the cause is observable.
9. Common tunnel lifecycle actions expose pending, success, and failure states and avoid duplicate execution.
10. Diagnostics provide actionable current-state troubleshooting without becoming v0.4 historical activity analytics.
11. CLI/WebUI concurrent configuration changes are not silently overwritten.
12. No WebUI interaction establishes hidden global workspace routing or ChatGPT conversation ownership.
13. All essential controls are usable without hover-only interaction.

## 16. Inputs to the Next Specifications

### 16.1 UI Specification

The UI Spec should now define the visual realization of this interaction contract, including:

- application shell/navigation layout;
- Setup stepper/wizard presentation;
- Workspaces list and detail layouts;
- Connection layered-status layout;
- Diagnostics layout;
- Settings layout;
- forms, dialogs, toasts, pending states, and empty/error states;
- typography, spacing, color/status language, responsive behavior, and accessibility details.

The UI Spec must not introduce new product objects or workflow semantics merely for visual richness.

### 16.2 Technical Architecture RFC

The Technical RFC must determine how to implement these interactions against the existing v0.2 codebase, especially:

- long-lived process ownership/supervision;
- WebUI/control API hosting;
- safe local folder/path acquisition from a browser-based control surface;
- secure tunnel credential availability during autostart;
- tunnel-client profile/lifecycle supervision;
- configuration revision/conflict handling between CLI and WebUI;
- machine-verifiable request attribution for final onboarding verification, if feasible;
- browser security for local state-changing operations;
- frontend/backend technology selection;
- packaging and OS startup integration.

If a technical constraint makes an interaction impossible or unsafe, the RFC should propose the smallest product-compatible adjustment rather than silently changing the interaction contract.

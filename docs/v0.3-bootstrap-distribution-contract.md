# WorkspaceLens v0.3 Bootstrap and Distribution Contract

Status: Accepted v0.3 product/technical contract.

This document defines how a normal user installs, starts, and returns to WorkspaceLens. It complements `v0.3-product-spec.md`, `v0.3-interaction-spec.md`, `v0.3-ui-spec.md`, and `v0.3-technical-architecture-rfc.md`.

The governing product principle is:

> **One install, one bootstrap, zero daily CLI.**

The user should not need to understand WorkspaceLens process topology, tunnel-client process topology, PIDs, ports, daemon supervision, MCP transport, or runtime aliases in order to use the product.

---

## 1. User-facing Product Model

The user-facing product is simply **WorkspaceLens**.

Internally, v0.3 may involve:

- one long-lived WorkspaceLens Control Runtime;
- the official OpenAI `tunnel-client` managed runtime;
- a browser tab rendering the local WorkspaceLens WebUI.

Those are implementation layers, not product concepts.

The normal user mental model is:

```text
Install WorkspaceLens once
        |
        v
Start WorkspaceLens once
        |
        v
Browser opens local WebUI
        |
        v
Complete setup
        |
        v
Enable Start at login
        |
        v
Daily use requires no Terminal
```

Closing the browser must not stop WorkspaceLens or break the reasoning-client connection.

---

## 2. v0.3 Distribution Levels

### 2.1 Required v0.3 distribution — npm package

The first complete v0.3 distribution may use npm as the installation channel.

Expected normal-user bootstrap:

```bash
npm install -g workspace-lens
workspace-lens start
```

After `workspace-lens start`, the user should not need the Terminal for normal WorkspaceLens operation.

The npm package must include:

- compiled Node runtime;
- built WebUI assets;
- CLI launcher;
- all runtime dependencies required by the Control Runtime;
- package metadata required to resolve static assets from the installed module location.

The package must not assume execution from a Git checkout or from the repository root.

### 2.2 Contributor/developer path

Repository contributors may continue to use:

```bash
git clone ...
npm install
npm run build
```

This is not the normal product onboarding path and must not be presented as such in v0.3 user-facing setup.

### 2.3 Native installers are optional enhancement, not a v0.3 blocker

Future distribution may provide:

- macOS `.dmg` / signed app or installer;
- Windows installer;
- Linux package/AppImage/deb/rpm.

A native installer does **not** imply that WorkspaceLens needs Electron or Tauri. A native launcher may simply start the existing local Control Runtime and open the system browser.

Native packaging should only be promoted into the v0.3 release gate if npm bootstrap proves to be a material adoption blocker.

---

## 3. Canonical User-facing Launcher

v0.3 uses one canonical user-facing command:

```text
workspace-lens start
```

This supersedes provisional naming such as `workspace-lens ui` for the normal product path.

`workspace-lens control` may exist as an internal/advanced foreground command for development, diagnostics, service definitions, and tests, but ordinary onboarding documentation should use `workspace-lens start`.

### 3.1 `workspace-lens start` behavior

The command must:

1. determine whether the current user's WorkspaceLens Control Runtime is already healthy;
2. if healthy, reuse it rather than creating a duplicate;
3. if absent, start the Control Runtime using the supported local launch path;
4. wait for bounded local readiness;
5. open the local WorkspaceLens WebUI in the user's default browser;
6. print the local URL as a fallback;
7. return a clear error if startup cannot reach readiness.

It must not:

- start a duplicate healthy Control Runtime;
- require the user to know the port;
- require the user to start `workspace-lens serve` separately;
- require the user to start `tunnel-client` manually after normal setup;
- place runtime API keys in argv or ordinary config;
- imply that provider-side ChatGPT setup was completed merely because the local runtime is healthy.

### 3.2 Repeated invocation

Running `workspace-lens start` again while WorkspaceLens is already healthy should behave like an idempotent launcher:

```text
existing runtime detected
-> open/reuse WebUI
-> no duplicate runtime
```

---

## 4. Browser Is a Control Surface, Not the Runtime

The browser renders the WebUI but is not the WorkspaceLens runtime.

```text
Browser tab
    |
    | loopback HTTP
    v
WorkspaceLens Control Runtime  <-- long-lived
    |
    +-- Control API
    +-- read-only MCP endpoint
    +-- application services
    `-- provider integration control
```

Therefore:

- closing the browser must not stop WorkspaceLens;
- refreshing the browser must reconstruct state from the runtime/current config;
- opening multiple browser tabs must not create multiple WorkspaceLens runtimes;
- the WebUI must not own authoritative runtime state that disappears with the tab.

---

## 5. Post-bootstrap Setup Experience

After the first successful `workspace-lens start`, the browser enters the state-driven Setup flow defined by the Interaction Spec:

```text
System
-> First Workspace
-> Tunnel
-> ChatGPT
-> Verify
```

All local steps that WorkspaceLens can safely perform should be performed through the WebUI.

Provider-owned browser/account steps remain guided rather than falsely automated.

The user should not be instructed to return to the Terminal for routine setup tasks that the v0.3 Control API owns.

---

## 6. Start at Login

The WebUI exposes an explicit setting:

```text
Start WorkspaceLens at login
```

When enabled:

1. the OS starts the WorkspaceLens Control Runtime for the current user;
2. the Control Runtime becomes locally healthy without opening a browser automatically unless explicitly configured;
3. if provider auto-connect is enabled, WorkspaceLens reconciles the official tunnel-client managed runtime;
4. if a required dependency/credential/provider setting is missing, WorkspaceLens remains available locally and surfaces `Action required` rather than exiting permanently.

The startup definition must not contain runtime API key material.

---

## 7. Tunnel Lifecycle Is Hidden From Normal Users

WorkspaceLens uses the official `tunnel-client` runtime management surface for the ChatGPT connection.

The normal WebUI language should be product-oriented:

```text
Connection
Healthy

[Restart connection]
```

not infrastructure-oriented:

```text
PID 38217
managed runtime alias
child process
pgrep
```

WorkspaceLens may invoke supported tunnel-client commands internally, including structured runtime status/connect/stop operations, but must not expose process-management vocabulary as required user knowledge.

The user should not need to run `tunnel-client` manually after initial v0.3 setup.

---

## 8. CLI Policy After v0.3 Setup

CLI remains supported for:

- advanced users;
- scripting;
- diagnostics;
- local MCP stdio clients;
- contributors;
- recovery when the WebUI/control runtime itself cannot start.

CLI is **not** the expected daily product surface.

Acceptance rule:

> After a successful initial v0.3 setup with autostart enabled, normal daily WorkspaceLens use must not require Terminal interaction.

---

## 9. Failure and Recovery

If the reasoning client cannot access WorkspaceLens, the expected recovery path is:

```text
Open WorkspaceLens WebUI
-> inspect Connection / Diagnostics
-> perform the offered recovery action
```

not:

```text
open Terminal
-> remember process commands
-> grep PIDs
-> reconstruct tunnel state
```

If the Control Runtime itself is not running, `workspace-lens start` is the single bootstrap/recovery command.

---

## 10. Acceptance Criteria

This contract is satisfied when:

1. A packaged installation can be started with one canonical launcher command.
2. `workspace-lens start` is idempotent and does not create duplicate runtimes.
3. Starting WorkspaceLens opens the WebUI without requiring the user to know the local port.
4. Closing the WebUI/browser does not stop WorkspaceLens or the provider connection.
5. Workspace/tunnel/settings administration after bootstrap is available from the WebUI.
6. `Start at login` allows normal post-login availability without manual Terminal commands.
7. Tunnel process/PID/supervision concepts are hidden from ordinary user interactions.
8. A missing tunnel dependency/credential does not prevent the local WebUI from starting and explaining the problem.
9. The npm/package-shaped runtime resolves WebUI assets without depending on `process.cwd()` or a Git checkout.
10. Native installers remain optional and do not force a desktop-shell architecture into v0.3.

# WorkspaceLens v0.2 Test Contract

Status: Required verification contract for v0.2.

The purpose of this contract is to prevent a false-green implementation where the new tools work for simple linear repositories but fail on the actual review and security boundaries that motivated v0.2.

## 1. Verification Strategy

Tests should preserve the existing repository layers:

```text
adapter tests
MCP handler/schema tests
security tests
integration tests
real ChatGPT acceptance
```

Do not create a separate test framework for v0.2.

Every critical behavior must be tested through the lowest useful unit boundary and at least once through the production-facing MCP path where practical.

## 2. Fixture Repository Model

The primary historical Git fixture should contain meaningful topology rather than only a linear history.

Minimum topology:

```text
          C---D---E  base branch
         /
A---B---+
         \
          X---Y      feature branch / reviewed head
```

The fixture must allow tests to prove that:

- `direct(E, Y)` and `merge_base(E, Y)` have intentionally different semantics;
- merge-base comparison resolves to `B -> Y`;
- local commits can exist without any remote/GitHub state.

Additional fixtures must cover:

- root commit;
- merge commit;
- detached HEAD;
- unborn repository/no commits;
- rename/delete/copy where practical;
- sensitive historical paths;
- authorized workspace as a subdirectory of a larger repository;
- oversized historical diff.

## 3. `git_history` Cases

Required:

- defaults to `HEAD`;
- returns newest-to-oldest bounded metadata;
- resolves branch name;
- resolves tag where present;
- resolves full SHA;
- resolves unambiguous abbreviated SHA;
- respects caller `max_commits` below the server ceiling;
- rejects `max_commits` outside schema bounds;
- marks truncation when additional history exists;
- handles detached HEAD;
- returns a stable error for an unborn/no-commit repository where `HEAD` cannot resolve;
- rejects invalid revision syntax before adapter history execution;
- does not return changed filenames or commit bodies.

## 4. `git_commit` Cases

Required:

### Normal commit

- resolves revision to full SHA;
- returns metadata;
- compares first parent -> commit;
- returns policy-allowed diff;
- returns correct allowed/redacted counts.

### Root commit

- `parents` is empty;
- `comparison_base` is null;
- diff semantics are empty tree -> root commit.

### Merge commit

- returns all parent SHAs;
- comparison base is first parent;
- returned diff is first parent -> merge commit;
- no implicit per-parent merge analysis is performed.

### Change shapes

- add;
- modify;
- delete;
- rename;
- filenames containing spaces/unusual allowed characters.

### Limits

- large diff is bounded;
- truncation is explicit;
- truncation never causes blocked content to appear.

## 5. `git_compare` Cases

Required:

### Direct

- base/head both resolve to commits;
- returned comparison base equals resolved base;
- diff is resolved base -> resolved head.

### Merge base

Use a genuinely diverged history fixture.

Prove:

- merge base is calculated from resolved base/head;
- returned comparison base equals the merge base;
- feature review excludes unrelated post-divergence base-branch commits;
- output differs from `direct` when fixture topology requires it.

### Edge cases

- same base/head returns valid empty diff;
- invalid base returns `GIT_REVISION_NOT_FOUND`;
- invalid head returns `GIT_REVISION_NOT_FOUND`;
- unrelated histories/no merge base returns `GIT_NO_MERGE_BASE`;
- local-only head commits work without remote state;
- working-tree changes are not included.

## 6. Revision Validation Cases

Accepted where existing in fixture:

```text
HEAD
main
feature/foo
v0.2.0
full SHA
unambiguous abbreviated SHA
```

Rejected:

```text
HEAD~1
HEAD^
main..HEAD
main...HEAD
@{upstream}
HEAD:path
:/message
--all
-leading
trailing/
foo//bar
foo.lock
revision with whitespace
revision with backslash
```

The rejection test must verify the adapter operation is not invoked with the rejected raw value.

## 7. Historical AccessPolicy Cases

These are release-blocking.

Create commits that:

- add `.env`;
- modify `.env`;
- delete `.env`;
- rename allowed file -> blocked file;
- rename blocked file -> allowed file;
- modify an allowed source file in the same commit as a blocked file;
- modify a sibling path outside an authorized workspace subdirectory.

For `git_commit` and `git_compare`, prove:

- allowed source diffs remain visible;
- blocked path names do not appear;
- blocked diff bodies do not appear;
- redacted count increases appropriately;
- outside-workspace sibling paths do not appear.

## 8. Git Execution Hardening Cases

Required regression/security tests:

- repository-local external diff config cannot cause executable invocation;
- repository-local textconv cannot cause executable invocation;
- no shell is used;
- caller cannot inject Git options through revision fields;
- Git working tree/index status before and after inspection is unchanged.

## 9. Existing Tool Regression

The existing seven tools remain additive-compatible.

Run full regression for:

```text
workspace_list
workspace_info
list_files
read_file
search_workspace
git_status
git_diff
```

No v0.2 implementation may weaken their schemas, AccessPolicy behavior, output limits, or error disclosure.

## 10. Setup Documentation Acceptance

After implementation stabilizes, validate `docs/getting-started.md` from a clean environment/account path as far as practical.

Required sequence:

```text
install dependencies/package
-> authorize one workspace
-> workspace-lens doctor
-> configure OpenAI tunnel integration
-> start required local processes
-> complete ChatGPT-side setup
-> real ChatGPT workspace_list call succeeds
```

Classify failures:

- documentation defect -> fix documentation;
- existing correctness defect that blocks the documented path -> minimal product fix allowed;
- lifecycle/productization friction -> document it and defer automation to v0.3.

Do not expand v0.2 into a setup wizard while fixing documentation.

## 11. Real End-to-End Acceptance Gate

Prepare a real local repository with:

```text
trusted base
  -> local commit A
  -> local commit B
  -> HEAD
  + uncommitted working-tree change
```

Do not push A/B/HEAD for the acceptance run.

From a real reasoning chat using WorkspaceLens only for local context, demonstrate:

1. `git_history` identifies A/B;
2. `git_commit` inspects one local-only commit;
3. `git_compare(trusted base, HEAD)` reviews the committed implementation;
4. `git_status` + `git_diff` review the uncommitted remainder;
5. `read_file` / `search_workspace` provide surrounding code context;
6. no GitHub push, code upload, shell access, or write-capable tool is required.

v0.2 does not pass acceptance until this workflow succeeds honestly on the real integration path.

## 12. Release Gate

Before reporting v0.2 complete:

```text
npm run typecheck
npm test
```

must pass, followed by the real acceptance gate above.

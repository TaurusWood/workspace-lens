# WorkspaceLens v0.3 Technical Readiness Audit

Status: Technical readiness audit for v0.3. This document evaluates the current v0.2 implementation against `v0.3-product-spec.md`, `v0.3-interaction-spec.md`, and `v0.3-ui-spec.md`. It identifies reusable foundations, missing application-layer seams, technical gates, and decisions that must be made in the Technical Architecture RFC.

This is an audit, not the final architecture decision. It intentionally avoids committing to a frontend framework, HTTP framework, process topology, credential store, or OS startup implementation before the trade-offs are resolved.

## 1. Executive Summary

The current v0.2 codebase is a good base for v0.3. The read-only Core, adapters, MCP tool contracts, workspace identity model, and provider-integration boundary should be preserved rather than redesigned.

The primary v0.3 work is outside the read-only context kernel:

```text
Existing v0.2

CLI
 |
 +--> ConfigStore
 +--> tunnel helpers / child processes
 +--> diagnostics

MCP stdio server
 |
 +--> WorkspaceRegistry(snapshot)
 +--> Core / AccessPolicy / adapters


Required v0.3 direction

CLI --------------------+
                        |
WebUI / Control API ----+--> Shared Application Services
                                  |
                                  +--> Workspace administration
                                  +--> Diagnostics/status
                                  +--> Tunnel lifecycle
                                  +--> Startup/credential adapters
                                  |
                                  v
                         Existing Core / Config / Integrations
```

The main conclusion is:

> v0.3 should add a shared application/control layer around the existing Core, not turn the Core into a GUI/runtime framework.

The largest technical risks are:

1. live configuration refresh while the MCP server is running;
2. safe concurrent mutation of configuration by CLI and WebUI;
3. ownership and supervision of the long-lived local runtime and official tunnel client;
4. secure credential availability for autostart;
5. localhost control-plane browser security;
6. packaging the WebUI and local control runtime without duplicating product logic.

None of these require weakening the existing read-only MCP boundary.

## 2. Current Architecture Readiness

### 2.1 Core and access-policy layer — REUSE

Current Core already contains the durable security primitives v0.3 needs:

- explicit workspace identity;
- enabled/disabled authorization state;
- canonical workspace roots;
- path containment;
- shared AccessPolicy;
- bounded read/search/Git operations;
- no write-capable repository operations;
- no shell passthrough.

`WorkspaceRegistry` resolves workspaces by explicit `workspace_id`; it does not model a current/recent workspace. This aligns with the v0.3 multi-chat/multi-workspace contract.

**Decision:** preserve Core semantics. Do not add WebUI, tunnel lifecycle, HTTP, ChatGPT Project, session, or process-management concepts to Core.

### 2.2 MCP layer — REUSE WITH TEST EXPANSION

The MCP layer already has a clean request-scoped shape:

```text
MCP request
  -> parsed args
  -> explicit workspace_id
  -> ToolContext
  -> WorkspaceRegistry
  -> AccessPolicy / adapter
```

`ToolContext` contains limits, logger, registry, and policy. It does not contain mutable session/workspace state. `tool-runner` derives `workspace_id` from each request for logging rather than maintaining a global active target.

This is a strong foundation for concurrent requests targeting different workspaces.

**Required v0.3 additions:**

- automated concurrent multi-workspace isolation tests;
- tests proving WebUI/control-plane state cannot influence MCP workspace selection;
- live-config behavior tests after the Technical RFC chooses reload semantics.

### 2.3 Config schema — MOSTLY REUSE

The config schema already models the core Workspace identity correctly:

```text
workspace_id
name
root
enabled
```

`workspace_id` is stable and separate from display name. This matches the Product/Interaction specs.

The current schema should remain small. v0.3 should not put runtime process state, ChatGPT session state, CR/Plan state, API keys, or transient health into the workspace config.

A config-version bump should occur only if persistent v0.3 product settings actually require schema changes.

### 2.4 ConfigStore — EXTEND / HARDEN

`ConfigStore` already provides valuable guarantees:

- canonicalizes existing roots;
- rejects duplicate and overlapping roots;
- persists with restrictive file permissions;
- uses temp-file + rename for single-write atomic replacement;
- keeps workspace IDs stable after creation.

However, it currently exposes only the administration operations needed by v0.2 (`add`, `remove`, generic `load/save`). v0.3 requires first-class operations for at least:

- rename display name;
- enable workspace;
- disable workspace;
- validate workspace;
- possibly update product settings such as absolute-path exposure or startup preferences, depending on final ownership.

More importantly, `load -> mutate -> save` currently has no stale-write detection. Two actors can race:

```text
WebUI loads config A
CLI changes A -> B
WebUI saves old A' over B
```

Atomic rename prevents partial-file corruption but not lost updates.

**Technical gate:** the RFC must define one mutation strategy, e.g. serialized writes through the long-lived control service, revision/CAS semantics, file locking, or a narrowly scoped combination. CLI compatibility means the design must handle CLI mutations while WebUI is open.

### 2.5 WorkspaceRegistry — REUSE SEMANTICS, CHANGE REFRESH MODEL

The registry currently receives a `WorkspaceLensConfig` snapshot in its constructor.

`runServe()` loads config once at MCP server startup:

```text
ConfigStore.load()
    -> new WorkspaceRegistry(config)
    -> MCP server stays alive
```

Therefore a workspace added/disabled/renamed after server startup is not automatically reflected in that running MCP process.

This conflicts with the v0.3 product expectation that workspace management in WebUI immediately changes what the reasoning client can access.

**Technical gate:** RFC must select one explicit model:

- dynamic registry/config provider read on request;
- watched immutable snapshots swapped atomically in-process;
- control-service-driven reload IPC;
- controlled MCP/tunnel restart after configuration changes.

The choice must preserve request isolation and must never expose a partially written config.

A silent requirement that users manually restart the tunnel after every workspace change would violate the v0.3 UX goal and is not acceptable as the default behavior.

## 3. CLI Readiness

### 3.1 Current CLI — THIN USER INTERFACE, BUT BUSINESS LOGIC IS EMBEDDED

The CLI is small and clear, but commands currently orchestrate product operations directly. For example `add` directly creates `ConfigStore` and calls `store.add()`, while `connect chatgpt` directly coordinates config loading, tunnel detection, profile validation, doctor, process discovery, and process spawning.

This is appropriate for v0.2 but becomes a duplication risk in v0.3.

If the WebUI independently reproduces this logic, WorkspaceLens will have two behavior models:

```text
CLI rules != WebUI rules
```

That would violate the existing v0.3 requirement that CLI and WebUI converge on the same state and semantics.

### 3.2 Required extraction — SHARED APPLICATION SERVICES

Before adding WebUI endpoints, extract use-case-oriented services such as:

```text
WorkspaceAdminService
  list()
  add()
  rename()
  setEnabled()
  remove()
  validate()

DiagnosticsService
  checkSystem()
  checkWorkspaces()
  checkProviderIntegration()
  sanitizedReport()

ChatGptConnectionService
  inspect()
  configureProfile()
  start()
  stop()
  restart()
  repair()
```

Names are illustrative. The important rule is ownership:

> CLI and WebUI adapters call the same application services; neither owns the business rules.

The services may compose existing `ConfigStore`, `WorkspaceRegistry`, tunnel integration functions, and Core types rather than moving those concerns into one large manager class.

## 4. Provider / Tunnel Integration Readiness

### 4.1 Existing OpenAI integration — GOOD PROTOTYPE FOUNDATION

The current integration correctly stays outside Core and drives only the official `tunnel-client`.

Existing reusable capabilities include:

- tunnel-client detection;
- profile location/inspection;
- exact profile init arguments;
- official `doctor` invocation;
- local `/healthz` and `/readyz` probing;
- detection of a running daemon/profile;
- no credential-value logging;
- explicit avoidance of reimplementing the tunnel protocol.

These map directly to v0.3 Connection and Diagnostics UI requirements.

### 4.2 Process detection/supervision — NEEDS REDESIGN

Current `findRunningDaemon()` uses `pgrep -fl tunnel-client` and command-line parsing. This is sufficient for the current macOS-oriented CLI prototype but is not a durable process supervisor.

v0.3 needs to know not only whether some process exists, but also:

- whether WorkspaceLens owns/started it;
- which profile it is using;
- whether it is starting/stopping;
- whether it crashed;
- whether restart is safe;
- whether a duplicate process would conflict;
- how autostart hands ownership back after login/reboot.

**Technical gate:** define one lifecycle owner and supervision model in the RFC. Avoid making both the OS startup mechanism and the WebUI independently believe they own the same child process.

### 4.3 Credential model — BLOCKING TECHNICAL DECISION

Current ChatGPT tunnel flow expects `CONTROL_PLANE_API_KEY` in the environment and deliberately does not persist it.

That works for a foreground terminal process but conflicts with the v0.3 target:

```text
login
 -> WorkspaceLens autostarts
 -> tunnel becomes available
 -> no terminal export required
```

The key must not be placed in ordinary WorkspaceLens JSON config or surfaced to diagnostics/UI after entry.

**Technical gate:** RFC must define a secure credential source appropriate to supported OSes, with macOS-first acceptable. Candidate classes include OS credential stores/keychains or another provider-supported credential mechanism. The exact choice must be verified against tunnel-client behavior before implementation.

The WebUI interaction must treat credentials as write-only secret input where possible.

## 5. Diagnostics and Logging Readiness

### 5.1 Diagnostics — EXTRACT AND STRUCTURE

The current `doctor` command already checks useful facts:

- Node version;
- config validity;
- workspace availability;
- Git availability;
- MCP server construction;
- tunnel-client/profile availability.

But it constructs human-readable CLI output directly.

v0.3 needs structured diagnostic results that can be rendered by both CLI and WebUI:

```text
{
  id,
  group,
  status: pass | warning | fail | unknown,
  summary,
  detail?,
  action?
}
```

The exact DTO belongs in the RFC/implementation contract, but `doctor` should become a presentation adapter over shared checks rather than the source of truth.

### 5.2 Logging — KEEP LIGHT IN v0.3

Current metadata-only logger already records tool name, workspace ID, duration, error code, count, and truncation without repository content.

This is compatible with future v0.4 Activity Log work.

For v0.3, do not build a persistence/analytics subsystem merely because logs exist. Only expose last/current runtime facts needed for recovery if the chosen process model can do so safely.

## 6. WebUI / Local Control Surface Readiness

### 6.1 No existing Web stack — CLEAN SLATE

The current package is intentionally small:

- Node 24;
- TypeScript;
- official MCP SDK;
- Zod;
- Vitest.

There is no HTTP server, frontend framework, bundler, component library, or browser test stack.

This means v0.3 has no legacy frontend constraint, but every new dependency must justify itself.

The Technical RFC should optimize for the actual product shape:

- local-only SPA/control UI;
- no SEO;
- no SSR requirement;
- no hosted multi-tenant backend;
- few routes/pages;
- modest state complexity;
- long-lived local Node runtime already required.

A full-stack web framework should not be selected by default merely because it is common for public web applications.

### 6.2 Local HTTP/API boundary — NEW

v0.3 requires a browser-facing local control API for:

- workspace administration;
- connection/status operations;
- diagnostics;
- settings/autostart;
- helper text generation/copy source.

This API is an administrative capability and is more privileged than the read-only MCP surface because it may change WorkspaceLens configuration and process state.

It therefore needs an explicit browser security contract:

- loopback binding only by default;
- strict Host/Origin handling;
- no permissive CORS;
- CSRF-resistant mutations;
- no API-key/credential reflection;
- no generic filesystem or process endpoints;
- explicit bounded operations rather than command passthrough.

### 6.3 Folder selection — TECHNICAL GATE

The product interaction says `Choose local folder`, but an ordinary browser page cannot be assumed to obtain arbitrary canonical absolute paths with desktop-native semantics.

The RFC must define how localhost WebUI obtains a root safely without introducing a generic filesystem browser/API.

Possible solution classes may include:

- a control-service-owned native folder chooser launched locally;
- explicit path entry/paste with server-side validation;
- a narrowly scoped local directory-selection flow.

The decision should minimize platform complexity and preserve the explicit-authorization security story.

## 7. Process Model Readiness

Current ChatGPT path is:

```text
user / CLI
  -> tunnel-client run --profile workspace-lens
       -> tunnel-client is long-lived
       -> tunnel-client spawns `workspace-lens serve`
```

There is currently no independent long-lived WorkspaceLens control process.

v0.3 adds requirements that need a locally reachable owner even when the tunnel is stopped:

- serve the WebUI;
- serve the control API;
- inspect configuration;
- start/restart tunnel-client;
- expose diagnostics;
- participate in autostart.

Therefore the current process shape cannot satisfy v0.3 unchanged.

**RFC decision required:** define which local process is the durable product owner and how it relates to the tunnel-spawned MCP server.

The design should satisfy these invariants:

1. WebUI remains available when tunnel-client is stopped/broken.
2. There is one clear owner for starting/stopping/restarting the managed tunnel runtime.
3. Core/MCP semantics remain usable through stdio clients independently of the WebUI.
4. Provider-specific lifecycle remains outside Core.
5. A tunnel failure does not corrupt workspace configuration.
6. Startup/autostart does not create duplicate competing supervisors.

## 8. Build and Packaging Readiness

Current production build is plain TypeScript compilation from `src` to `dist`.

A browser UI introduces at least one additional asset-build concern. The RFC should decide whether the repository remains one package with two build stages or adopts another minimal structure.

Requirements:

- one normal installation should include the control UI assets;
- the Node control runtime should be able to serve those assets locally;
- CLI/stdio usage must remain available without requiring a browser runtime;
- development workflow should remain simple;
- build output used by the tunnel profile must remain stable or have a migration/repair path.

Do not introduce Electron solely to package static WebUI assets unless later evidence demonstrates a native-shell requirement.

---

## 9. Testing Readiness

The existing repository already has useful separation across core, adapters, MCP, integrations, security, and integration tests.

v0.3 should preserve that structure and add new coverage rather than replacing it with UI-only end-to-end tests.

Required new test areas include:

### Application-service tests

- workspace add/rename/enable/disable/remove semantics;
- validation and error shaping;
- diagnostics DTOs;
- tunnel lifecycle state transitions.

### Config concurrency tests

- CLI/WebUI stale-write prevention;
- atomic persistence remains fail-closed;
- concurrent workspace operations do not lose unrelated changes.

### Live-config tests

- newly enabled workspace becomes visible to MCP according to chosen refresh model;
- disabled workspace stops being accessible without undefined transitional behavior;
- no request switches workspace because another request/config operation occurs concurrently.

### Control API security tests

- loopback-only default;
- rejected cross-origin mutation;
- rejected malformed/oversized input;
- no generic path/process access;
- no secret leakage in errors/diagnostics.

### Process/lifecycle tests

- start/stop/restart idempotency;
- crash detection/recovery;
- no duplicate managed tunnel runtime;
- UI/control runtime remains available when tunnel is unhealthy.

### UI tests

Keep UI tests focused on product-critical flows rather than pixel coverage:

- first-run state rendering;
- workspace management;
- layered connection state;
- destructive confirmation;
- error/action feedback;
- narrow-width interaction accessibility.

## 11. Technical RFC Decision List

The Technical Architecture RFC should make explicit decisions, in this order:

1. **Process topology and lifecycle owner** — what stays alive, who starts whom, and who owns restart/autostart.
2. **Live configuration model** — how running MCP requests see workspace changes.
3. **Shared application-service boundary** — APIs used by CLI and WebUI.
4. **Configuration concurrency model** — how stale writes/lost updates are prevented.
5. **Credential model** — how tunnel credentials are safely available to autostart.
6. **Local Control API security model** — loopback, Host/Origin, CSRF/session strategy, bounded endpoints.
7. **Folder-selection strategy** — how local roots are selected without generic filesystem exposure.
8. **Backend HTTP implementation** — minimal Node HTTP layer/framework based on required behavior.
9. **Frontend stack** — minimal SPA/tooling/component approach consistent with UI Spec.
10. **Build/package/startup layout** — production asset paths, commands, install/update assumptions.
11. **Test contract** — service, concurrency, lifecycle, security, and UI integration gates.

The process/config/credential decisions should precede frontend-framework selection because they determine the actual runtime shape of the product.

## 12. Recommended Next Step

Proceed to `v0.3-technical-architecture-rfc.md`.

The RFC should not revisit the established product/UI boundaries. Its job is to choose the smallest architecture that satisfies them while preserving the v0.2 security contracts.

The key design question is no longer whether v0.3 is feasible. It is:

> What is the minimum long-lived local architecture that can safely provide WebUI control, live multi-workspace configuration, tunnel supervision, and autostart without duplicating Core or turning WorkspaceLens into a general-purpose runtime?

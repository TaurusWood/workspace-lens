# WorkspaceLens v0.2 Implementation Plan

Status: Execution plan for v0.2 after contract freeze.

This plan implements `v0.2-requirements.md`, `v0.2-mcp-tools-contract.md`, `v0.2-security-contract.md`, and `v0.2-test-contract.md` without expanding into v0.3 productization.

## 1. Source of Truth

Read in this order before implementation:

1. `docs/product-experience.md`
2. `docs/security-model.md`
3. `docs/mcp-tools-spec.md`
4. `docs/v0.2-requirements.md`
5. `docs/v0.2-security-contract.md`
6. `docs/v0.2-mcp-tools-contract.md`
7. `docs/v0.2-test-contract.md`
8. this implementation plan

The v0.2 documents are normative deltas to the v0.1 contracts. Do not reinterpret them to make implementation easier.

If a contradiction is discovered, stop that implementation slice and resolve the contract rather than silently choosing behavior.

## 2. Fixed Decisions

Implementation MUST preserve:

- TypeScript / existing Node runtime;
- existing Core/adapter/MCP dependency direction;
- one `GitAdapter` inspection boundary rather than a second historical-Git subsystem;
- fixed Git command templates;
- no shell;
- no arbitrary Git args;
- shared `AccessPolicy`;
- central output limits;
- existing result/error envelope;
- provider independence;
- no write capability.

Public tool names are frozen for v0.2:

```text
git_history
git_commit
git_compare
```

## 3. Phase 0 — Contract Freeze

Deliverables are the four v0.2 contract documents plus this plan.

Gate:

- tool inputs/outputs are defined;
- revision semantics are defined;
- `direct` / `merge_base` are defined;
- root/merge commit behavior is defined;
- historical redaction is defined;
- test topology and acceptance are defined;
- v0.3 features remain explicit non-goals.

No production code is changed in this phase.

## 4. Phase 1 — Shared Historical Git Primitives

Extend the existing `src/adapters/git.ts` rather than creating a second Git execution boundary.

Introduce the smallest internal primitives needed by all three tools, conceptually:

```text
validateRevisionInput
resolveCommit
readCommitMetadata
readHistory
resolveMergeBase
compareCommittedRevisions
historical diff path filtering/redaction
```

Exact private names are implementation details.

### 4.1 Revision validation

Add one shared validator/schema helper used by every public revision field.

The validation must enforce the v0.2 restricted commitish grammar before Git resolution.

Resolution should use a fixed internal template and return a full commit SHA.

Do not add a generic rev-parse helper that accepts arbitrary caller syntax.

### 4.2 Commit metadata

Use deterministic machine-readable output and parse it without depending on locale-sensitive human formatting.

Return only contract fields.

### 4.3 Historical diff filtering

Reuse current repository/workspace mapping and AccessPolicy logic from `GitAdapter`.

Prefer the same safe strategy already used by current diff handling:

1. determine changed paths through a fixed machine-readable operation;
2. map repository-relative paths into the authorized workspace;
3. classify old/new paths through `AccessPolicy`;
4. request/retain diff content only for allowed entries;
5. redact sensitive/out-of-workspace entries;
6. apply the central byte budget;
7. report truncation explicitly.

Do not obtain unrestricted historical diff output and assume string filtering alone is a sufficient security boundary when a path-filtered Git operation can avoid it.

### Phase 1 tests

Implement adapter/security fixtures from `v0.2-test-contract.md` before exposing MCP tools.

Gate:

- resolution grammar is enforced;
- normal/root/merge metadata primitives work;
- historical secret paths cannot leak;
- subdirectory workspace containment works;
- large output is bounded;
- existing `git_status`/`git_diff` adapter tests still pass.

## 5. Phase 2 — `git_history`

Add:

- schema;
- MCP tool handler;
- adapter integration;
- server registration;
- structured/text fallback result as used by existing tools;
- tests.

Keep handler logic thin. Security and Git semantics belong in shared adapter/core layers.

Gate:

- all `git_history` contract tests pass;
- full typecheck/test suite passes.

## 6. Phase 3 — `git_commit`

Add the public tool using Phase 1 primitives.

Required implementation cases:

- normal commit first-parent diff;
- root commit empty-tree diff;
- merge commit first-parent diff;
- add/modify/delete/rename;
- sensitive path redaction;
- subdirectory workspace filtering;
- central diff truncation.

Gate:

A local commit not present on GitHub can be completely inspected through the MCP tool while blocked historical content remains inaccessible.

Run typecheck and the full suite.

## 7. Phase 4 — `git_compare`

Implement both frozen modes:

```text
direct
merge_base
```

Use resolved SHAs for all comparison operations.

`merge_base` must be tested against a truly diverged repository fixture so that the test would fail if it accidentally behaved like direct comparison.

Do not include working-tree state.

Gate:

- direct semantics pass;
- merge-base semantics pass;
- unrelated histories return stable error;
- local-only head works;
- historical redaction and truncation pass;
- full suite passes.

## 8. Phase 5 — MCP and Security Regression Gate

At this point, stop feature work.

Verify:

- all ten tools register correctly;
- unknown properties are rejected;
- new error codes normalize correctly;
- repository content is still treated as untrusted data;
- current seven tools are behaviorally unchanged;
- no MCP schema contains generic `command`, `args`, shell, or arbitrary Git controls;
- no historical tool bypasses AccessPolicy;
- Git inspection leaves repository/index state unchanged.

Run:

```text
npm run typecheck
npm test
```

No phase may proceed with a red security regression.

## 9. Phase 6 — Canonical Setup Documentation

Create `docs/getting-started.md` after tool behavior is stable.

Document the actual current path rather than an aspirational v0.3 path.

Required sections:

1. prerequisites;
2. install/build WorkspaceLens;
3. authorize a workspace;
4. run `workspace-lens doctor`;
5. configure OpenAI Secure MCP Tunnel;
6. start WorkspaceLens and required tunnel process;
7. configure the ChatGPT app/connector side;
8. verify `workspace_list` from a real chat;
9. perform a first review;
10. daily usage;
11. troubleshooting.

Clearly label which steps belong to WorkspaceLens, OpenAI Platform, and ChatGPT.

Update README only enough to point users to the canonical guide and avoid duplicated setup instructions drifting apart.

If the clean-path exercise finds a blocking correctness bug, fix only the minimal defect. Do not implement a daemon, WebUI, autostart, or onboarding wizard.

## 10. Phase 7 — Real Acceptance

Use a real local repository containing:

```text
trusted base
  -> local commit A
  -> local commit B
  -> HEAD
  + working-tree changes
```

Do not push the reviewed local commits for the acceptance run.

From a real ChatGPT reasoning conversation through the supported tunnel path:

```text
git_history
  -> git_commit
  -> git_compare(base, HEAD)
  -> git_status
  -> git_diff
  -> read_file/search_workspace
```

Confirm the reviewer can reason about both committed and uncommitted local state without GitHub or uploads.

Record any platform UX limitation honestly rather than compensating with v0.3 functionality.

Gate:

All criteria in `v0.2-requirements.md` and `v0.2-test-contract.md` pass.

## 12. Explicit Stop Conditions

Stop and revisit the contract instead of improvising if implementation would require any of the following:

- accepting arbitrary Git revision expressions;
- exposing generic Git args;
- weakening AccessPolicy for historical content;
- reading blocked historical diff bodies as a normal path and relying only on model behavior for safety;
- adding a database/index merely for history;
- adding provider-specific code to Core/GitAdapter;
- adding write-capable Git behavior;
- implementing v0.3 lifecycle/UI features to complete v0.2.

## 13. Completion Definition

v0.2 is complete when:

```text
contracts satisfied
+ automated suite green
+ canonical setup path verified
+ real local-only committed + working-tree review succeeds
```

Code written without the final real acceptance gate is not sufficient for release completion.

# WorkspaceLens v0.3 Test Contract

Status: Required pre-implementation test contract for v0.3.

This document defines **what v0.3 must prove** before implementation is considered correct. It is intentionally implementation-oriented enough for a local coding harness to turn into executable tests, but it does not prescribe production-code design beyond the accepted upstream contracts.

Upstream authority:

- `v0.3-product-spec.md`
- `v0.3-interaction-spec.md`
- `v0.3-ui-spec.md`
- `v0.3-technical-readiness-audit.md`
- `v0.3-technical-architecture-rfc.md`
- `v0.3-bootstrap-distribution-contract.md`
- `v0.3-control-plane-security-contract.md`
- `v0.3-implementation-plan.md`

The governing testing rule is:

> **Define the observable behavior first. The harness implements evidence for that behavior. Production code must satisfy the contract; tests must not be weakened merely to make implementation pass.**

---

## 1. Ownership and Workflow

### 1.1 Contract owner

The product/review side owns:

- required behavior;
- security invariants;
- user-visible acceptance criteria;
- PASS / FAIL / BLOCKED semantics;
- decisions about changing this contract.

### 1.2 Local harness owner

The local coding harness owns:

- translating this document into executable tests;
- test fixtures, stubs, helpers, and deterministic local environments;
- running the tests and recording evidence;
- reporting contract gaps or technical blockers;
- keeping tests maintainable as implementation progresses.

The harness MUST NOT independently:

- relax an expected result;
- replace a required black-box assertion with an implementation-detail assertion;
- mark a required test `skip`, `todo`, or equivalent to obtain a green suite;
- remove an existing regression test because new code makes it inconvenient;
- change a security requirement;
- reinterpret a product requirement to match the implementation;
- add production behavior solely to satisfy a test artifact that contradicts upstream contracts.

If the harness believes a contract is infeasible or internally inconsistent, it MUST return:

```text
CONTRACT BLOCKED
Contract ID: <id>
Reason: <technical/product conflict>
Evidence: <reproduction / source / result>
Suggested options: <bounded alternatives>
```

and stop changing that contract until reviewed.

---

## 2. Test Strategy

v0.3 uses five test layers.

```text
L0  Existing v0.2 regression
L1  Application/service contracts
L2  Integration and adapter contracts
L3  Security contracts
L4  Product-flow / installed-package E2E
```

The purpose of this structure is to avoid two failure modes:

1. a large E2E suite that is slow and unable to identify the failing boundary;
2. a large mock-heavy unit suite that stays green while the real product path is broken.

### 2.1 Evidence hierarchy

Prefer, in order:

1. real in-process behavior through public application/service interfaces;
2. real local HTTP behavior against an ephemeral Control Runtime;
3. real child-process behavior using a controlled stub executable at the external-process boundary;
4. pure unit tests for deterministic transforms/parsers;
5. mocks only where the external dependency cannot be safely/reliably exercised in CI.

A mock may prove WorkspaceLens's reaction to an external contract. It does not prove that the external product actually implements that contract. That distinction is especially important for Technical Gates B and C.

### 2.2 No false-green principle

A test does not satisfy a contract merely because:

- it asserts that a helper function was called;
- it mocks the same function that contains the behavior being tested;
- it asserts only HTTP status while ignoring state mutation;
- it checks a UI label without checking the underlying API state;
- it runs only against one workspace when the contract is about isolation;
- it checks only a happy path when the security contract requires rejection behavior.

Every contract below states the minimum evidence that must exist.

## 3. Pre-implementation RED Baseline

The harness should create a dedicated v0.3 contract suite before production implementation begins.

Recommended shape:

```text
tests/v0.3/
  gates/
  application/
  integration/
  security/
  product/
```

The exact directories may change if the repository test structure has a better equivalent.

### 3.1 Default regression suite

Existing `npm test` / existing v0.2 tests MUST remain green throughout v0.3 development.

### 3.2 New contract suite

New v0.3 tests may initially be RED because production interfaces do not yet exist. Do **not** hide this by skipping required tests.

Use a separate contract command/config if needed, for example conceptually:

```text
npm run test:v0.3
```

The harness must record a baseline report that distinguishes:

- expected RED because a v0.3 capability is not implemented yet;
- unexpected RED caused by a broken v0.2 regression;
- BLOCKED because an external technical assumption cannot yet be proven.

### 3.3 Green progression

Each implementation slice owns a defined subset of contract IDs. A slice is not complete until:

- its owned required contracts are green;
- existing v0.2 regression remains green;
- no unrelated v0.3 contract regresses from green to red.

# 4. L0 — v0.2 Regression Contract

## REG-001 — MCP tool surface unchanged

**Goal:** v0.3 must not accidentally alter the public read-only tool contract.

**Evidence:**

- existing MCP contract suite remains green;
- tool names remain the accepted ten-tool surface;
- existing input/output envelope semantics remain compatible.

**Fail if:** a Control API operation appears as an MCP tool, an existing tool disappears, or response semantics change unintentionally.

## REG-002 — read-only security unchanged

**Goal:** v0.3 productization must not weaken repository access controls.

**Evidence:** existing AccessPolicy/security tests remain green, including path containment, sensitive-path blocking, and bounded outputs.

## REG-003 — stdio remains supported

**Action:** invoke the existing stdio MCP path (`workspace-lens serve`) in a test fixture.

**Expected:** existing local MCP behavior still works after the Control Runtime / HTTP path is introduced.

## REG-004 — existing config remains readable

**Precondition:** a valid v0.2 `config.json` with authorized workspaces.

**Action:** load it through v0.3 configuration/application paths.

**Expected:** no re-authorization or destructive migration is required.

# 5. L1 — Application and Configuration Contracts

## APP-001 — add workspace through shared application service

**Precondition:** empty valid config; readable directory A.

**Action:** add A through `WorkspaceAdminService` (or final equivalent shared application interface).

**Expected:**

- one workspace exists;
- root is canonicalized;
- stable `workspace_id` is assigned according to existing rules;
- workspace is enabled by default;
- no user workspace file is modified.

## APP-002 — duplicate and overlapping authorization rejected

**Action:** attempt duplicate root, symlink-equivalent duplicate, descendant, and ancestor authorization.

**Expected:** each rejected with stable product/config error; existing authorization remains unchanged.

## APP-003 — rename does not change identity or root

**Action:** rename workspace display name.

**Expected:**

- `workspace_id` unchanged;
- canonical root unchanged;
- enabled state unchanged.

## APP-004 — disable is immediate and reversible

**Action:** disable workspace A, then enable it again.

**Expected:**

- disabled A is unavailable to subsequent MCP content operations;
- re-enable revalidates the existing root;
- no local repository file is modified.

## APP-005 — remove removes authorization only

**Action:** remove workspace A.

**Expected:** config authorization removed; underlying directory/files remain untouched.

## APP-006 — invalid root fails closed

**Precondition:** registered root disappears or becomes inaccessible.

**Expected:** workspace reports unavailable/error; system never falls back to a parent directory or another workspace.

---

## CFG-001 — atomic concurrent mutation without lost update

**Precondition:** two independent processes/services target the same config.

**Action:** perform two non-conflicting mutations concurrently, e.g. add A and add B.

**Expected:** final valid config contains both accepted mutations exactly once.

**Must prove:** separate-process concurrency, not only two async calls sharing one in-memory mutex.

## CFG-002 — no partial JSON during interrupted/concurrent writes

**Action:** exercise mutation under contention/failure conditions supported by the chosen lock/write implementation.

**Expected:** readers observe either a previous complete config or next complete config; never partial JSON produced by the mutation path.

## CFG-003 — lock failure is explicit

**Action:** force lock timeout/contention failure.

**Expected:** mutation fails explicitly; it does not silently continue unlocked and does not overwrite newer state.

## CFG-004 — stale-state write cannot overwrite newer config

**Precondition:** actor A reads config; actor B changes config; actor A attempts a mutation.

**Expected:** application mutation operates on the latest config after lock acquisition, preserving B's accepted change.

## CFG-005 — malformed current config fails closed

**Action:** make config malformed before an operation.

**Expected:** no stale broader authorization is silently used; operation returns a stable configuration error.

# 6. Live Configuration and Workspace Isolation

## LIVE-001 — add workspace visible without runtime restart

**Precondition:** Control Runtime already running with workspace A.

**Action:** add workspace B through the shared application/Control API path.

**Required evidence:**

- the Control Runtime PID/process instance does not restart;
- the next `workspace_list` request contains B;
- A remains available.

**Fail if:** B appears only after restarting WorkspaceLens or the tunnel.

## LIVE-002 — disable visible on next MCP request

**Action:** disable A while Control Runtime is running, then issue an MCP request for A.

**Expected:** next request rejects A as disabled according to the existing tool/error contract without runtime restart.

## LIVE-003 — remove visible on next MCP request

**Action:** remove A authorization while Control Runtime is running.

**Expected:** next A request returns not-found/unavailable according to the accepted contract; it must not use an old in-memory authorization snapshot.

## ISO-001 — concurrent workspace filesystem isolation

**Precondition:** A and B contain distinct sentinel files/content.

**Action:** issue concurrent read/list/search requests to A and B.

**Expected:** no response for A contains B-only filesystem content and vice versa.

## ISO-002 — concurrent Git cwd isolation

**Precondition:** A and B are separate Git repositories with distinct branches/status/commits.

**Action:** issue concurrent Git operations.

**Expected:** each result reflects only its requested repository.

## ISO-003 — failure never redirects workspace identity

**Action:** make A invalid while B remains valid; request A and B concurrently.

**Expected:** A fails; B succeeds; A never falls through to B or any recent/current workspace.

# 7. Technical Gate Contracts

These gates occur before full v0.3 implementation. Their purpose is to validate architectural assumptions, not to build the product prematurely.

## GATE-A — Streamable HTTP MCP parity

**Question:** can the accepted MCP SDK/runtime expose the existing WorkspaceLens tool contract through a loopback Streamable HTTP endpoint without changing Core/tool semantics?

### GATE-A-1 — minimal HTTP MCP round trip

**Setup:** temporary local server using the intended SDK transport with a test registry.

**Action:** MCP client connects/calls at least `workspace_list` and one content-bearing tool.

**PASS:** request/response succeeds through HTTP using the existing tool definitions/envelope semantics.

### GATE-A-2 — stdio/HTTP semantic parity

For the same fixture and representative operations:

- `workspace_list`;
- one filesystem read;
- one Git operation;
- one stable error case;

compare meaningful structured results across stdio and HTTP.

**PASS:** no product/tool semantic fork is required.

### GATE-A-3 — stateless/request isolation feasibility

**Action:** concurrent HTTP MCP calls to different workspaces.

**PASS:** no protocol/session requirement forces a mutable global current workspace.

### GATE-A result

- **PASS:** architecture may proceed.
- **FAIL:** document exact SDK/transport blocker and return for architecture review.
- **BLOCKED:** only if the environment cannot exercise the SDK assumption; include evidence.

Gate A must not silently migrate MCP SDK major versions merely to pass.

---

## GATE-B — official tunnel-client managed runtime contract

**Question:** does the installed/supported official `tunnel-client` provide the structured runtime lifecycle assumed by the RFC?

### GATE-B-1 — command discovery

Verify the real supported binary exposes the required managed-runtime command family and HTTP MCP target option used by the RFC.

### GATE-B-2 — JSON lifecycle shape

Against a controlled/non-production test configuration where feasible, capture and document structured output for:

- runtime connect/create path;
- status;
- stop;
- missing alias/runtime;
- unhealthy/error state.

**PASS:** WorkspaceLens can implement a typed adapter without scraping human-readable process listings/log text.

### GATE-B-3 — secret reference behavior

Verify the runtime key can be supplied by the supported secret-reference mechanism without placing the literal secret in argv/output.

### GATE-B-4 — adapter fixture capture

Create sanitized fixture JSON representative of the real command output for deterministic adapter tests.

**Important:** tests may stub the executable after real contract discovery. A stub alone does not satisfy Gate B.

### GATE-B result

- **PASS:** freeze the exact supported fields/commands consumed by WorkspaceLens.
- **FAIL:** return to Technical RFC before building ConnectionService.
- **BLOCKED:** include binary/version/platform evidence.

---

## GATE-C — SecretStore feasibility on Node 24

**Question:** can v0.3 store/retrieve the runtime credential through an OS-backed secret store without plaintext fallback and without making installation impractical?

### GATE-C-1 — candidate install/build

Validate candidate secret-store dependency/adapter on Node 24 in the supported development platform(s).

### GATE-C-2 — set/get/delete

In a test namespace/key:

- set secret;
- retrieve exact value;
- delete secret;
- verify absence after delete.

The test must never print the literal secret.

### GATE-C-3 — unavailable-store behavior

Simulate or detect unavailable credential storage.

**Expected:** product can report `Action required`; it must not fall back automatically to plaintext config.

### GATE-C result

- **PASS:** chosen implementation is acceptable for supported platform scope.
- **FAIL:** choose another OS-backed adapter or narrow initial OS support explicitly.
- **BLOCKED:** report platform/environment limitation; do not introduce plaintext fallback.

# 8. L2 — Control Runtime and HTTP Integration Contracts

## HTTP-001 — loopback runtime starts and reports health

**Action:** start Control Runtime on an ephemeral or test port.

**Expected:** health/readiness endpoint responds locally; runtime can shut down cleanly.

## HTTP-002 — single runtime ownership

**Action:** start a second normal Control Runtime for the same state/config root.

**Expected:** duplicate ownership is rejected or existing healthy runtime is reused according to the RFC; two independent managers must not coexist accidentally.

## HTTP-003 — WebUI assets served from installed/module location

**Precondition:** runtime launched from a working directory unrelated to the repository root.

**Expected:** built UI assets resolve correctly; no `process.cwd()` dependency.

## HTTP-004 — `/mcp` and `/api/v1/*` capabilities remain separated

**Expected:** MCP surface cannot invoke workspace administration, settings, secret, startup, or tunnel lifecycle operations.

## START-001 — canonical bootstrap starts/reuses runtime

**Action:** execute the final `workspace-lens start` behavior against a controlled environment.

**Expected:**

- healthy existing runtime is reused rather than duplicated;
- absent runtime is started;
- local WebUI URL is made available/opened through an injectable browser-launch adapter;
- command returns an actionable error if local runtime cannot start.

## START-002 — browser lifecycle is independent

**Action:** start runtime, open/probe WebUI, then terminate the browser test client/tab equivalent while leaving runtime intact.

**Expected:** Control Runtime stays healthy and MCP endpoint remains available.

# 9. Connection / Tunnel Adapter Contracts

## CONN-001 — structured status normalization

Given captured Gate-B fixture JSON, normalize into stable product states such as ready/stopped/unhealthy/action-required without leaking tunnel implementation details to UI/application callers.

## CONN-002 — exact argument arrays

For connect/status/stop/restart paths, assert exact executable plus argument-array construction.

**Forbidden:** `shell: true`, command-string concatenation with user input, literal secret in argv.

## CONN-003 — external command failure is bounded

Exercise:

- binary missing;
- nonzero exit;
- timeout;
- malformed JSON;
- alias missing;
- unhealthy runtime.

**Expected:** stable application errors; no raw stack/secret leakage.

## CONN-004 — tunnel failure does not kill control plane

**Action:** simulate/stop tunnel runtime while WorkspaceLens Control Runtime is healthy.

**Expected:** WebUI/Control API remain available; Connection state becomes actionable; workspace configuration remains intact.

## CONN-005 — adding workspace does not create another tunnel

**Action:** add second/third workspace.

**Expected:** connection/tunnel alias count remains one normal product connection.

# 10. L3 — Control Plane Security Contracts

These tests implement `v0.3-control-plane-security-contract.md` and are release-blocking.

## SEC-001 — loopback only

**Expected:** default server bind is loopback; attempting unsupported non-loopback exposure is rejected or requires an explicit future capability not present in v0.3.

## SEC-002 — invalid Host rejected

Send request with an unexpected Host header.

**Expected:** rejected before privileged mutation; state unchanged.

## SEC-003 — foreign Origin mutation rejected

**Action:** mutating request with `Origin: https://evil.example`.

**Expected:** rejected; target state/config unchanged.

## SEC-004 — missing/invalid CSRF rejected

For each privileged mutation family, representative requests without valid CSRF/session proof must fail without state change.

## SEC-005 — GET cannot mutate

Probe GET endpoints and malformed method usage.

**Expected:** no authorization/settings/connection mutation occurs from GET.

## SEC-006 — wildcard CORS absent

**Expected:** no `Access-Control-Allow-Origin: *` or equivalent broad browser access on privileged surfaces.

## SEC-007 — request body limits enforced

Oversized JSON/body is rejected before unbounded processing.

## SEC-008 — DTO validation rejects malformed input

Exercise wrong types, unknown/invalid workspace IDs, malformed settings/connection payloads.

**Expected:** stable 4xx-style error; no partial mutation.

## SEC-009 — session cookie attributes

Where browser session cookies are used, assert the required security attributes from the security contract (`HttpOnly`, `SameSite=Strict`, and other accepted local behavior).

## SEC-010 — CSP present and restrictive

WebUI response includes the accepted restrictive CSP; no requirement for unsafe remote script/CDN execution is introduced by v0.3.

## SEC-011 — secrets absent from API, logs, diagnostics, argv

Use a unique sentinel secret and exercise setup/connection/diagnostics/error paths.

**Expected:** sentinel does not appear in:

- JSON API responses;
- log capture;
- diagnostic report;
- child-process argv capture;
- persisted normal config/control-state.

## SEC-012 — sensitive workspace contents not included in diagnostics

Create sentinel content in a workspace file and run diagnostics.

**Expected:** diagnostic output contains status metadata only, not file bodies/diffs/search snippets.

## SEC-013 — MCP cannot escalate to Control API

Through MCP client/tool calls, prove there is no tool or protocol path to add/remove workspaces, read secrets, alter startup, or control tunnel lifecycle.

# 11. Secret, Startup, and Folder Picker Adapter Contracts

## SECRET-001 — secret persists outside ordinary config

After credential setup, inspect normal WorkspaceLens config/control state.

**Expected:** literal secret absent.

## SECRET-002 — unavailable secret store is actionable, not insecure

**Expected:** operation reports action required/failure; no plaintext fallback file is created.

## AUTO-001 — startup definition contains no secret

Generate/inspect the per-OS startup definition in a test location.

**Expected:** fixed WorkspaceLens startup command only; no runtime API key.

## AUTO-002 — enable/disable idempotence

Repeated enable/disable operations reach the intended state without duplicate startup entries.

## AUTO-003 — login startup failure leaves WebUI recoverable

Simulate missing secret/tunnel-client/provider config during startup reconciliation.

**Expected:** Control Runtime can still start; status becomes actionable rather than exiting the product completely.

## PICK-001 — picker result is server-validated

Any selected/manual path must pass the same canonicalization/authorization checks as CLI paths.

## PICK-002 — picker cancellation is no-op

Canceling native picker causes no configuration mutation.

## PICK-003 — manual path fallback works

A valid manually supplied path can be authorized when native picker is unavailable.

## PICK-004 — no general filesystem browser API introduced

Route/surface contract inspection must show no arbitrary directory-enumeration endpoint used merely to implement picking.

# 12. Diagnostics and Helper Contracts

## DIAG-001 — structured diagnostics reused by CLI and API

Given the same controlled environment, CLI `doctor` and Control API diagnostics derive from the same structured check results/application service rather than duplicate independent business rules.

## DIAG-002 — one workspace failure does not mark unrelated workspace invalid

A missing A and healthy B should produce separate statuses.

## HELP-001 — Project Instructions use stable workspace identity

Generated instructions explicitly target the selected `workspace_id` and instruct the reasoning client not to guess another workspace if target is unavailable/ambiguous.

## HELP-002 — Review/Plan helpers are stateless

Generating/copying helpers must not create review/plan/session/task records.

# 13. WebUI Test Boundary

The WebUI should be tested for behavior, not implementation trivia.

Required component/integration coverage should focus on:

- route/page availability;
- machine-verified vs user-confirmed status distinction;
- loading/error/empty states;
- disabled/loading behavior during mutations;
- destructive authorization confirmation;
- server-side error presentation;
- helper copy fallback;
- no hover-only essential operation;
- narrow-width navigation remains usable.

Do **not** require tests asserting arbitrary CSS class names, exact DOM nesting, pixel values, or internal React hook structure unless a specific accessibility/interaction requirement needs them.

### UI-001 — Workspaces empty/populated states

Verify primary add action, workspace identity display, enabled/disabled/error state, and navigation to detail.

### UI-002 — Connection state does not overclaim provider state

Given locally healthy but unverified provider state, UI must not display `ChatGPT connected` or equivalent unsupported claim.

### UI-003 — Verified vs User confirmed are distinguishable

Both text/semantic treatment must differ; color alone is insufficient.

### UI-004 — destructive remove language is precise

Confirmation states that WorkspaceLens authorization is removed and local files are untouched.

### UI-005 — setup is state-driven

Reloading setup reconstructs machine-observable progress from current state rather than blindly trusting a stored wizard page index.

# 14. L4 — Product Flow / End-to-End Acceptance

A unit/integration-green build is not enough. v0.3 is accepted only when product flows work through built/package-shaped artifacts.

## E2E-001 — package-shaped bootstrap

**Environment:** clean temporary user/config state; package/build artifact installed or exercised in package-shaped form, not repository-relative dev assumptions.

**Flow:**

```text
install WorkspaceLens
-> workspace-lens start
-> Control Runtime healthy
-> WebUI available
```

**Expected:** no repository checkout/root assumptions are required.

## E2E-002 — first workspace + HTTP MCP

**Flow:**

```text
start
-> authorize workspace A
-> MCP workspace_list sees A
-> representative read/Git call succeeds
```

## E2E-003 — add B without restart

**Flow:**

```text
runtime already healthy with A
-> add B through Control API/WebUI-equivalent product path
-> do NOT restart Control Runtime
-> do NOT restart tunnel adapter fixture/runtime
-> next MCP workspace_list sees A and B
```

This is a release-blocking v0.3 contract.

## E2E-004 — disable/remove without stale authorization

Disable/remove a workspace through product path; next MCP call must reflect the change immediately.

## E2E-005 — tunnel unavailable, WebUI recoverable

With tunnel runtime stopped/unhealthy, Control Runtime and WebUI stay available and show an actionable connection state.

## E2E-006 — zero daily CLI after bootstrap

Automated/local simulation must prove that ordinary workspace management, connection recovery, diagnostics, and settings do not require invoking additional WorkspaceLens CLI commands after bootstrap.

Provider-owned ChatGPT/OpenAI UI steps are exempt because WorkspaceLens cannot automate them without a supported provider interface.

## E2E-007 — startup reconciliation

Where supported by the test platform/adapter:

```text
autostart enabled
-> simulate/start user-session startup command
-> Control Runtime starts
-> desired tunnel connection is reconciled if prerequisites exist
```

No secret may be embedded in startup definition.

## E2E-008 — real ChatGPT verification (manual release gate)

This final gate is intentionally manual/external because CI cannot own the user's ChatGPT/OpenAI account.

Required release evidence:

1. install/start v0.3 product path;
2. configure one real tunnel/provider connection using WebUI guidance;
3. call `workspace_list` from ChatGPT;
4. add workspace B through WebUI;
5. without restarting WorkspaceLens or tunnel, call `workspace_list` again and observe B;
6. verify representative read/Git operation;
7. close browser and verify ChatGPT MCP access remains available;
8. record any provider-side steps that remain user-confirmed rather than machine-verified.

This gate must be executed before calling v0.3 product-complete.

# 17. Review / False-Green Checklist

Independent CR of the harness's test submission must verify:

- every release-blocking contract has a test or explicit BLOCKED evidence;
- tests exercise public/service/API boundaries rather than private implementation where possible;
- no required test is silently skipped;
- mocks are placed only at genuine external boundaries;
- test fixture behavior does not duplicate the production implementation and then test itself;
- security tests assert **state unchanged** after rejected requests;
- concurrency tests use real process-level concurrency where specified;
- live-config tests explicitly prove **no runtime restart**;
- isolation tests use distinct sentinel content/repos;
- secret tests search all relevant outputs for a unique sentinel;
- package tests run from outside repository root;
- E2E flow is not fragmented into module-local tests only;
- failures remain diagnosable and deterministic.

---

# 18. Explicit Test Non-goals

v0.3 does not require:

- load testing for large multi-user server traffic;
- distributed-system chaos testing;
- pixel-perfect visual regression for every screen;
- browser-matrix parity beyond supported product scope;
- fuzzing every MCP payload beyond existing schema/security boundaries;
- performance optimization benchmarks without observed performance risk;
- tests for CR/Plan workflow state, because WorkspaceLens does not own such state;
- tests for agent orchestration, because it is not a product capability;
- tests for native installer formats if v0.3 ships first as an npm distribution;
- automated ChatGPT browser control.

These may be added only if implementation evidence or later product scope justifies them.

---

# 19. v0.3 Test Completion Definition

The v0.3 test program is complete when all of the following are true:

1. existing v0.2 regression suite is green;
2. all required APP/CFG/LIVE/ISO/HTTP/CONN/SEC/SECRET/AUTO/PICK/DIAG/HELP/UI contracts applicable to shipped scope are green;
3. Gate A/B/C have explicit PASS results or an approved architecture change superseding them;
4. package-shaped E2E contracts are green on the supported release platform scope;
5. manual real-ChatGPT E2E-008 has been executed successfully;
6. no release-blocking test remains skipped, todo, unexplained red, or silently weakened;
7. diagnostics/logs/artifacts contain no test sentinel secret;
8. independent CR finds no material false-green gap.

The final product-level proof remains:

```text
clean install / package-shaped environment
        |
        v
workspace-lens start
        |
        v
WebUI manages A
        |
        v
MCP sees A
        |
        v
WebUI adds B without restart
        |
        v
MCP immediately sees B
        |
        v
normal daily use requires no Terminal
```

If this flow cannot be demonstrated, v0.3 is not complete even if all module-local tests are green.

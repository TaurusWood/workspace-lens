# WorkspaceLens v0.3 Control Plane Security Contract

Status: Required security contract for v0.3 implementation.

This contract governs the new local WebUI and Control API introduced in v0.3. It complements the existing read-only MCP security model. It does not replace `security-model.md` or the v0.2 MCP/security contracts.

The core distinction is:

> **MCP security protects local workspace data from remote/model access. Control-plane security protects WorkspaceLens administration from browser-origin and local integration abuse.**

The Control API is privileged because it can change WorkspaceLens authorization, connection state, settings, credentials, and startup behavior even though it still cannot modify authorized workspace contents.

---

## 1. Security Boundaries

v0.3 has three distinct trust surfaces:

```text
Remote reasoning client
        |
        | Secure MCP Tunnel
        v
/mcp  -------------------- read-only repository context

Local browser
        |
        | same-origin loopback HTTP
        v
/api/v1/* ---------------- privileged WorkspaceLens administration

Local OS/user session
        |
        +-- config files
        +-- credential store
        +-- startup manager
        `-- official tunnel-client runtime
```

These surfaces MUST NOT share capabilities merely because they are hosted by one Control Runtime.

---

## 2. Durable Capability Separation

### 2.1 MCP surface

`/mcp` may expose only the existing bounded read-only MCP tools.

It MUST NOT expose:

- workspace add/remove/enable/disable;
- settings mutation;
- secret access;
- tunnel lifecycle operations;
- autostart operations;
- arbitrary local command execution;
- Control API forwarding;
- browser session authority.

### 2.2 Control API surface

`/api/v1/*` may mutate WorkspaceLens-owned state only.

It may:

- authorize/de-authorize workspace roots;
- rename/enable/disable workspace registrations;
- manage WorkspaceLens settings;
- configure/reconcile the supported provider integration;
- store/delete supported runtime credentials through SecretStore;
- enable/disable WorkspaceLens login startup;
- request bounded diagnostics;
- invoke a fixed local folder picker adapter.

It MUST NOT:

- edit/write files inside authorized workspaces;
- execute arbitrary user-provided shell commands;
- run arbitrary Git commands;
- expose a general local filesystem browser;
- expose raw secret values after storage.

---

## 3. Network Binding Contract

The normal Control Runtime MUST bind only to loopback.

Accepted normal bindings:

```text
127.0.0.1
::1
```

It MUST NOT silently bind:

```text
0.0.0.0
::
LAN/private interfaces
public interfaces
```

Remote/LAN administration is not a v0.3 feature.

If a future development-only override exists, it must be explicit, off by default, clearly marked unsafe/unsupported for normal use, and excluded from release acceptance.

---

## 4. Host and DNS-Rebinding Protection

Loopback binding alone does not make a browser control surface safe.

The HTTP server MUST validate the effective Host/authority for WebUI and Control API requests.

Allowed values are limited to the active loopback host and configured local port, for example:

```text
127.0.0.1:43127
localhost:43127  # only if explicitly supported by the implementation
[::1]:43127
```

Unexpected Host values MUST be rejected before privileged routing.

The product must not trust a request merely because the TCP peer is local.

---

## 5. Browser Session Contract

The Control Runtime MUST establish a fresh ephemeral browser-control session for its lifetime.

Recommended properties:

- generated from cryptographically secure randomness;
- stored only in Control Runtime memory;
- delivered through a `HttpOnly` cookie;
- `SameSite=Strict`;
- `Secure` where the transport permits it; localhost HTTP exception must be documented if used;
- no long-lived reusable bearer token in LocalStorage;
- invalidated when the Control Runtime exits/restarts.

The browser session authorizes access to the local administration UI. It is not an MCP credential and MUST NOT be accepted on `/mcp` as administrative authority.

---

## 6. Same-Origin and CSRF Contract

All state-changing Control API methods MUST enforce same-origin browser intent.

For mutations:

- require a valid browser-control session;
- require exact expected `Origin` where browsers provide it;
- reject foreign origins;
- require a per-session CSRF token or equivalent non-simple custom header;
- never use GET for mutation;
- do not permit wildcard CORS;
- do not treat `Referer` alone as sufficient authorization.

Mutation examples include:

```text
POST
PUT
PATCH
DELETE
```

Read-only API routes may still require the browser session when their output contains local administrative information.

---

## 7. Content Security Policy

The WebUI MUST be served with a restrictive CSP suitable for a locally bundled SPA.

The intended shape is:

- `default-src 'self'`;
- scripts/styles/assets from packaged local origin only unless a concrete reviewed exception is required;
- no remote arbitrary script CDN dependency;
- no `unsafe-eval` in production;
- disallow framing by unrelated origins;
- restrict `connect-src` to the same local origin and explicitly required endpoints;
- block plugin/object content.

The production UI should be self-contained in the WorkspaceLens package.

---

## 8. Control API Input Validation

Every external Control API DTO MUST be validated at the boundary before entering application services.

Use Zod (or the accepted equivalent already present in the project) for:

- request bodies;
- path/route parameters;
- query parameters where behavior changes;
- normalized tunnel-client JSON output before use;
- persisted control-state documents.

Invalid DTOs MUST return a bounded product error without raw stack traces or internal object dumps.

---

## 9. Request Limits

The Control Runtime MUST impose bounded limits appropriate to a small local administration UI.

At minimum:

- maximum JSON request body size;
- maximum helper/prompt input size where any user-editable input exists;
- bounded diagnostic output;
- bounded subprocess output capture;
- bounded subprocess timeout;
- bounded folder-picker invocation lifetime;
- bounded lock wait timeout.

The Control API is not a general file-upload endpoint.

---

## 10. Secret Handling Contract

Runtime API keys and other provider secrets MUST NOT be stored in:

- workspace authorization config;
- ordinary control-state JSON;
- browser LocalStorage/sessionStorage;
- URL query strings;
- process argv;
- logs;
- diagnostics reports;
- MCP tool results;
- prompt helpers;
- Git-tracked files.

Secrets MUST be handled through a `SecretStore` abstraction backed by an OS credential store when available.

The Control API may accept a secret during setup, but after successful storage it MUST return only non-secret metadata such as:

```json
{
  "configured": true
}
```

It MUST NOT provide a `GET secret` endpoint that returns the original value.

### 10.1 tunnel-client secret references

When invoking the official tunnel client, WorkspaceLens MUST pass a reference such as:

```text
--runtime-api-key env:WORKSPACE_LENS_TUNNEL_API_KEY
```

or a reviewed file reference where appropriate.

The literal secret value may be injected into the child environment for the bounded invocation but must not appear in the command arguments.

### 10.2 No insecure automatic fallback

If an OS-backed credential store is unavailable, WorkspaceLens MUST NOT silently fall back to plaintext config storage.

Allowed behavior:

- show `Action required`;
- allow an advanced environment-variable workflow;
- keep local WebUI available;
- explain why automatic login reconnection cannot be enabled securely.

---

## 11. Subprocess Execution Contract

WorkspaceLens v0.3 may execute only explicitly supported binaries for product-owned integration tasks.

Examples:

- official `tunnel-client`;
- fixed OS startup utilities/APIs;
- fixed OS folder-picker adapters where required;
- bounded version/prerequisite probes.

Rules:

- use argument arrays (`execFile`/`spawn`) rather than shell command strings;
- `shell: true` is forbidden in normal product paths;
- do not interpolate user-controlled shell fragments;
- validate identifiers and paths before use;
- bound execution time;
- bound captured output;
- redact secrets before logging or returning failures;
- normalize subprocess errors into stable product errors.

There is no generic `run command` Control API.

---

## 12. Workspace Authorization Contract

The v0.3 WebUI must preserve all existing workspace authorization semantics:

- root must explicitly exist when initially authorized;
- root is canonicalized;
- duplicate roots are rejected;
- overlapping roots are rejected;
- `workspace_id` is stable after creation;
- missing roots never fall back to ancestors;
- disabled workspaces remain registered but unavailable to MCP;
- AccessPolicy still governs every content-bearing MCP operation.

Control-plane convenience MUST NOT weaken these rules.

### 12.1 Root reassignment

v0.3 MUST NOT silently change an existing `workspace_id` to point at another root.

If the root changes, the normal action is explicit de-authorization and new authorization unless a separately reviewed reauthorization contract is introduced later.

---

## 13. Safe Configuration Mutation

All product paths that mutate the workspace authorization config MUST use the accepted locked read-modify-write primitive.

Security properties:

- acquire inter-process lock before reading the mutation base state;
- load and validate latest config after locking;
- apply one bounded mutation;
- write with restrictive permissions;
- atomically replace;
- release lock;
- fail closed on lock/validation error.

A stale browser page MUST NOT overwrite unrelated newer CLI/WebUI changes using an old whole-config payload.

Control API mutations should express intent (`disable workspace X`) rather than submit the entire config document.

---

## 14. Live Authorization Semantics

MCP requests MUST resolve authorization from current validated config state rather than a stale startup-only registry.

If config becomes invalid/unreadable:

- do not silently continue serving a stale broader authorization set;
- fail the affected request closed;
- surface a configuration problem in Diagnostics.

One request may use one immutable validated config snapshot for internal consistency.

---

## 15. Folder Picker Security

The folder picker is a bounded UX adapter, not a filesystem API.

It may return only the user-selected directory path.

It MUST NOT expose:

- arbitrary directory enumeration endpoints;
- recursive filesystem browsing;
- file-content previews;
- shell command composition from user input.

Manual path entry remains a supported fallback and is validated server-side by the same workspace authorization rules.

---

## 16. Startup Security

OS startup definitions MUST contain only fixed WorkspaceLens executable/arguments and non-secret configuration references.

They MUST NOT contain:

- runtime API key literals;
- admin keys;
- browser session secrets;
- workspace file contents.

Enabling/disabling startup must be an explicit user action from Settings or an explicit CLI command.

If startup is enabled but provider credentials are unavailable, the Control Runtime still starts and surfaces the missing credential as `Action required`.

---

## 17. Diagnostics Redaction Contract

Diagnostics are factual operational data, not dumps of local state.

Default diagnostic output MUST exclude:

- provider secret values;
- environment dumps;
- credential-store contents;
- file contents/diffs/search snippets;
- cookies/session/CSRF values;
- full arbitrary subprocess environment;
- ChatGPT conversation identifiers;
- CR/plan/task semantics.

Workspace paths should be minimized/redacted by default where not required for diagnosis.

If the UI offers `Include local paths`, it must be explicit and still exclude secrets.

---

## 18. Logging Contract

The existing metadata-only logging principle remains.

Allowed examples:

```text
timestamp
tool name
workspace_id
duration
result count
error code
truncated flag
runtime lifecycle event
connection transition
```

Disallowed examples:

```text
file body
diff body
search snippet
API key
cookie
CSRF token
credential value
arbitrary request body
```

v0.3 current-state observability must not accidentally become persistent semantic workflow analytics.

---

## 19. Error Contract

User-facing/API errors should be stable and actionable without leaking internals.

Errors should distinguish categories such as:

- invalid request;
- authorization/configuration conflict;
- workspace unavailable;
- dependency missing;
- tunnel runtime unavailable;
- credential unavailable;
- startup integration failure;
- config lock conflict/timeout;
- internal failure.

Raw stack traces MUST NOT be returned through the production Control API or MCP surface.

Detailed local errors may be logged only under the metadata/redaction contract.

---

## 20. Explicit Threat Scope

WorkspaceLens v0.3 aims to protect against:

- remote/model attempts to exceed read-only MCP capabilities;
- path traversal and unauthorized workspace access;
- malicious websites attempting localhost state-changing requests;
- DNS-rebinding-style browser attacks;
- accidental cross-origin mutation;
- secret leakage through config/argv/logs/diagnostics;
- CLI/WebUI lost-update authorization bugs;
- accidental multi-workspace cross-contamination.

WorkspaceLens does **not** claim to protect user files from an arbitrary malicious native process already executing with the same OS user privileges. Such a process can generally access the user's filesystem outside WorkspaceLens entirely.

---

## 21. Required Security Tests

v0.3 cannot ship without automated coverage for at least:

1. Control Runtime rejects non-loopback normal bind configuration.
2. Unexpected Host is rejected.
3. Foreign Origin mutation is rejected.
4. Missing/invalid CSRF is rejected.
5. GET endpoints cannot perform state mutation.
6. Wildcard CORS is not enabled.
7. Oversized request bodies are rejected.
8. Invalid DTOs do not reach application mutations.
9. Secrets never appear in tunnel argv.
10. Secrets never appear in logs/diagnostics/API responses after storage.
11. Workspace add/remove/enable/disable preserves existing authorization rules.
12. CLI/WebUI concurrent mutations do not lose updates.
13. Malformed config fails MCP authorization closed rather than serving stale broader state.
14. Concurrent MCP requests for different workspaces do not cross roots/Git cwd/policy state.
15. Folder-picker endpoint cannot be used as a general filesystem enumeration API.
16. Startup definitions contain no secret material.
17. `/mcp` cannot invoke Control API capabilities.
18. Browser session/CSRF authority is not accepted as an MCP administration channel.

---

## 22. Release Gate

The v0.3 Control Plane security gate passes only when:

- all required controls above exist in production configuration;
- all required security tests pass;
- existing v0.2 security/tool-contract tests continue to pass;
- a package-shaped smoke test confirms the Control API is not externally bound;
- credential handling has no plaintext automatic fallback;
- security review confirms that WebUI convenience introduced no repository write/execute capability.

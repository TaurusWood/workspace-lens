# WorkspaceLens v0.3 Product Specification

Status: Product specification draft for v0.3. This document refines the v0.3 requirements in `version-requirements-v0.2-v0.5.md` into product behavior. It intentionally does not choose the WebUI framework, HTTP framework, daemon/process topology, credential store, startup mechanism, or visual design system. Those decisions belong to later interaction/UI and technical RFCs.

## 1. Product Goal

WorkspaceLens v0.3 turns the existing command-line integration into a local context control plane that a developer can configure once and keep available for daily reasoning work.

The product promise is:

> Set up WorkspaceLens once, authorize multiple local workspaces, and keep one read-only context connection available to reasoning clients without repeating terminal setup for every project or review.

The normal product model is:

```text
ChatGPT / reasoning client
          |
          | one WorkspaceLens app / MCP connection
          v
WorkspaceLens local product
          |
          +--> Workspace A
          +--> Workspace B
          +--> Workspace C
          `--> Workspace N
```

v0.3 does not make Web ChatGPT a coding harness. WorkspaceLens supports reasoning-dense inspection work such as review, planning, architecture discussion, requirement audit, and repository understanding. Write/execute/test/debug loops remain the responsibility of local coding harnesses or humans.

## 2. Target User and Primary Jobs

The primary user is a developer who:

- uses a web reasoning client such as ChatGPT for code review, planning, architecture, or requirement reasoning;
- uses Codex, Claude Code, Zcode, an IDE, or another local harness for implementation and execution;
- works across multiple local projects;
- wants the reasoning client to inspect current local and unpushed repository state without granting repository write or command-execution capability;
- does not want to repeat CLI/tunnel setup every time a new project is reviewed.

The primary jobs are:

1. **First-time setup** — get from installation to one verified reasoning-client tool call with clear guidance about which steps WorkspaceLens owns and which steps must be completed in the provider UI.
2. **Authorize projects** — add, inspect, enable/disable, and remove local workspaces from a visual control surface.
3. **Keep the connection available** — understand whether WorkspaceLens and its provider integration are healthy and recover them without memorizing CLI commands.
4. **Target the right workspace** — expose a stable workspace identity that can be referenced from ChatGPT Project Instructions or an ordinary chat.
5. **Diagnose failures** — identify whether a failure is caused by local prerequisites, workspace configuration, the tunnel/runtime, or an unfinished provider-owned setup step.

## 3. Product Boundaries

### 3.1 WorkspaceLens owns local context connectivity

The WebUI may manage:

- local WorkspaceLens configuration;
- workspace authorization;
- local runtime status;
- provider-integration profile/lifecycle operations that WorkspaceLens can perform locally;
- factual diagnostics;
- local startup/autostart configuration;
- optional helpers for referring to a workspace from a reasoning environment.

### 3.2 The provider owns provider-side account and conversation state

WorkspaceLens does not own and must not model:

- ChatGPT conversation IDs or chat lifecycle;
- ChatGPT Project IDs or Project lifecycle;
- which chat is currently open;
- which message is currently using WorkspaceLens;
- provider-side permissions that WorkspaceLens cannot verify;
- provider-side UI actions that do not have a supported automation interface.

Provider-owned setup steps should be guided, linked, and explained rather than simulated through browser automation.

### 3.3 WorkspaceLens does not own AI workflow semantics

WorkspaceLens does not know whether an MCP request belongs to:

- a code review;
- a plan;
- a requirement audit;
- an architecture discussion;
- another repository question.

It therefore does not track CR completion, plan completion, review outcome, task status, or reasoning-session state.

Optional `Copy Review Prompt` and `Copy Plan Prompt` actions are convenience helpers only. They do not establish workflow state and are not mandatory interaction steps.

## 4. Core Product Objects

v0.3 has four primary product objects and one supporting concept.

### 4.1 Local Runtime

Represents the local WorkspaceLens product required to provide the WebUI/control plane and context service.

User-relevant facts include:

- available / unavailable;
- starting / running / stopping where useful;
- healthy / unhealthy;
- autostart enabled / disabled;
- diagnostic reason when unhealthy.

The exact process topology is a technical decision and is deliberately not part of this product specification.

### 4.2 Provider Connection

Represents the configured route from the reasoning provider to WorkspaceLens.

For the initial ChatGPT integration, relevant product facts include:

- official tunnel client installed / missing;
- local tunnel profile configured / missing / invalid;
- tunnel runtime stopped / starting / healthy / unhealthy / recovering where observable;
- provider-owned setup action still required / locally ready;
- last detectable connection error.

The WebUI must distinguish **locally observable connection state** from **provider-side setup assumptions**.

It must not display `ChatGPT connected` merely because local configuration exists. A status label must state only what WorkspaceLens can verify.

### 4.3 Workspace

A Workspace is an explicitly authorized local context root.

Each workspace has:

- stable `workspace_id` used by MCP operations;
- human-readable name;
- canonical local root;
- enabled / disabled authorization state;
- validation state;
- optional repository metadata that can be obtained read-only.

Product-level workspace states should be understandable without exposing implementation internals. At minimum:

- **Enabled / Healthy** — root exists and is readable;
- **Enabled / Warning** — workspace is readable but an optional capability such as Git repository context is unavailable;
- **Enabled / Error** — configured root is missing or inaccessible;
- **Disabled** — remains configured but is unavailable to MCP clients.

A workspace is not a ChatGPT Project and is not a ChatGPT conversation.

### 4.4 Onboarding State

Onboarding is a guided set of observable checkpoints, not a hidden workflow engine.

The user should be able to understand the status of:

1. local prerequisites;
2. WorkspaceLens configuration;
3. at least one authorized workspace;
4. local provider/tunnel integration;
5. provider-owned account/app setup;
6. final real-world verification.

A checkpoint may be one of:

- Ready;
- Action required;
- Waiting for verification;
- Failed with a diagnostic reason.

WorkspaceLens should not persist fictitious completion state for provider actions that it cannot verify. Where necessary, the UI may present a user-confirmed checklist separately from machine-verified state.

### 4.5 Diagnostics

Diagnostics is supporting factual information about the four objects above.

v0.3 diagnostics may include:

- Node/runtime prerequisite status;
- Git availability;
- configuration validity;
- workspace validation failures;
- tunnel-client availability;
- tunnel profile validity;
- locally observable tunnel health;
- last runtime/connection error;
- a sanitized copyable diagnostic report.

Historical MCP Activity / Access Log is a v0.4 capability. v0.3 may expose only lightweight current/last-known runtime status needed for troubleshooting.

## 5. Multi-workspace Product Model

### 5.1 One normal installation, one normal connection, many workspaces

Adding a second or tenth local project should normally require only adding another authorized workspace.

It should not require:

- another WorkspaceLens installation;
- another MCP server by default;
- another tunnel by default;
- another ChatGPT app by default.

### 5.2 Enabled workspaces are available through the normal connection

For v0.3, the default product model is that all enabled workspaces registered in the local configuration are discoverable through the normal WorkspaceLens connection.

A disabled workspace behaves as unavailable.

Per-connection subsets or stronger connection-level isolation are not v0.3 requirements. They may be considered later if real security or multi-user use cases demonstrate a need.

### 5.3 No global active workspace

WorkspaceLens must not maintain a mutable global `current workspace`, `recent workspace`, or similar state that can silently redirect multiple chats.

Each content-bearing MCP request resolves against explicit workspace identity.

This allows different chats or reasoning clients to inspect different projects concurrently without cross-project state.

## 6. Primary User Journeys

### 6.1 Journey A — First-time Setup

Target outcome: the user completes one verified reasoning-client call without needing to understand transport internals.

Conceptual flow:

```text
Install / start WorkspaceLens
        |
        v
Open local WebUI
        |
        v
Check local prerequisites
        |
        v
Authorize first workspace
        |
        v
Configure local provider integration
        |
        v
Complete provider-owned steps with guidance
        |
        v
Verify with a real WorkspaceLens call
        |
        v
Ready for daily use
```

Product rules:

- WorkspaceLens-owned steps should be automated where safe.
- Provider-owned steps should be explicit and guided.
- The user should always know whether an incomplete step is local or provider-side.
- Failure should lead to an actionable next step rather than an opaque `Disconnected` state.

### 6.2 Journey B — Add Another Project

Target outcome: adding another project does not repeat provider setup.

Conceptual flow:

```text
Open Workspaces
      |
      v
Add workspace
      |
      v
Choose/provide local root
      |
      v
Set/confirm logical identity
      |
      v
Validate
      |
      v
Enable
      |
      +--> optional: Copy Project Instructions
      +--> optional: Copy Review Prompt
      `--> optional: Copy Plan Prompt
```

No tunnel/App recreation should normally appear in this journey.

### 6.3 Journey C — Normal Daily Use

Target outcome: WorkspaceLens requires no routine interaction when healthy.

Conceptual flow:

```text
Machine/login start
      |
      v
WorkspaceLens becomes locally available
      |
      v
Provider integration becomes available
      |
      v
User opens ChatGPT Project / chat
      |
      v
Reasoning client accesses the intended workspace
```

The best normal daily experience is that the user does not need to open the WebUI.

The WebUI is primarily a setup, management, and recovery surface rather than a daily development dashboard.

### 6.4 Journey D — Failure Recovery

Target outcome: a user who notices that ChatGPT cannot access local context can identify the failing layer and recover it without reconstructing CLI knowledge.

Conceptual flow:

```text
Reasoning client cannot access context
        |
        v
Open WorkspaceLens WebUI
        |
        v
See failing layer and reason
        |
        +--> workspace invalid -> repair/disable/remove
        +--> tunnel stopped -> restart
        +--> prerequisite missing -> install/fix
        +--> provider action required -> open guidance
        `--> unknown -> copy sanitized diagnostics
        |
        v
Healthy / next explicit action
```

## 7. Workspace Identity Helpers

WorkspaceLens should make each workspace easy to reference from an external reasoning environment without establishing a technical conversation binding.

A selected workspace may offer:

- **Copy Project Instructions** — recommended default-workspace instruction for a ChatGPT Project;
- **Copy Review Prompt** — optional generic starting prompt for a read-only code review;
- **Copy Plan Prompt** — optional generic starting prompt for implementation planning.

These helpers must remain small and replaceable.

They must not grow into:

- prompt-library management;
- prompt versioning;
- workflow state;
- automatic review invocation;
- automatic plan invocation;
- mandatory project conventions.

A repository-provided skill, `AGENTS.md`, Project Instructions, or another process may supersede them entirely.

## 8. Product-Level Status Principles

### 8.1 Prefer actionable state over technical state

The UI should answer:

- Is WorkspaceLens usable?
- Is this workspace available?
- Is the provider integration locally ready?
- What do I need to do next?

It should not force the user to understand child processes, profile file formats, ports, or protocol internals.

### 8.2 Do not merge distinct failure causes into `Disconnected`

Where detectable, distinguish at least:

- not configured;
- local dependency missing;
- workspace invalid;
- tunnel/runtime stopped;
- tunnel/runtime unhealthy;
- provider-owned action required;
- locally healthy but provider-side state unverified.

### 8.3 Do not overclaim provider state

Machine-verifiable and user-confirmed states should be visually/semantically distinct.

WorkspaceLens must not claim that a ChatGPT Project, chat, or message is connected unless a supported provider signal proves it.

## 9. Explicit v0.3 Non-goals

v0.3 does not add:

- ChatGPT chat/session management;
- ChatGPT Project synchronization;
- source-code browser/editor;
- diff viewer as a product surface;
- terminal or arbitrary command execution;
- build/test/debug execution;
- coding-harness control;
- task manager;
- `.agent/tasks` workflow UI;
- CR/Plan semantic history or completion analytics;
- review outcome analytics;
- historical MCP Activity / Access Log beyond lightweight troubleshooting state;
- prompt library/version-management features;
- cloud-hosted WorkspaceLens control plane;
- remote/LAN administration by default;
- agent orchestration;
- a separate provider connection per workspace by default.

Feature count is not a v0.3 success criterion. A small control plane that reliably removes setup and connection friction is preferable to a larger dashboard with weak ownership boundaries.

## 10. Product Acceptance Criteria

v0.3 product behavior is complete when:

1. A new user can move from local installation to a verified WorkspaceLens call through a guided experience that clearly separates local and provider-owned steps.
2. A user can manage multiple authorized workspaces without editing the config file or repeating provider setup for each workspace.
3. Each workspace has a stable, visible identity and clear enabled/validation state.
4. The product exposes enough connection state to distinguish local readiness, local failure, and provider-owned actions that WorkspaceLens cannot verify.
5. Normal healthy daily use does not require repeated CLI commands or routine WebUI interaction.
6. A user can recover common local connection failures from the WebUI or receive a specific next action.
7. Optional Project Instructions / Review / Plan helpers are available without introducing workflow ownership.
8. Different workspaces can be targeted concurrently without any global active-workspace state or cross-project contamination.
9. WorkspaceLens continues to expose repository context read-only and does not acquire execution/coding-harness responsibilities.
10. The product does not claim knowledge of ChatGPT conversation, Project, CR, plan, or task state that it cannot actually observe.

## 11. Inputs to the Next Specifications

This Product Spec intentionally leaves the following work for later layers.

### 11.1 Interaction / Information Architecture Spec

Must define:

- navigation and page hierarchy;
- first-run onboarding interactions;
- workspace add/edit/remove/disable interactions;
- connection status interactions;
- error/recovery interactions;
- confirmation behavior for destructive control-plane actions;
- empty/loading/error states;
- Project Instructions / Review / Plan helper interactions.

### 11.2 UI Spec

Must define:

- screen layouts;
- visual hierarchy;
- components;
- responsive behavior;
- status visual language;
- interaction feedback;
- accessibility behavior.

### 11.3 Technical Architecture RFC

Must decide, based on the existing v0.2 implementation:

- long-lived process ownership and supervision topology;
- how the local WebUI/control API is hosted;
- WebUI/frontend framework choice;
- local HTTP framework choice, if any;
- how workspace folder selection/path acquisition works safely from a browser-based UI;
- how tunnel-client lifecycle is supervised;
- how autostart is implemented per supported OS;
- how the tunnel runtime obtains credentials during autostart without storing secrets in ordinary config/plain text;
- whether and how lightweight runtime status is persisted;
- browser control-surface security (loopback, origin, anti-CSRF/session strategy);
- packaging/install/update behavior;
- concurrency/isolation tests.

The technical RFC must preserve the existing Core/config/access-policy contracts rather than rebuilding them for the WebUI.

# WorkspaceLens v0.3 Technical Architecture RFC

Status: Accepted architecture for v0.3.

This RFC turns the accepted v0.3 product, interaction, UI, readiness, bootstrap, and security contracts into implementation architecture.

Related contracts:

- `v0.3-product-spec.md`
- `v0.3-interaction-spec.md`
- `v0.3-ui-spec.md`
- `v0.3-technical-readiness-audit.md`
- `v0.3-bootstrap-distribution-contract.md`
- `v0.3-control-plane-security-contract.md`
- `v0.3-implementation-plan.md`

Guiding rule:

> Add a local control plane around the existing read-only Core. Do not turn Core into an agent runtime, and do not reimplement capabilities already owned by the official tunnel client.

User-facing delivery rule:

> **One install, one bootstrap, zero daily CLI.**

---

## 1. Decision Summary

v0.3 uses the following architecture:

```text
OS user session / login
        |
        v
+--------------------------------------------------------------+
| WorkspaceLens Control Runtime                                |
|                                                              |
| Hono local HTTP server bound to loopback only                |
|                                                              |
| /              -> built React/Vite WebUI                     |
| /api/v1/*      -> privileged local Control API               |
| /mcp           -> read-only Streamable HTTP MCP endpoint     |
|                                                              |
| Application Services                                         |
| - WorkspaceAdminService                                      |
| - ConnectionService                                          |
| - DiagnosticsService                                         |
| - SettingsService                                            |
| - PromptHelperService                                        |
|                                                              |
| Existing Core / AccessPolicy / adapters                      |
+------------------------------+-------------------------------+
                               ^
                               |
                         loopback HTTP
                               |
+------------------------------+-------------------------------+
| official OpenAI tunnel-client managed runtime                |
| native runtimes connect/status/stop surface                  |
+------------------------------+-------------------------------+
                               ^
                               |
                     Secure MCP Tunnel
                               |
                     ChatGPT / reasoning client
```

The existing `workspace-lens serve` stdio adapter remains supported for direct local MCP clients.

The normal ChatGPT v0.3 path uses the Control Runtime's local Streamable HTTP MCP endpoint.

Key decisions:

1. One long-lived WorkspaceLens Control Runtime owns WebUI, Control API, current application state, and local MCP HTTP.
2. Official `tunnel-client` owns tunnel runtime supervision; WorkspaceLens does not own raw tunnel PIDs.
3. The tunnel targets the local `/mcp` URL rather than launching a second WorkspaceLens child for the normal v0.3 path.
4. Core remains provider-agnostic, harness-agnostic, and read-only.
5. Filesystem workspace authorization config remains source of truth.
6. Config mutations are locked read-modify-write operations.
7. MCP authorization observes current config without WorkspaceLens/tunnel restart.
8. Browser Control API has a separate privileged security boundary.
9. Runtime provider secrets are stored outside ordinary config in an OS-backed secret store.
10. WebUI is a small React + Vite SPA; no Next.js/SSR/Electron/Tauri.
11. Local HTTP/control adapter uses Hono on Node 24.
12. MCP SDK major migration is not coupled to v0.3 unless a separate parity gate proves it trivial.
13. Canonical user-facing launcher is `workspace-lens start`; `workspace-lens control` is an advanced/foreground runtime command.

## 2. Process Ownership

### 2.1 WorkspaceLens Control Runtime

Advanced/foreground command:

```text
workspace-lens control
```

Responsibilities:

- serve WebUI static assets;
- expose Control API;
- expose read-only MCP Streamable HTTP endpoint;
- run application services;
- expose local health/readiness;
- reconcile desired provider connection state on startup;
- keep only bounded current operational state in memory.

It must not:

- execute arbitrary shell commands;
- become an agent runtime;
- own ChatGPT sessions;
- own review/plan/task semantics;
- reimplement Secure MCP Tunnel;
- manually supervise raw tunnel-client PIDs when the supported managed-runtime surface exists.

### 2.2 tunnel-client managed runtime

Official `tunnel-client` owns:

- tunnel process launch/supervision;
- local runtime state;
- health/readiness;
- control-plane polling;
- runtime alias state;
- native runtime diagnostics/repair metadata;
- runtime stop/remove lifecycle.

WorkspaceLens interacts only through bounded executable calls and structured output.

Normal operations use the supported `runtimes` command family, including connect/status/stop/list where required.

No `shell: true` path is permitted.

### 2.3 Stable runtime alias

One product-owned normal alias:

```text
workspace-lens
```

The alias represents the one normal provider connection, not a project.

Adding another local workspace does not create another tunnel/runtime alias.

### 2.4 Browser lifecycle

The browser is only a UI/control surface.

Closing the browser:

- does not stop Control Runtime;
- does not stop tunnel runtime;
- does not invalidate workspace authorization.

## 3. Canonical User Launcher

Normal user command:

```text
workspace-lens start
```

Behavior:

1. probe the current user's Control Runtime;
2. if healthy, reuse it;
3. if absent, start it through the supported local launch path;
4. wait for bounded readiness;
5. open the WebUI in the default browser;
6. print local URL fallback;
7. never start a duplicate healthy runtime.

The user should not need to know the local port or tunnel process model.

After successful setup and `Start at login`, ordinary daily use should require no Terminal interaction.

`workspace-lens control` remains useful for development, tests, service definitions, and advanced recovery; it is not the primary onboarding command.

See `v0.3-bootstrap-distribution-contract.md`.

---

## 4. Runtime Singleton and Local Listener

Only one normal Control Runtime should manage one WorkspaceLens config/state root for a user.

Use a dedicated local runtime lock.

A second runtime attempt must:

- detect the healthy existing runtime;
- avoid duplicate startup;
- return/report the existing URL/status.

Stale ownership recovery must be bounded and tested.

Runtime-singleton locking and config-write locking are separate concerns.

The Control Runtime binds loopback only:

```text
127.0.0.1
::1
```

Never silently bind `0.0.0.0`, `::`, LAN, or public interfaces.

---

## 5. Local HTTP Surfaces

One Node listener hosts three logically separate surfaces.

### 5.1 WebUI

```text
GET /
GET /assets/*
```

Serves only package-owned build assets.

### 5.2 Control API

```text
/api/v1/*
```

Privileged local administration surface.

Representative resources:

```text
GET    /api/v1/status
GET    /api/v1/workspaces
POST   /api/v1/workspaces
PATCH  /api/v1/workspaces/:id
DELETE /api/v1/workspaces/:id

GET    /api/v1/connection
POST   /api/v1/connection/connect
POST   /api/v1/connection/start
POST   /api/v1/connection/stop
POST   /api/v1/connection/restart

GET    /api/v1/diagnostics
POST   /api/v1/diagnostics/run

GET    /api/v1/settings
PATCH  /api/v1/settings

POST   /api/v1/folder-picker
POST   /api/v1/helpers/project-instructions
POST   /api/v1/helpers/review-prompt
POST   /api/v1/helpers/plan-prompt
```

Exact DTOs belong to the implementation/API contract modules.

The Control API may mutate WorkspaceLens-owned configuration/integration state but not authorized workspace contents.

### 5.3 MCP endpoint

```text
POST /mcp
```

Read-only Streamable HTTP adapter over the same existing tool definitions.

Rules:

- public tool semantics unchanged;
- no Control API operation through MCP;
- no workspace administration MCP tools;
- no tunnel/startup/secret MCP tools;
- same explicit workspace identity contract;
- no arbitrary browser CORS.

The normal tunnel configuration points to the local MCP URL and uses a secret reference (`env:`/reviewed `file:` reference), never literal API key argv.

## 6. Application Service Layer

v0.3 introduces shared application services:

```text
src/application/
  workspace-admin-service.ts
  connection-service.ts
  diagnostics-service.ts
  settings-service.ts
  prompt-helper-service.ts
```

### WorkspaceAdminService

Owns:

- list + validation state;
- add;
- rename display name;
- enable/disable;
- remove authorization;
- identity suggestion/validation;
- safe UI metadata.

`workspace_id` and root are immutable after creation in v0.3.

### ConnectionService

Owns:

- tunnel-client detection;
- current configured provider/tunnel state;
- connect/start/stop/restart;
- managed-runtime status normalization;
- safe repair-action presentation.

It does not execute arbitrary provider-supplied commands.

### DiagnosticsService

Returns structured factual checks.

CLI `doctor` becomes a formatter over this service.

### SettingsService

Owns non-secret product preferences such as:

- autostart desired state;
- provider setup user confirmations;
- auto-connect preference;
- non-secret local settings.

### PromptHelperService

Generates optional Project Instructions / Review Prompt / Plan Prompt from stable workspace identity.

No workflow state.

## 7. Configuration Model

### 7.1 Workspace authorization config

Keep security-relevant workspace config focused on:

- config version;
- expose-absolute-paths setting;
- workspace identity;
- canonical root;
- enabled state.

Do not mix transient UI/runtime state into it.

### 7.2 Separate control state

v0.3 may add:

```text
~/.config/workspace-lens/control-state.json
```

Allowed examples:

- tunnel alias/id metadata;
- auto-connect preference;
- provider user confirmations;
- non-secret UI/product settings.

Forbidden:

- API keys/tokens;
- ChatGPT chat/Project IDs;
- CR/Plan/task state;
- persisted health as authoritative truth.

### 7.3 Browser-only preferences

Pure UI preferences (for example theme) may live in browser local storage if no backend ownership is needed.

---

## 8. Safe Concurrent Config Mutation

Current atomic temp-write/rename protects file integrity but not lost updates across CLI/WebUI processes.

v0.3 adds:

```text
ConfigStore.mutate(fn)
```

Semantics:

1. acquire inter-process config lock;
2. load latest config after lock acquisition;
3. validate;
4. apply one intent-level mutation;
5. validate result;
6. write restrictive temp file;
7. atomic rename;
8. release lock;
9. fail closed on error.

CLI and WebUI use the same service/mutation layer.

Do not expose whole-config replacement from browser UI.

A reviewed lockfile implementation such as an atomic directory/lock dependency may be used rather than inventing an unsafe ad-hoc scheme.

---

## 9. Live Authorization

v0.3 must not require MCP restart after workspace administration.

Preferred implementation:

```text
MCP request
-> load/fetch current validated config snapshot
-> resolve explicit workspace_id
-> execute the whole request against that immutable snapshot
```

Why request-scoped fresh config is preferred initially:

- config is tiny;
- correctness is simple;
- CLI changes become visible immediately;
- no watcher/cache invalidation complexity;
- reasoning workloads are low/moderate request density compared with coding loops.

If config is malformed/unreadable:

- do not silently use a stale broader authorization snapshot;
- fail the request closed;
- surface Diagnostics problem.

---

## 10. Tunnel Integration

The v0.2 prototype's `pgrep` discovery is not the v0.3 normal contract.

v0.3 uses the official tunnel-client managed-runtime surface and structured output.

WorkspaceLens should consume factual runtime state such as:

- process running;
- healthy;
- ready;
- control-plane poll health;
- repair metadata;
- selected/live binary details when relevant.

Do not infer runtime truth by grepping arbitrary command lines or scraping human logs when supported JSON exists.

WorkspaceLens must not duplicate provider runtime state/history as its own source of truth.

---

## 11. Runtime Credential Strategy

Provider runtime secret values must not be stored in:

- workspace config;
- `control-state.json`;
- browser local storage;
- URLs;
- logs;
- diagnostics;
- argv;
- prompt helpers.

Use a narrow `SecretStore` interface:

```text
available()
get(name)
set(name, secret)
delete(name)
```

Preferred production implementation is OS-backed credential storage.

Node 24/platform viability is an implementation gate.

No automatic plaintext fallback.

If credential storage is unavailable:

- WebUI still starts;
- show `Action required`;
- advanced environment-variable configuration may remain possible;
- automatic secure reconnect/autostart must not pretend to be configured.

WorkspaceLens does not need to store provider admin keys for normal v0.3 operation.

---

## 12. Login Autostart

Autostart launches the WorkspaceLens Control Runtime.

After startup:

```text
Control Runtime healthy
-> load desired local state
-> inspect tunnel managed runtime
-> if auto-connect required and not healthy
   -> retrieve secret
   -> connect/reconcile via official tunnel-client
```

This makes WorkspaceLens the product-level reconciler, not the tunnel process supervisor.

Adapters:

- macOS LaunchAgent;
- Windows per-user Task Scheduler;
- Linux `systemd --user` where supported.

Startup definitions contain no API key values.

If provider integration fails, Control Runtime/WebUI remain available for recovery.

---

## 13. Browser Control-Surface Security

The Control API is more privileged than the reasoning MCP surface.

Required controls include:

- loopback-only bind;
- Host validation / DNS-rebinding protection;
- no wildcard CORS;
- restrictive CSP;
- ephemeral browser control session;
- `HttpOnly` + `SameSite=Strict` cookie;
- exact same-origin validation for mutation;
- CSRF token/custom-header requirement;
- no mutation through GET;
- request body limits;
- Zod DTO validation;
- diagnostics/secret redaction;
- no LAN exposure by default.

See `v0.3-control-plane-security-contract.md` for the normative contract and tests.

---

## 14. Folder Selection

Browser directory APIs are not the authorization identity source for v0.3.

Define a bounded local adapter:

```text
FolderPicker.pickDirectory()
```

It may use a fixed OS-native dialog implementation.

Always retain manual path input/paste fallback with server-side validation and `~` expansion.

Do not add a general filesystem browser/enumeration endpoint.

---

## 15. Backend Technology

Keep:

- Node.js 24;
- TypeScript;
- Zod.

Use Hono + Node adapter for the small localhost server/control surface.

Hono is only an HTTP adapter. Application services remain framework-independent and directly testable.

---

## 16. MCP HTTP and SDK Version

Mount a stateless/request-scoped Streamable HTTP adapter using the existing MCP tool definitions.

The architecture does not require an MCP SDK major migration.

Decision:

> Do not make MCP SDK major-version migration a prerequisite for v0.3.

First prove HTTP parity with the existing supported SDK/tool/security tests.

A later isolated migration gate may be attempted only if it remains small and contract-equivalent.

---

## 17. Frontend Technology

Use:

- React stable line;
- Vite stable line;
- TypeScript;
- ordinary SPA routing/state;
- project-owned CSS variables/components with CSS Modules/plain CSS.

Do not require:

- Next.js;
- SSR;
- React Server Components;
- Electron;
- Tauri;
- custom browser shell;
- large enterprise design-system dependency.

Do not add a global state framework initially.

SPA routes:

```text
/setup
/workspaces
/workspaces/:id
/connection
/diagnostics
/settings
```

## 18. Build and Distribution

Recommended layout:

```text
src/       Node/Core/control/application
ui/        React/Vite source

dist/     compiled Node runtime
dist-ui/  built WebUI assets
```

Build pipeline:

```text
npm run typecheck
npm run build:runtime
npm run build:ui
npm run build
```

The npm package includes required built UI assets.

Runtime resolves assets relative to installed module location, not `process.cwd()`.

No separate web deployment exists.

Required first product distribution may be:

```text
npm install -g workspace-lens
workspace-lens start
```

Native installers are optional follow-up unless adoption evidence promotes them to a release requirement.

---

## 19. Diagnostics and Lightweight Observability

`DiagnosticsService.run()` returns structured factual checks consumed by:

```text
CLI doctor -> text
Control API -> JSON
WebUI -> UI
```

v0.3 may keep bounded in-memory operational state:

- active MCP request count;
- last MCP request timestamp;
- last local MCP error;
- last lifecycle error;
- current connection transition.

Do not persist this as CR/Plan/task history.

v0.4 may add bounded factual Activity/Access Log behind the same seams.

---

## 20. Verification Semantics

The Control Runtime can observe inbound MCP HTTP traffic but must not overclaim provider conversation state.

Allowed:

- local MCP request observed;
- tunnel runtime healthy;
- provider integration locally ready;
- tunnel/MCP path exercised where evidence supports it.

Not allowed without provider proof:

- this ChatGPT chat is connected;
- this ChatGPT Project is connected;
- CR complete;
- Plan complete.

Provider-side setup may remain `User confirmed` even when local/tunnel evidence is healthy.

---

## 21. Test Contract

v0.3 implementation must preserve all existing Core/AccessPolicy/adapter/MCP/CLI compatibility tests except intentionally updated product wording/flow.

New required coverage:

### Live config

- add workspace without restart -> next MCP request sees it;
- disable -> next request rejects it;
- malformed config fails closed.

### Concurrent workspace isolation

Parallel A/B requests cannot cross:

- filesystem roots;
- Git cwd;
- AccessPolicy state;
- output/error redirection.

### Config concurrency

Separate processes prove:

- no lost update;
- no partial JSON;
- explicit lock timeout/failure;
- bounded stale lock recovery.

### Tunnel adapter

Stub supported executable contract and verify:

- connect/status/stop/restart;
- JSON parsing;
- missing binary;
- failure normalization;
- no literal secret in argv/log/output.

### Browser security

Prove normative Control Plane security contract.

### Startup

Test generated startup definitions/adapters without modifying the real user's startup state.

### Package smoke

Installed/package-shaped test proves:

- `workspace-lens start`/Control Runtime startup;
- WebUI asset resolution;
- Control API status;
- `/mcp` representative request;
- stdio `serve` remains available;
- unrelated cwd works.

## 22. Migration from v0.2

Existing workspace authorization config remains readable.

v0.3 may create additional non-secret control state/secret-store entries but must not require users to re-authorize existing roots.

Existing `connect chatgpt` may become a compatibility wrapper over shared ConnectionService.

`pgrep`-based tunnel runtime discovery is retired from the normal v0.3 path.

`getting-started.md` remains the verified v0.2 guide until v0.3 code/package behavior is real; a v0.3 guide is written after acceptance, not before.

---

## 23. Implementation Order

The authoritative executable breakdown is `v0.3-implementation-plan.md`.

Dependency shape:

```text
technical gates
-> application/service boundaries
-> safe config mutation
-> live authorization
-> Control Runtime
-> MCP HTTP
-> diagnostics
-> tunnel managed-runtime integration
-> Control API security
-> administrative APIs/settings/secrets
-> canonical start launcher
-> WebUI
-> folder picker
-> autostart
-> packaging
-> end-to-end acceptance
```

Do not begin by building UI around invented backend state.

---

## 24. Architecture Acceptance

v0.3 architecture is successfully implemented when:

1. one WorkspaceLens Control Runtime remains available independently of browser/tunnel failure;
2. official tunnel-client owns tunnel runtime supervision;
3. normal ChatGPT path targets local MCP HTTP;
4. stdio `serve` remains supported;
5. WebUI/CLI share application services;
6. workspace authorization changes affect next MCP request without restart;
7. multi-workspace concurrent isolation is proven;
8. Control API satisfies its separate security contract;
9. secrets are absent from ordinary config/argv/logs/diagnostics;
10. `workspace-lens start` is the one normal bootstrap command;
11. login autostart enables zero-daily-CLI operation;
12. existing v0.2 read-only tool/security contracts remain intact.

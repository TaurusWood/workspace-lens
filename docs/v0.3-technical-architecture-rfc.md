# WorkspaceLens v0.3 Technical Architecture RFC

Status: Proposed architecture for v0.3.

This RFC turns the accepted v0.3 product, interaction, UI, and readiness documents into an implementation architecture. It makes concrete decisions about process ownership, local control hosting, configuration consistency, tunnel lifecycle, credentials, browser security, folder selection, frontend/backend stack, startup, packaging, and test boundaries.

The guiding rule is:

> Add a local control plane around the existing read-only Core. Do not turn the Core into an agent runtime, and do not reimplement capabilities already owned by the official tunnel client.

---

## 1. Decision Summary

v0.3 adopts the following architecture:

```text
OS user session / login
        |
        v
+--------------------------------------------------------------+
| WorkspaceLens Control Runtime                                |
|                                                              |
|  Hono local HTTP server bound to loopback only               |
|                                                              |
|  /              -> built React/Vite WebUI                    |
|  /api/v1/*      -> privileged local Control API              |
|  /mcp           -> read-only Streamable HTTP MCP endpoint    |
|                                                              |
|  Application Services                                        |
|  - WorkspaceAdminService                                     |
|  - ConnectionService                                         |
|  - DiagnosticsService                                        |
|  - SettingsService                                           |
|  - PromptHelperService                                       |
|                                                              |
|  Existing Core / AccessPolicy / adapters                     |
+------------------------------+-------------------------------+
                               ^
                               |
                         loopback HTTP
                               |
+------------------------------+-------------------------------+
| official OpenAI tunnel-client managed runtime                |
| tunnel-client runtimes connect/status/stop --json            |
+------------------------------+-------------------------------+
                               ^
                               |
                     Secure MCP Tunnel
                               |
                     ChatGPT / OpenAI client
```

The existing `workspace-lens serve` stdio entry remains supported for direct local MCP clients and backward compatibility. The normal ChatGPT v0.3 path, however, uses the long-lived Control Runtime's local Streamable HTTP MCP endpoint.

Key decisions:

1. **One long-lived WorkspaceLens process** owns WebUI, Control API, current product state, and the local read-only MCP endpoint.
2. **The official `tunnel-client` owns tunnel process supervision.** WorkspaceLens invokes its native `runtimes ... --json` command surface instead of inventing daemon management.
3. **The tunnel targets the local MCP HTTP URL**, not a second `workspace-lens serve` child, for the normal v0.3 ChatGPT path.
4. **Core remains provider-agnostic and read-only.** HTTP, WebUI, tunnel lifecycle, startup, and credentials stay outside Core.
5. **The filesystem config remains the source of truth for workspace authorization.** Mutations become locked read-modify-write operations; MCP reads observe current config without a restart.
6. **Control-plane browser security is separate from MCP read-only security.** The local API is privileged and must be protected against browser-origin attacks.
7. **The runtime API key is stored outside ordinary config in an OS-backed secret store.** Only a secret reference/environment injection is passed to `tunnel-client`.
8. **The WebUI is a small React + Vite SPA.** No Next.js, SSR, Electron, Tauri, or desktop shell is required for v0.3.
9. **The local HTTP layer uses Hono on Node 24.** It is an adapter/control surface, not a new business-logic layer.
10. **The current MCP SDK v1 contract is preserved for the first v0.3 implementation unless an isolated migration gate proves v2 migration is trivial and contract-equivalent.** Protocol migration must not be entangled with control-plane implementation.

## 2. Why the Control Runtime Also Hosts MCP HTTP

Two viable process models were considered.

### Option A — control service + tunnel-managed stdio child

```text
WorkspaceLens Control Runtime
        |
        +--> WebUI / Control API
        |
        `--> tunnel-client runtimes ...
                  |
                  `--> workspace-lens serve (stdio child)
```

Advantages:

- maximally preserves the current ChatGPT stdio path;
- tunnel-client owns the MCP child lifecycle.

Costs:

- two WorkspaceLens processes hold product state;
- workspace config changes must propagate across process boundaries;
- request/activity observability is split between the control process and MCP child;
- v0.4 Activity Log becomes harder to implement cleanly;
- verification of inbound MCP activity requires another shared logging/state mechanism;
- installation paths containing spaces require robust cross-platform `mcp-command` quoting;
- tunnel restart also restarts the MCP child unnecessarily.

### Option B — control service owns local MCP HTTP endpoint — ACCEPTED

```text
WorkspaceLens Control Runtime
        |
        +--> WebUI / Control API
        `--> /mcp
               ^
               |
        tunnel-client managed runtime
```

Advantages:

- only one long-lived WorkspaceLens process;
- WebUI and MCP always observe the same current configuration and services;
- tunnel restart does not restart WorkspaceLens;
- no `mcp-command` quoting/path problem for the normal ChatGPT path;
- lightweight active-request and last-request status is locally observable;
- v0.4 Activity / Access Log has a natural interception point;
- future local providers may connect to the same standard HTTP MCP endpoint;
- official `tunnel-client runtimes connect` already supports `--mcp-server-url`.

Cost:

- v0.3 must add a loopback Streamable HTTP MCP adapter.

That cost is bounded and does not alter Core semantics, so Option B is preferred.

### Rejected option — tunnel owns WorkspaceLens Control Runtime

The WebUI/control service must not be a child of the tunnel process. If the tunnel is stopped or broken, the user still needs the WebUI to diagnose and recover it.

Therefore:

> Control Runtime lifecycle and tunnel lifecycle are related but independent.

## 3. Process Ownership

### 3.1 WorkspaceLens Control Runtime

A new command starts the local control process:

```text
workspace-lens control
```

Responsibilities:

- serve WebUI static assets;
- expose the local Control API;
- expose the read-only MCP Streamable HTTP endpoint;
- run application services;
- expose local health/readiness;
- reconcile desired tunnel availability on startup when configured;
- keep only lightweight bounded operational state in memory.

It must not:

- execute arbitrary shell commands;
- become an agent runtime;
- own ChatGPT sessions;
- own review/plan/task semantics;
- reimplement Secure MCP Tunnel protocol;
- directly supervise raw tunnel-client child processes when the native `runtimes` surface is available.

### 3.2 tunnel-client managed runtime

The official tunnel client owns:

- tunnel process launch;
- tunnel process state;
- tunnel health/readiness;
- control-plane polling;
- runtime alias state;
- native repair diagnostics;
- stopping/removing the local tunnel runtime.

WorkspaceLens interacts through exact executable calls such as:

```text
tunnel-client runtimes connect ... --json
tunnel-client runtimes status workspace-lens --json
tunnel-client runtimes stop workspace-lens --json
```

No `shell: true` path is allowed.

### 3.3 Stable runtime alias

v0.3 uses one product-owned tunnel runtime alias:

```text
workspace-lens
```

The alias represents the one normal WorkspaceLens provider connection, not an individual local project.

Adding a workspace must not create another tunnel alias.

### 3.4 Existing stdio server

`workspace-lens serve` remains a supported adapter:

```text
local MCP client -> stdio -> workspace-lens serve
```

It continues to exercise the same MCP tool definitions and Core services.

The HTTP and stdio surfaces must share tool contracts rather than fork implementations.

## 4. Local Runtime Startup and Singleton Behavior

### 4.1 Singleton

Only one normal Control Runtime should manage a given WorkspaceLens state/config root.

The process acquires a local runtime lock under the WorkspaceLens state directory.

A second `workspace-lens control` invocation should:

- detect the healthy existing runtime;
- report the current local URL;
- exit without starting a duplicate process.

A stale lock may be recovered only after health/PID checks prove no valid runtime owns it.

### 4.2 User-facing launcher

A convenience command may be added:

```text
workspace-lens ui
```

Behavior:

1. probe the local Control Runtime;
2. if absent, launch/reuse it for the current user session;
3. wait for local health;
4. open the local WebUI in the default browser;
5. never start a duplicate runtime.

This is a WorkspaceLens-owned process and may use a bounded detached launch path. This does **not** apply to `tunnel-client`, whose own runtime manager remains authoritative.

### 4.3 Local listen address

The Control Runtime binds loopback only.

Default shape:

```text
http://127.0.0.1:<workspace-lens-port>
```

It must never silently bind `0.0.0.0` or a LAN interface.

The port is a local product setting/state detail. A stable default is preferable for usability, but a configurable override is allowed for conflicts and development.

## 5. Local HTTP Surfaces

One Node HTTP listener hosts three logically distinct surfaces.

### 5.1 WebUI

```text
GET /
GET /assets/*
```

Serves only build-time WorkspaceLens assets.

### 5.2 Control API

```text
/api/v1/*
```

This is a privileged local administrative surface. It can mutate WorkspaceLens's own configuration and control the provider integration, but it cannot modify authorized workspace contents.

Representative resources:

```text
GET    /api/v1/status
GET    /api/v1/workspaces
POST   /api/v1/workspaces
PATCH  /api/v1/workspaces/:id
DELETE /api/v1/workspaces/:id

GET    /api/v1/connection
POST   /api/v1/connection/connect
POST   /api/v1/connection/start
POST   /api/v1/connection/stop
POST   /api/v1/connection/restart

GET    /api/v1/diagnostics
POST   /api/v1/diagnostics/run

GET    /api/v1/settings
PATCH  /api/v1/settings

POST   /api/v1/folder-picker
POST   /api/v1/helpers/project-instructions
POST   /api/v1/helpers/review-prompt
POST   /api/v1/helpers/plan-prompt
```

Exact DTOs belong to an API contract module and implementation plan.

### 5.3 MCP endpoint

```text
POST /mcp
```

v0.3 exposes a stateless Streamable HTTP MCP adapter over the same existing tool definitions.

Rules:

- read-only tool contract remains unchanged;
- no Control API operation is exposed through MCP;
- no workspace administration tool is added to MCP;
- no tunnel/startup/secret operation is exposed to MCP;
- the endpoint is loopback-only;
- CORS is not opened to arbitrary browser origins.

The normal tunnel binding is:

```text
tunnel-client runtimes connect \
  --alias workspace-lens \
  --tunnel-id <id> \
  --runtime-api-key env:WORKSPACE_LENS_TUNNEL_API_KEY \
  --mcp-server-url http://127.0.0.1:<port>/mcp \
  --json
```

The literal key is never placed in argv.

## 6. Application Service Layer

v0.3 introduces an application layer so CLI and WebUI do not duplicate product rules.

Recommended structure:

```text
src/
  application/
    workspace-admin-service.ts
    connection-service.ts
    diagnostics-service.ts
    settings-service.ts
    prompt-helper-service.ts

  control/
    server.ts
    api/
    security/

  integrations/
    openai/
      tunnel-runtime-adapter.ts
    startup/
    secrets/
    folder-picker/

  core/
  adapters/
  mcp/
  config/
  cli/
```

### 6.1 WorkspaceAdminService

Owns product-level workspace administration:

- list with validation state;
- add;
- rename display name;
- enable;
- disable;
- remove authorization;
- derive/suggest workspace identity;
- validate current root;
- expose safe metadata for UI.

The service reuses ConfigStore/Core validation rules. It does not bypass them.

### 6.2 ConnectionService

Owns product-level provider integration behavior:

- detect tunnel-client;
- read tunnel configuration state;
- configure/connect the stable runtime alias;
- start/reconnect;
- stop;
- restart;
- normalize `runtimes status --json` into WorkspaceLens product status;
- surface `repair_actions` without blindly executing arbitrary instructions.

### 6.3 DiagnosticsService

Extracts the current CLI `doctor` checks into structured data.

CLI `doctor` becomes a formatter over this service rather than a separate implementation.

### 6.4 SettingsService

Owns:

- autostart desired state;
- provider integration metadata that belongs to WorkspaceLens;
- setup user-confirmations;
- non-secret local product settings.

### 6.5 PromptHelperService

Generates the optional Project Instructions / Review Prompt / Plan Prompt helpers from stable workspace identity.

It owns no workflow state.

## 7. Configuration Model

### 7.1 Keep authorization config small

The existing workspace authorization file remains security-relevant and should stay focused on:

- config version;
- `expose_absolute_paths`;
- workspace identity;
- canonical root;
- enabled state.

Do not mix transient UI/runtime state into this file.

### 7.2 Add separate control state

v0.3 may add a second local state document for non-secret control-plane preferences, for example:

```text
~/.config/workspace-lens/control-state.json
```

Possible contents:

```json
{
  "version": 1,
  "tunnel_alias": "workspace-lens",
  "tunnel_id": "tunnel_...",
  "auto_connect": true,
  "provider_confirmations": {
    "chatgpt_app_configured": true
  }
}
```

Rules:

- no API key values;
- no bearer tokens;
- no chat IDs;
- no ChatGPT Project IDs;
- no CR/plan/task state.

Machine-observable runtime status must be re-derived instead of persisted as truth.

### 7.3 Browser-only preferences

Pure UI preferences such as theme may remain in browser local storage and do not need backend config unless later requirements justify it.

## 8. Safe Concurrent Configuration Mutation

Current atomic temp-file + rename prevents partial files but not lost updates between separate processes.

v0.3 therefore adds one mutation primitive:

```text
ConfigStore.mutate(fn)
```

Semantics:

1. acquire an inter-process lock for the config path;
2. load the latest config **after** lock acquisition;
3. apply one validated mutation;
4. write temp file with restrictive permissions;
5. atomically rename;
6. release lock;
7. fail closed on lock/config errors.

CLI and WebUI must both use this primitive through shared application services.

Direct read-modify-`save()` sequences outside the config layer should be removed from product paths.

### 8.1 Lock implementation

Use a proven cross-process lockfile implementation based on atomic directory creation rather than inventing an ad-hoc PID lock protocol for configuration writes.

`proper-lockfile` is an acceptable v0.3 dependency for this narrow role, subject to dependency/security review.

Runtime-singleton locking and config-write locking are separate concerns even if they share a low-level primitive.

---

## 9. Live Configuration Semantics

v0.3 must not require MCP restart after workspace administration.

The source of truth remains the config file, so MCP workspace resolution must observe current config.

Preferred simple implementation:

- introduce a live registry/provider backed by `ConfigStore`;
- obtain a fresh validated config snapshot at the beginning of each relevant MCP operation (or equivalent request-scoped snapshot);
- perform the rest of that operation against the immutable snapshot/workspace resolved from it.

Why this is preferred over file watching in v0.3:

- config is tiny;
- reasoning workloads have low-to-moderate MCP request frequency;
- synchronous local JSON reads are cheap relative to Git/search operations and network latency;
- correctness is easier to prove;
- CLI changes are immediately visible;
- no watcher invalidation/stale-cache edge cases are introduced.

If performance evidence later proves this material, an mtime/hash cache may be introduced without changing service contracts.

### 9.1 Fail closed

If the config becomes malformed or unreadable during a request:

- do not use a stale broader authorization snapshot silently;
- return a stable configuration error;
- surface the problem in Diagnostics.

## 10. Tunnel Integration

### 10.1 Replace process discovery heuristics

The current prototype uses `pgrep` to discover a running `tunnel-client` process. That is not the v0.3 control contract.

v0.3 uses the official native runtime surface:

```text
tunnel-client runtimes list --json
tunnel-client runtimes status workspace-lens --json
tunnel-client runtimes connect ... --json
tunnel-client runtimes stop workspace-lens --json
```

This removes platform-specific `pgrep` dependence and consumes structured health state.

### 10.2 WorkspaceLens does not parse tunnel internals when JSON exists

Prefer structured fields exposed by `tunnel-client`, such as:

- process running;
- healthy;
- ready;
- control-plane poll health;
- live admin URL;
- repair actions;
- selected/live binary information.

Do not derive runtime truth by grepping arbitrary process command lines or scraping human-readable logs.

### 10.3 Runtime state belongs to tunnel-client

WorkspaceLens must not copy or fork:

- alias state;
- process history;
- health URL files;
- tunnel logs;
- generated tunnel profile contents.

It may read status through the supported CLI and retain only normalized transient product state.

## 11. Runtime Credential Strategy

### 11.1 Principle

The runtime API key must not be stored in:

- workspace authorization config;
- `control-state.json`;
- tunnel ID fields;
- logs;
- diagnostics bundles;
- argv;
- generated prompt helpers.

### 11.2 OS-backed secret store

The preferred v0.3 model is:

```text
WebUI setup
   -> SecretStore.set(runtime-key)
   -> OS credential store

Control Runtime start/reconnect
   -> SecretStore.get(runtime-key)
   -> inject into child environment only
   -> tunnel-client runtimes connect
      --runtime-api-key env:WORKSPACE_LENS_TUNNEL_API_KEY
```

The generated tunnel profile stores only the environment-variable reference, which matches the official tunnel-client secret-reference model.

### 11.3 SecretStore adapter

Define a narrow interface:

```text
get(name)
set(name, secret)
delete(name)
available()
```

Preferred implementation candidate: `@github/keytar`, because it targets macOS Keychain, Windows Credential Vault, and Linux Secret Service.

**Implementation Gate:** verify Node 24 install/prebuild behavior on supported platforms before adopting it. No automatic plaintext-file fallback is allowed merely to make the test pass.

If an OS credential store is unavailable:

- manual environment-variable configuration may remain supported as an advanced fallback;
- autostart requiring an unavailable secret must show `Action required` rather than persist the literal key insecurely.

### 11.4 Admin keys are out of scope

WorkspaceLens v0.3 does not need to store `OPENAI_ADMIN_KEY` for normal operation.

Remote tunnel creation remains provider-owned/manual unless a later requirement explicitly introduces admin CRUD.

The long-lived runtime uses only the least-privilege runtime key with Tunnel Read + Use.

## 12. Login Autostart

### 12.1 What autostarts

The autostart toggle installs/removes startup for **WorkspaceLens Control Runtime**.

After Control Runtime starts, it may reconcile the tunnel runtime:

```text
control start
  -> load desired local state
  -> tunnel-client runtimes status workspace-lens --json
  -> if auto_connect && not running
       retrieve runtime secret
       runtimes connect ... --json
```

This makes WorkspaceLens the product-level reconciler without making it the tunnel process supervisor.

### 12.2 Platform adapters

Use explicit fixed-command adapters, not arbitrary shell execution:

- macOS: user LaunchAgent (`launchd`);
- Linux: `systemd --user` service where available;
- Windows: per-user Task Scheduler entry.

The adapter contract should support:

```text
status()
enable(command, args)
disable()
```

Startup definitions must contain no runtime API key.

### 12.3 Failure behavior

If startup is enabled but:

- the secret is missing;
- tunnel-client is missing;
- provider configuration is invalid;

then Control Runtime still starts and WebUI remains available. The connection becomes `Action required` or `Problem` with the specific cause.

## 13. Browser Control-Surface Security

The Control API is more privileged than the MCP API because it can change WorkspaceLens authorization and process state.

Binding to localhost alone is not sufficient against browser-origin attacks.

### 13.1 Required controls

The v0.3 local server must implement all of the following:

1. bind loopback only;
2. reject unexpected `Host` values to reduce DNS-rebinding risk;
3. do not enable wildcard CORS;
4. serve a restrictive Content Security Policy;
5. issue an ephemeral per-Control-Runtime browser session cookie (`HttpOnly`, `SameSite=Strict`);
6. require exact same-origin `Origin` for mutating API calls;
7. require a per-session CSRF token/custom header for mutations;
8. never mutate state from GET requests;
9. cap request body sizes;
10. use JSON DTO validation before application-service calls;
11. redact secrets and sensitive diagnostics;
12. do not expose the control listener to LAN by default.

### 13.2 Threat boundary

The browser controls protect against malicious websites and accidental cross-origin requests.

WorkspaceLens does not claim to defend local workspace data from arbitrary malicious native processes already executing as the same OS user; such a process can generally read the user's files directly.

### 13.3 MCP endpoint separation

`/mcp` does not accept the browser Control API session as authority for administration.

It exposes only the existing read-only MCP tool contract.

## 14. Folder Selection

A normal browser directory picker does not provide a trustworthy absolute local path to a localhost backend across browsers/platforms.

v0.3 therefore does not depend on browser File System Access APIs for authorization identity.

### Accepted model

Define a `FolderPickerAdapter` in the local Control Runtime.

`Choose folder` may invoke an OS-native dialog using only fixed executable/argument patterns, with no user-controlled command interpolation.

Examples of implementation families:

- macOS native dialog through a fixed system utility;
- Windows native folder dialog through a fixed system API/PowerShell script owned by WorkspaceLens;
- Linux desktop dialog when a supported utility is present.

The API returns only the chosen directory path.

### Fallback

Always provide a text/path entry fallback with server-side validation and `~` expansion.

Do not add a general arbitrary-filesystem browser endpoint merely to implement folder selection.

## 15. Backend Technology

### 15.1 Runtime

Keep:

- Node.js 24 LTS line;
- TypeScript;
- Zod for DTO/input validation.

### 15.2 Local HTTP framework — Hono

Use Hono with its Node adapter for:

- route organization;
- JSON request/response plumbing;
- static UI serving integration;
- small middleware surface;
- graceful shutdown integration.

Reasons:

- the application is a small localhost control API, not a large server framework;
- Hono runs cleanly on Node 24;
- it keeps the adapter layer thin;
- business logic remains in application services.

Hono must not become the domain/application architecture. Services should remain callable from CLI/tests without HTTP context.

### 15.3 MCP HTTP routing

The MCP endpoint may be mounted at the Node listener boundary rather than forcing MCP transport semantics through ordinary Control API middleware.

For the initial v0.3 implementation, use the existing MCP SDK v1.30 Streamable HTTP transport in stateless/request-scoped form while preserving all tool contracts.

This minimizes simultaneous protocol + product changes.

## 16. MCP SDK Version Decision

As of v0.3 planning, MCP TypeScript SDK v2 is stable and implements the 2026-07-28 protocol. The current WorkspaceLens code is on the maintained v1.30 line.

The architecture does not require a v2 migration.

Decision:

> Do not make MCP SDK v2 migration a prerequisite for the Control Plane.

Reasons:

- v0.3 already changes lifecycle, HTTP hosting, configuration, UI, and startup;
- v1.30 already supports Streamable HTTP;
- current v0.2 tool-contract tests provide strong regression protection;
- the accepted v0.3 workload needs no new v2 protocol feature.

A separate bounded migration gate may be attempted after the local HTTP adapter is proven:

```text
Migrate to @modelcontextprotocol/server v2
-> run full existing tool/security/contract suite
-> require zero public tool semantic changes
-> keep only if the migration remains small
```

If the migration creates unrelated complexity, defer it to a later maintenance version.

## 17. Frontend Technology

### 17.1 React + Vite SPA

Use:

- React stable line;
- Vite stable line;
- TypeScript;
- ordinary client-side SPA routing/state;
- CSS variables + CSS Modules/plain CSS.

Do not use:

- Next.js;
- SSR;
- React Server Components;
- Electron;
- Tauri;
- a custom browser shell;
- a large design-system dependency merely for a four-section utility.

### 17.2 State management

Do not add a global state-management framework initially.

Use:

- server state fetched from the Control API;
- page/local component state;
- a small API client abstraction;
- explicit refresh/polling only where connection state requires it.

If implementation evidence shows repeated cache/mutation complexity, a server-state library may be introduced later, but it is not an architectural prerequisite.

### 17.3 Routing

The SPA needs routes for:

```text
/workspaces
/workspaces/:id
/connection
/diagnostics
/settings
/setup
```

History routing or hash routing is an implementation detail as long as deep-link behavior is deterministic when served by the local runtime.

### 17.4 Styling

Prefer project-owned tokens/components sufficient for the UI Spec.

Do not make Tailwind, a full enterprise component suite, or an icon library a prerequisite unless implementation evidence shows it materially reduces work without distorting the UI contract.

## 18. UI Build and Packaging

Recommended source layout:

```text
src/               # Node/Core/control/application code
ui/                # React/Vite source

dist/              # compiled Node runtime
dist-ui/           # built static UI assets
```

Build pipeline:

```text
npm run typecheck
npm run build:runtime
npm run build:ui
npm run build
```

The npm package/release must include the built UI assets required by `workspace-lens control`.

The runtime resolves asset paths relative to its installed module location, not `process.cwd()`.

No separate web deployment exists in v0.3.

## 19. Diagnostics Architecture

The existing `doctor` command already contains useful checks but returns formatted CLI text.

Refactor into:

```text
DiagnosticsService.run()
  -> structured CheckResult[]
```

Then:

```text
CLI doctor       -> text formatter
Control API      -> JSON DTO
WebUI Diagnostics-> UI components
```

Checks should remain factual and bounded.

Tunnel status should use native `runtimes ... --json` output rather than process grepping.

---

## 20. Lightweight Runtime Observability

v0.3 needs only enough live state for status/recovery.

The Control Runtime may track in memory:

- active MCP request count;
- last MCP request timestamp;
- last local MCP error;
- last Control API lifecycle error;
- current connection transition (`starting`, `stopping`, etc.).

This state is not persisted as workflow history.

The existing metadata-only `Logger` remains the safety baseline.

v0.4 Activity / Access Log may later add a bounded persistent sink behind the same logging/observation seams without changing tool behavior.

---

## 21. Verification Semantics

The Control Runtime can observe inbound MCP HTTP calls, which is useful evidence, but it still must not overclaim ChatGPT conversation state.

Allowed statements include:

- `Local MCP request observed`;
- `Tunnel runtime healthy`;
- `Provider connection locally ready`.

Do not claim:

- `ChatGPT Project connected`;
- `this ChatGPT chat is connected`;
- `CR completed`;
- `plan completed`.

If Setup Verify observes an MCP request while the configured tunnel runtime is healthy, the UI may report that the tunnel/MCP path was exercised. ChatGPT-side app configuration may still remain `User confirmed` unless a provider-supported signal proves it.

## 22. Test Contract for v0.3 Architecture

Implementation is not complete without tests for the new boundaries.

### 22.1 Preserve v0.2

All existing:

- Core tests;
- AccessPolicy/security tests;
- adapter tests;
- MCP contract tests;
- CLI compatibility tests

must continue to pass except for intentionally updated CLI wording/flow.

### 22.2 Live config tests

Prove:

- add workspace through application service;
- without restarting Control Runtime;
- next MCP request sees it;
- disable workspace;
- next MCP request rejects it;
- no stale broader authorization snapshot is used after malformed config.

### 22.3 Concurrent workspace tests

Run concurrent MCP requests against different workspace IDs and prove:

- filesystem roots do not cross;
- Git cwd does not cross;
- AccessPolicy state does not cross;
- one workspace failure does not redirect another request.

### 22.4 Config concurrency tests

Use separate processes to mutate the same config and prove:

- no lost update;
- no partial JSON;
- lock timeout/failure is explicit;
- stale lock recovery is bounded and tested.

### 22.5 Tunnel adapter tests

Stub only the `tunnel-client` executable contract and verify exact argument arrays for:

- connect;
- status;
- stop;
- restart/reconnect;
- JSON parse failure;
- nonzero exit;
- missing binary;
- secret never appearing in argv/output/logs.

### 22.6 Browser security tests

Prove:

- non-loopback bind is rejected by default;
- invalid Host rejected;
- foreign Origin mutation rejected;
- missing/invalid CSRF rejected;
- GET cannot mutate;
- oversized body rejected;
- CORS is not wildcard/open;
- secrets absent from diagnostics.

### 22.7 Startup tests

Per supported OS adapter, test generated startup definition/commands without modifying the real user's startup state.

### 22.8 Packaging smoke

Install/package-shaped smoke must prove:

- `workspace-lens control` starts;
- WebUI assets resolve from installed location;
- `/api/v1/status` works;
- `/mcp` accepts an MCP client request;
- `workspace-lens serve` stdio remains available.

## 23. Migration from Current v0.2

v0.3 should preserve existing user state.

Existing:

```text
~/.config/workspace-lens/config.json
```

must remain readable.

The first v0.3 start may create additional control state and secret-store entries but must not require users to re-authorize existing workspaces.

Current `workspace-lens connect chatgpt` behavior may be adapted to call the shared ConnectionService or retained temporarily as a compatibility path, but CLI and WebUI must converge on the same application logic before v0.3 is considered complete.

The current `pgrep`-based running-daemon detection should be retired from the v0.3 normal path in favor of native tunnel-client runtime status.

## 25. Explicit Rejections

v0.3 does **not** adopt:

- one MCP/tunnel per workspace;
- global active/recent workspace state;
- direct ChatGPT conversation management;
- WorkspaceLens-owned tunnel wire protocol;
- WorkspaceLens-owned raw tunnel daemon supervisor when `tunnel-client runtimes` exists;
- arbitrary shell execution;
- Next.js/SSR;
- Electron/Tauri merely to obtain a settings UI;
- a database for workspace config;
- SQLite/activity analytics for v0.3;
- filesystem indexing/vector DB;
- prompt library/workflow engine;
- CR/Plan state inference;
- provider admin-key storage for normal operation;
- plaintext runtime key in WorkspaceLens JSON config.

## 26. Remaining Implementation Gates

These are bounded verification gates, not unresolved product decisions.

### Gate A — tunnel-client runtime JSON contract

Before coding ConnectionService, record fixtures from the supported `tunnel-client` version for:

- `runtimes connect --json`;
- `runtimes status --json`;
- `runtimes stop --json`;
- common failure/repair states.

The adapter should parse a narrow normalized subset and fail safely on incompatible output.

### Gate B — OS secret-store dependency

Verify the selected OS-backed Node credential library on the supported Node 24/platform matrix.

If it fails on a platform, do not silently downgrade to plaintext storage. Mark secure credential persistence/autostart unavailable there until a safe adapter exists.

### Gate C — folder picker platform behavior

Prototype the fixed-command/native folder dialog on each supported desktop OS and preserve manual path entry as the universal fallback.

### Gate D — MCP HTTP compatibility

Run the current tool contract over the new local Streamable HTTP endpoint through the official tunnel-client before removing the existing stdio ChatGPT setup path from documentation.

### Gate E — optional MCP SDK v2 migration

Attempt only as an isolated parity change. It is not allowed to delay the v0.3 Control Plane if the migration stops being small.

## 27. Acceptance Criteria

The technical architecture is realized when:

1. one WorkspaceLens Control Runtime can stay available after login and serve the WebUI, Control API, and read-only local MCP endpoint;
2. the official tunnel-client runtime can connect to that endpoint and is controlled through its native runtime commands;
3. adding/disabling/removing a workspace becomes visible to subsequent MCP requests without restarting WorkspaceLens;
4. CLI and WebUI share the same application services and mutation rules;
5. concurrent CLI/WebUI mutations cannot silently lose updates;
6. concurrent MCP requests for different workspaces remain isolated;
7. tunnel runtime credentials are not stored in ordinary WorkspaceLens config or exposed in argv/logs/diagnostics;
8. autostart can restore the Control Runtime and, when configured, reconcile the tunnel connection without terminal interaction;
9. a malicious unrelated website cannot use the browser to mutate the local Control API through ordinary cross-origin requests;
10. existing read-only MCP security and tool contracts remain intact;
11. WebUI assets ship with the local package and require no cloud hosting;
12. stopping/breaking the tunnel does not make the WorkspaceLens WebUI unavailable;
13. no new coding, execution, task-orchestration, or ChatGPT-session capability is introduced.

---

## 28. External Technical Assumptions

This RFC relies on current supported external surfaces rather than private protocol behavior:

- OpenAI Secure MCP Tunnel remains the supported route from ChatGPT to a developer-machine/private MCP server.
- `tunnel-client` provides native `runtimes connect`, `runtimes status`, and `runtimes stop` lifecycle commands with JSON output and supports both local stdio MCP commands and MCP server URLs.
- runtime keys may be supplied by secret reference such as `env:NAME` or `file:/path`; literal secrets should not be persisted in generated tunnel state.
- MCP Streamable HTTP is a standard supported server transport.

If these provider surfaces change, only the provider/control adapters should need to change. Core tool and workspace semantics must remain stable.

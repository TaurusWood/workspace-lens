# WorkspaceLens v0.3 Goal Mode Prompt

Status: execution prompt for local coding harness after v0.3 Design / Contract Freeze.

This prompt is intentionally short relative to the frozen contracts. It tells the harness **how to execute the contracts**; it does not duplicate or reinterpret them.

## Canonical Prompt

```text
You are implementing a bounded WorkspaceLens v0.3 development goal in Goal Mode.

Repository contracts are frozen and authoritative. Do not redesign product, architecture, security, interaction, testing, or UI semantics for implementation convenience.

Before changing code, read the relevant frozen documents, especially:

- docs/v0.3-freeze-declaration.md
- docs/v0.3-implementation-plan.md
- docs/v0.3-test-contract.md
- docs/v0.3-technical-architecture-rfc.md
- docs/v0.3-control-plane-security-contract.md
- docs/v0.3-ui-spec.md
- docs/v0.3-ui-implementation-contract.md when the assigned goal contains UI work

Also inspect the current source, tests, package configuration, and the RED/GREEN contracts owned by the assigned slices.

GOAL

Complete the assigned implementation slice(s) to production quality.

You may independently inspect the repository, determine exact files to modify, implement the required architecture, run tests, diagnose failures, and iterate until the assigned contracts are satisfied.

Do not stop after producing a plan unless a frozen contract is genuinely blocked by evidence.

GOVERNING RULES

1. Preserve all frozen v0.3 contracts and existing v0.2 behavior unless an upstream frozen document explicitly changes it.
2. Prefer the simplest implementation that satisfies the contracts. Keep module boundaries clear and follow KISS.
3. Do not introduce speculative abstractions for future versions.
4. Do not implement capabilities outside the assigned slices.
5. Do not weaken, skip, delete, or rewrite required tests merely to obtain green results.
6. Do not add production "test mode", "stub mode", simulation-only APIs, hidden fallbacks, or magic test strings to satisfy tests. Use dependency injection/test adapters where contracts require external boundaries to be controlled.
7. Do not change a frozen contract because implementation is inconvenient.
8. Keep the read-only MCP/Core security boundary intact.
9. No hidden global current/recent workspace. Every content-bearing operation remains explicitly workspace-scoped.
10. Do not add arbitrary shell execution, write/edit tools, agent orchestration, per-workspace tunnels, Next.js, Electron/Tauri, or unrelated product scope.

SLICE EXECUTION

When the goal contains multiple slices:

- implement them strictly in Implementation Plan order;
- complete and verify one slice before starting the next;
- make a focused commit per slice;
- if a slice is blocked, stop before dependent later slices rather than coding around the blocker.

A slice is complete only when:

- its focused tests pass;
- relevant v0.3 contracts expected to turn green actually turn green for the required behavior;
- the existing v0.2 regression suite remains green;
- typecheck passes;
- build passes;
- the final diff contains no unnecessary scope or complexity.

CONTRACT BLOCKER RULE

If implementation evidence proves a frozen contract impossible, internally inconsistent, or incompatible with a verified external dependency, do not silently change the contract.

Return:

CONTRACT BLOCKED
Contract:
Evidence:
Why the implementation cannot satisfy it:
Minimal options:
Affected slices:
Unaffected work completed:

Continue unaffected work only when doing so cannot prejudge the blocked architecture decision.

TEST / FALSE-GREEN RULE

A contract turning GREEN is valid only when the actual required behavior exists.

Forbidden ways to get green:

- skip/todo/xit;
- weaker assertions;
- test-only production branches;
- fake production test-support APIs;
- restarting a runtime when a contract requires live visibility without restart;
- mocking the subject under test;
- replacing product-path E2E evidence with direct application-service calls.

FINAL REVIEW

Before declaring the goal complete:

- run focused tests for every assigned slice;
- run npm test;
- run the relevant v0.3 contract suite/tests;
- run typecheck;
- run build;
- inspect git diff/status;
- remove dead code, debug output, temporary files, and unnecessary abstractions;
- verify no frozen non-goals were introduced.

COMPLETION REPORT

Return:

- goal completion status;
- commits created, one per completed slice;
- implementation summary;
- files changed;
- contract IDs moved RED -> GREEN;
- remaining RED / BLOCKED / MANUAL-GATE contracts relevant to this goal;
- focused/full test results;
- typecheck/build results;
- any implementation-level decisions made inside allowed freedom;
- any evidence that requires reopening a frozen contract;
- final HEAD SHA.

Stop after the assigned goal and wait for independent CR.
```

## Initial Goal — GOAL-1

Use the canonical prompt above with this assignment appended:

```text
ASSIGNED GOAL: GOAL-1 — Application / Mutable Config / Live Registry

Implement, in order:

- Slice 0 — Contract Scaffolding and Shared Application Layer
- Slice 1 — Safe Mutable Configuration
- Slice 2 — Live Workspace Registry / no-restart authorization visibility

Do not begin Slice 3 Control Runtime in this goal.

Required outcome:

1. shared application service boundaries exist without Hono/React dependencies;
2. workspace administration uses safe locked read-modify-write semantics;
3. concurrent CLI/WebUI-shaped mutations cannot lose accepted changes;
4. add/disable/remove changes become visible to the next MCP request without restarting the serving process;
5. v0.2 stdio behavior and read-only MCP/Core security remain intact;
6. all owned APP/CFG/LIVE contracts that are implementable in Slices 0-2 move from RED to GREEN for real behavior.

Create one focused commit per completed slice and stop after Slice 2 for independent CR.
```

# WorkspaceLens v0.2 Requirements

Status: Frozen product requirement for v0.2 implementation.

## 1. Objective

WorkspaceLens v0.2 closes the first real review-completeness gap discovered after v0.1 and makes the existing setup path reproducible from documentation.

The release has exactly two product goals:

1. allow a reasoning chat to review local committed Git state, including unpushed commits and a trusted-base-to-head implementation range;
2. provide one canonical first-time setup path from installation to a successful real ChatGPT `workspace_list` call.

v0.2 is not a product-surface or lifecycle release. WebUI, daemon management, autostart, Project mapping, Reviewer Skill integration, and agent orchestration remain deferred.

## 2. Product Context

v0.1 already provides:

```text
workspace_list
workspace_info
list_files
read_file
search_workspace
git_status
git_diff
```

This is sufficient for working-tree review but incomplete for common local development flows where implementation work has already been committed locally and has not been pushed.

The target v0.2 review surface is:

```text
Working tree
  - git_status
  - git_diff

Committed local state
  - git_history
  - git_commit
  - git_compare
```

The local workspace remains the shared source of truth. GitHub must not be required to inspect local-only commits.

## 3. Required Capabilities

### 3.1 `git_history`

Provide a bounded semantic query for recent commit history starting from a validated commitish.

It must return review-relevant metadata only and must not expose raw `git log` options.

Required information:

- resolved commit SHA;
- parent SHAs;
- subject;
- author name;
- committed timestamp.

The default starting revision is `HEAD`. The caller may lower, but not raise beyond, the server hard commit-count ceiling.

`git_history` must not return changed filenames in v0.2. Detailed change inspection belongs to `git_commit`.

### 3.2 `git_commit`

Provide a bounded semantic inspection of one validated local commit.

Required information:

- resolved commit SHA;
- parent SHAs;
- subject;
- author name;
- committed timestamp;
- comparison base used for the returned diff;
- allowed changed-file count;
- redacted-file count;
- bounded unified diff;
- explicit truncation flag.

Comparison semantics:

- normal commit: first parent -> commit;
- root commit: empty tree -> commit;
- merge commit: first parent -> merge commit.

The result must expose the parent list and comparison base so the reviewer can understand merge semantics.

### 3.3 `git_compare`

Provide a bounded comparison between two validated committed revisions.

Supported modes:

- `direct`: resolved base -> resolved head;
- `merge_base`: merge-base(resolved base, resolved head) -> resolved head.

`merge_base` is required because feature-branch review should not accidentally include unrelated changes made on the base branch after divergence.

`git_compare` covers committed Git state only. It does not include staged, unstaged, or untracked working-tree changes. Those remain the responsibility of `git_status` and `git_diff`.

### 3.4 Revision input

Public revision inputs are restricted commitish identifiers, not Git revision expressions.

v0.2 must support practical identifiers such as:

```text
HEAD
main
feature/foo
v0.2.0
full SHA
abbreviated SHA
```

The public contract must reject syntax that enables general revision expression behavior, including at minimum:

```text
~
^
..
@{
:
leading -
```

The implementation resolves accepted input to a concrete commit SHA before subsequent Git operations.

No MCP tool may accept caller-controlled Git flags, command fragments, or generic argument arrays.

## 4. Security Requirements

All v0.1 security invariants remain mandatory.

The new historical Git tools must preserve the same read-only boundary as `git_diff`:

- fixed Git executable selected by WorkspaceLens;
- fixed internal command templates;
- `shell: false` or equivalent;
- no arbitrary Git arguments;
- no Git writes or remote mutation;
- bounded output;
- no external diff execution;
- no textconv execution for diff-producing operations;
- no repository hook execution as part of the operation.

Historical Git content is not exempt from `AccessPolicy`.

A path blocked from `read_file` or current `git_diff` must not become readable through `git_commit` or `git_compare`, including when that path existed only historically and is currently deleted.

Git itself is not a security boundary.

## 5. Output Limits

`git_commit` and `git_compare` should reuse the existing server-wide Git diff payload ceiling unless implementation evidence demonstrates a need for a distinct limit.

v0.2 adds only the limits needed for history count:

```text
defaultGitHistoryCommits = 20
maxGitHistoryCommits = 100
```

The exact internal field names may differ, but callers must not be able to raise or disable the hard ceiling.

Any partial content result must report `truncated: true` explicitly.

## 6. Setup Documentation Requirement

v0.2 must add one canonical getting-started document that covers the proven path:

```text
Install WorkspaceLens
  -> authorize workspace
  -> workspace-lens doctor
  -> configure OpenAI Secure MCP Tunnel integration
  -> start required local processes
  -> complete ChatGPT-side app/connector setup
  -> call workspace_list from a real chat
  -> perform the first review
```

The documentation must distinguish:

- WorkspaceLens-owned steps;
- OpenAI Platform-owned steps;
- ChatGPT-owned steps;
- one-time setup;
- normal daily usage.

v0.2 documents the current process; it does not hide or automate lifecycle complexity. That productization belongs to v0.3.

## 7. Explicit Non-Goals

v0.2 MUST NOT add:

- WebUI or desktop GUI;
- Local Control Service;
- background daemon management;
- tunnel-client supervision;
- automatic login/startup behavior;
- hosted control plane;
- ChatGPT Project mapping;
- global/recent workspace selection state;
- Reviewer Skill packaging;
- development-flow integration APIs;
- reviewer-to-builder automatic handoff;
- generic Git tool;
- arbitrary Git arguments;
- shell execution;
- Git writes;
- remote Git fetch/push/synchronization;
- branch or tag mutation.

Small correctness fixes to existing CLI/doctor/setup behavior are allowed only when required for the canonical setup acceptance path.

## 8. Acceptance Criteria

v0.2 is complete only when all of the following are true:

1. all existing v0.1 review behavior remains available;
2. a reasoning chat can inspect recent local commits without GitHub;
3. a reasoning chat can inspect one selected local commit without GitHub;
4. a reasoning chat can compare a trusted base with a local reviewed head using both direct and merge-base semantics where appropriate;
5. local unpushed commits can be included in a complete review;
6. working-tree changes remain separately reviewable through `git_status` and `git_diff`;
7. blocked historical paths cannot leak names or diff bodies through the new tools beyond the contract's permitted redacted counts;
8. no new tool exposes arbitrary shell or Git execution primitives;
9. large history/diff results are bounded and explicitly truncated;
10. a new technical user can follow one documented path from installation to a successful real ChatGPT `workspace_list` call;
11. a real acceptance repository containing multiple local-only commits plus uncommitted changes can be reviewed end-to-end without GitHub push or file upload.

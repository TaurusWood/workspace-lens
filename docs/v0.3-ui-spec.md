# WorkspaceLens v0.3 UI Specification

Status: UI specification draft for v0.3. This document translates `v0.3-product-spec.md` and `v0.3-interaction-spec.md` into screen structure, visual hierarchy, component behavior, responsive rules, status language, feedback, and accessibility requirements. It intentionally does not choose the frontend framework, HTTP framework, process topology, credential storage mechanism, or operating-system integration mechanism.

## 1. UI Thesis

WorkspaceLens v0.3 is a local control plane, not a development dashboard.

The UI should feel like a focused developer utility:

- calm rather than decorative;
- compact but not dense enough to feel like an infrastructure console;
- explicit about local identity, authorization, and connection state;
- optimized for occasional configuration and troubleshooting rather than continuous monitoring;
- visually trustworthy and technically precise;
- free of code-editor, terminal, task-board, analytics-dashboard, or chat-product patterns.

The main visual principle is:

> Make workspace identity, connection health, and the next valid action obvious. Everything else is secondary.

The product should not add charts, counters, summary cards, decorative activity widgets, or large hero sections merely to make the interface appear more substantial.

## 2. Visual Character

### 2.1 Product character

The intended character is a modern desktop developer tool:

- neutral surfaces;
- restrained accent usage;
- clear typography;
- thin structural separators rather than heavy cards;
- moderate information density;
- small, meaningful status indicators;
- minimal animation;
- direct language.

The interface should not imitate a cloud operations dashboard. A local utility does not need large KPI tiles, real-time charts, or multiple monitoring panels on the landing page.

### 2.2 Light and dark appearance

The design system should support both light and dark appearance without changing information hierarchy.

The implementation MAY initially follow the operating-system/browser preference if an explicit theme selector would materially increase scope. If a manual appearance setting is included, it belongs in Settings and should support at least `System`, `Light`, and `Dark`.

### 2.3 Color roles

Exact color values belong to implementation tokens, but v0.3 should preserve semantic roles:

- **Accent** — primary actions, selected navigation, focus/active emphasis;
- **Success** — verified healthy state;
- **Warning** — usable but incomplete/degraded state, or user action required;
- **Danger** — blocking failure or destructive action;
- **Neutral** — disabled, unknown, informational, or secondary state.

Color must never be the only carrier of meaning. Every status also needs an icon/shape and text label.

`User confirmed` and `Verified` MUST NOT share identical visual treatment. The former should read as neutral/informational; the latter as machine-verified success.

## 3. Application Shell

### 3.1 Wide layout

For normal desktop widths, use a narrow persistent left navigation and a bounded main content column.

Conceptual layout:

```text
+------------------------------------------------------------------+
| WorkspaceLens     |                                              |
|                   |  Page title                    [● Healthy]    |
| Workspaces        |  Optional page description                    |
| Connection        |                                              |
| Diagnostics       |  Main content                                 |
| Settings          |                                              |
|                   |                                              |
|                   |                                              |
| v0.3.x            |                                              |
+------------------------------------------------------------------+
```

Guidelines:

- left navigation should remain visually light and narrow;
- the main content area should not stretch text and forms across very wide screens;
- ordinary content width should remain approximately suitable for reading/forms rather than full-viewport dashboards;
- global status belongs in the shell, not duplicated as a large card on every page;
- version/build metadata may appear unobtrusively at the bottom of navigation or Settings.

### 3.2 Narrow layout

At narrower browser widths, persistent side navigation should collapse into a compact top/header navigation or menu.

Requirements:

- all primary sections remain reachable without horizontal page scrolling;
- workspace rows may stack metadata vertically;
- actions should wrap or move into a clearly labeled overflow menu where appropriate;
- essential actions must remain tap/click accessible without hover;
- the UI must remain usable around 320 CSS px width even though desktop is the primary target.

### 3.3 Page header

Each permanent page uses a consistent page header:

- page title;
- optional one-line description only when it clarifies purpose;
- primary page action aligned opposite the title where space allows;
- global product status remains in the shell rather than becoming page-specific decoration.

Examples:

```text
Workspaces                                  [+ Add workspace]
Authorize the local projects WorkspaceLens may read.
```

```text
Connection
Manage the locally observable path between ChatGPT and WorkspaceLens.
```

Avoid redundant labels such as `WorkspaceLens Workspaces` or `Connection Dashboard`.

## 4. Core Components

v0.3 should use a small reusable component vocabulary.

### 4.1 Status Indicator

A status indicator combines:

- semantic icon/shape;
- short status label;
- optional concise explanation.

Supported common labels include:

- Healthy;
- Ready;
- Verified;
- User confirmed;
- Action required;
- Warning;
- Problem;
- Disabled;
- Checking;
- Unknown.

Do not invent multiple synonyms for the same state across pages.

### 4.2 Status Row

Used by Connection and Diagnostics.

Structure:

```text
[icon] Layer / check name
       concise supporting message                  [Status] [Action]
```

On narrow screens the status/action move below the message.

### 4.3 Workspace Row

The Workspaces page should prefer a vertically stacked list of rows rather than a card grid.

Rationale:

- project names and paths compare better in a list;
- users may eventually manage many workspaces;
- cards waste vertical space and encourage decorative content;
- rows remain easier to scan at different viewport widths.

Suggested structure:

```text
workspace-lens                                      Enabled  Healthy
workspace-lens
/Users/.../workspace-lens                                   >
```

The first line prioritizes display name and state. `workspace_id` and root are secondary metadata.

### 4.4 Buttons

Button hierarchy:

- **Primary** — one dominant next action per local context;
- **Secondary** — ordinary reversible operations;
- **Ghost/text** — low-emphasis navigation/helpers;
- **Danger** — destructive configuration action such as removing authorization.

Do not show multiple equally prominent primary buttons in one section unless the user truly has two equivalent next steps.

Buttons initiating async state transitions must show an in-progress state and disable duplicate invocation.

### 4.5 Toggle

Use toggles only for persistent binary settings such as:

- workspace Enabled / Disabled where context is unambiguous;
- Start at login;
- expose absolute paths if retained as a setting.

Do not use toggles for actions such as `Start tunnel`, `Restart`, or one-time setup completion.

### 4.6 Inline Notice

Use localized notices for warnings/errors related to a specific object or section.

Examples:

- workspace root is missing;
- tunnel profile points to an incompatible command;
- local connection is ready but provider setup is unverified.

Do not use global toast-only errors for conditions the user may need to inspect or fix.

### 4.7 Toast / transient feedback

Appropriate for short confirmations:

- `Copied`;
- `Workspace enabled`;
- `Display name updated`;
- `Diagnostics copied`.

A toast must not be the only record of a persistent error.

### 4.8 Dialog

Dialogs should be limited to actions where interrupting the flow is justified:

- remove workspace authorization;
- interrupt active requests when stopping/restarting, if active requests are observable;
- reconfigure an active connection where interruption is expected.

Ordinary enable/disable and restart actions should not produce unnecessary confirmation dialogs.

## 5. Workspaces Screen

Workspaces is the default post-onboarding page.

### 5.1 Layout

Conceptual wide-screen wireframe:

```text
Workspaces                                            [+ Add workspace]
Authorize the local projects WorkspaceLens may read.

---------------------------------------------------------------
workspace-lens                             [Enabled] [Healthy]  >
workspace-lens
~/code/workspace-lens
---------------------------------------------------------------
daily-signals                             [Enabled] [Healthy]  >
daily-signals
~/code/daily-signals
---------------------------------------------------------------
J-Store                                  [Disabled]             >
j-store
~/code/J-Store
---------------------------------------------------------------
```

This is a management list, not a repository activity feed.

Do not place branch, HEAD, dirty file count, last access history, CR count, or Plan count in the v0.3 default list. Those would shift the page toward a development dashboard and belong, if useful, to later context/observability work.

### 5.2 Row states

Enabled/healthy:

- normal foreground emphasis;
- success status label;
- entire row or explicit chevron/detail action opens detail.

Enabled/warning:

- warning indicator near status;
- short reason visible or available directly in detail;
- row remains usable when the warning is non-blocking, such as no Git repository.

Enabled/error:

- blocking issue clearly visible;
- reason such as `Root unavailable` shown rather than generic `Error`;
- global application should not necessarily be marked broken if other workspaces remain usable.

Disabled:

- reduced visual emphasis without making text unreadable;
- explicit `Disabled` label;
- path/name remain visible.

### 5.3 Empty state

When no workspaces are configured, do not show an empty table frame.

Use a compact empty state in the content column:

```text
No workspaces yet

Add a local project to make its read-only context available through
WorkspaceLens. Your files stay local and WorkspaceLens cannot modify them.

[Add workspace]
```

No illustration is required for v0.3.

### 5.4 Add Workspace surface

Prefer a focused modal/dialog or compact dedicated flow rather than embedding a large form permanently on Workspaces.

Fields/actions:

1. Select/provide root;
2. Display name;
3. Workspace ID;
4. validation result;
5. `Add workspace`.

Suggested layout:

```text
Add workspace

Local folder
[ ~/code/daily-signals                       ] [Choose]

Display name
[ daily-signals                              ]

Workspace ID
[ daily-signals                              ]
Stable identifier used by reasoning clients. Cannot be changed later.

[validation message]

                              [Cancel] [Add workspace]
```

Only errors relevant to a field should appear next to that field. General root validation may appear as one localized notice.

## 6. Workspace Detail

### 6.1 Layout hierarchy

Workspace detail should be a calm settings/detail page, not a repository browser.

Conceptual layout:

```text
< Workspaces

daily-signals                                    [Enabled] [Healthy]
daily-signals
~/code/daily-signals

Identity
------------------------------------------------------------
Display name    daily-signals                       [Edit]
Workspace ID    daily-signals                  immutable
Local root      ~/code/daily-signals            authorized
Git context     Available

Use in reasoning clients
------------------------------------------------------------
[Copy Project Instructions]
[Copy Review Prompt]   [Copy Plan Prompt]

Authorization
------------------------------------------------------------
Workspace access                                  [Enabled toggle]

Danger zone
------------------------------------------------------------
Remove this authorization without changing local files.
                                      [Remove authorization]
```

### 6.2 Identity section

The stable `workspace_id` should be visible enough to copy/reference, but not styled like an internal database identifier.

Use monospace typography selectively for:

- workspace ID;
- filesystem path;
- command/tool names when shown.

Display name remains ordinary UI typography.

### 6.3 Reasoning helpers

Do not elevate Review/Plan helpers above identity or authorization.

They are optional convenience actions, so they belong in a secondary section such as `Use in reasoning clients`.

`Copy Project Instructions` may be first because it helps establish durable workspace targeting. Review/Plan remain sibling secondary actions.

If clipboard access fails, open a small text surface with selectable content and explicit `Select and copy` guidance.

### 6.4 Danger zone

Use restrained danger styling. The entire section should not be a large red panel.

Only the destructive button and small warning cues require danger emphasis.

## 7. Connection Screen

Connection is the primary recovery/control surface for provider integration.

### 7.1 Visual model

Use a vertical ordered list of connection layers rather than a diagram-heavy dashboard.

Conceptual layout:

```text
Connection
Manage the locally observable path between ChatGPT and WorkspaceLens.

Local connection                                           [Healthy]

[✓] Local runtime                                Healthy
    WorkspaceLens control service is available.

[✓] Tunnel client                                Installed
    Official OpenAI tunnel client is available.

[✓] Local tunnel profile                         Ready
    Profile "workspace-lens" matches this installation.

[✓] Tunnel runtime                               Healthy      [Restart]
    Local tunnel health check passed.

[!] ChatGPT setup                                User confirmed
    WorkspaceLens cannot verify all provider-side settings. [Review setup]

[○] Verification                                 Not verified
    Verify from a real ChatGPT tool call.                   [Verify]
```

The ordering should match causal dependency. A lower layer should not visually appear healthy if a prerequisite layer blocks it.

### 7.2 Overall status summary

A small summary at the start of the page may say:

- `Local connection is ready.`
- `Action required before remote use.`
- `Tunnel runtime needs attention.`

Do not add numeric health scores, percentages, or synthetic uptime metrics in v0.3.

### 7.3 Recovery actions

The primary action belongs beside the failing layer.

Examples:

- `Install`;
- `Configure`;
- `Start`;
- `Restart`;
- `Repair profile`;
- `Review ChatGPT setup`;
- `Verify`.

Avoid a generic `Fix connection` button that hides which layer is affected.

### 7.4 Healthy state

A fully healthy local connection should become visually quiet. The page should not celebrate success with large banners or animations.

The product should make failure salient and success calm.

## 8. Setup UI

Setup is temporary and should visually differ from the normal control surface without becoming a separate product.

### 8.1 Layout

Use a centered/bounded single-column setup surface with visible progress:

```text
WorkspaceLens setup

1 System  —  2 Workspace  —  3 Tunnel  —  4 ChatGPT  —  5 Verify

[Current stage content]

                                        [Configure later] [Continue]
```

On narrow screens the stage indicator should wrap/stack without requiring horizontal scrolling.

### 8.2 Progress semantics

Stages should show states such as:

- complete / machine verified;
- current;
- incomplete;
- warning/user confirmation where needed.

Do not present provider-owned checklist completion with the same checkmark treatment as machine verification.

### 8.3 Stage 1 — System

Prefer a compact checklist:

```text
System

[✓] WorkspaceLens runtime       Ready
[✓] Git                         Available
[!] Tunnel client               Missing       [Install]
```

Do not expose PATH details, versions, or raw diagnostic output unless the user expands details.

### 8.4 Stage 2 — First Workspace

Reuse the Add Workspace form rather than inventing setup-specific workspace fields.

A successful add should visually confirm that the workspace is now authorized read-only.

### 8.5 Stage 3 — Tunnel

Split the stage into two visually distinct responsibilities:

- `OpenAI account step`;
- `Local WorkspaceLens step`.

The UI must make it obvious when the user has left WorkspaceLens to complete an external action.

Credentials should be rendered as secret/password inputs where appropriate, with no value shown after submission unless the later technical design explicitly permits safe retrieval. The final credential handling contract belongs to the Technical RFC.

### 8.6 Stage 4 — ChatGPT

Provider-side checklist should be concise and numbered.

Each item may support:

- external-link action;
- user confirmation checkbox/action;
- explanatory note when WorkspaceLens cannot verify it.

Avoid embedding a replica of ChatGPT settings UI, screenshots that will quickly become stale, or browser automation controls.

### 8.7 Stage 5 — Verify

The final stage should focus on one task:

```text
Verify WorkspaceLens from ChatGPT

1. Open a ChatGPT conversation with the WorkspaceLens App available.
2. Ask it to call `workspace_list`.
3. Confirm your workspace is returned.

[Copy verification prompt]

Waiting for verification…
```

If machine attribution is unavailable, provide a clearly secondary `I verified it successfully` action that results in `User confirmed`, not `Verified`.

## 9. Diagnostics Screen

### 9.1 Structure

Use grouped check lists, not raw console logs.

```text
Diagnostics                                      [Run again]

Local runtime
[✓] Configuration                               Valid
[✓] Runtime                                     Healthy

Workspaces
[✓] workspace-lens                              Healthy
[!] legacy-project                              Root unavailable   [Open]

Connection
[✓] Tunnel client                               Installed
[✓] Profile                                     Valid
[×] Tunnel runtime                              Stopped            [Start]

Support
[Copy diagnostic report]
[ ] Include local paths
```

### 9.2 Details disclosure

Technical detail should be available progressively:

- first line: human-readable problem;
- optional expanded detail: technical reason/code;
- action: clear recovery.

Raw command output should not dominate the page. If included at all, place it behind expandable diagnostic details.

### 9.3 Check states

Use exactly four diagnostic states where possible:

- Pass;
- Warning;
- Fail;
- Unknown/Checking.

Do not invent many severity levels.

## 10. Settings Screen

Settings is intentionally small.

Suggested v0.3 layout:

```text
Settings

Startup
------------------------------------------------------------
Start WorkspaceLens at login                         [toggle]
Keep the local control plane available after sign-in.

Privacy
------------------------------------------------------------
Expose absolute paths to reasoning clients           [toggle]
Off by default.

Setup
------------------------------------------------------------
Review setup steps                               [Open]

About
------------------------------------------------------------
Version        0.3.x
```

Settings should not duplicate workspace authorization or Connection controls.

Provider secrets, tunnel profile repair, and diagnostics belong to Connection/Diagnostics rather than a generic Settings dump.

## 11. Status Visual Language

### 11.1 Product-level states

| State | Meaning | Visual treatment |
| --- | --- | --- |
| Healthy | Local required layers are machine-verified healthy | success icon + text, visually quiet |
| Action required | Known user/setup action remains | warning icon + explicit next action |
| Problem | Configured local layer is failing | danger icon + reason/action |
| Checking | Current state is being refreshed | neutral progress treatment |

### 11.2 Verification states

| State | Meaning |
| --- | --- |
| Verified | WorkspaceLens has sufficient machine-observed evidence |
| User confirmed | User reports provider-side step succeeded; not machine verified |
| Not verified | No reliable proof yet |

These labels should remain stable across Setup and Connection.

### 11.3 Workspace states

Prefer combinations such as:

- `Enabled · Healthy`;
- `Enabled · Warning`;
- `Enabled · Root unavailable`;
- `Disabled`.

Avoid ambiguous labels such as `Online`, `Active`, or `Connected` for workspaces. A workspace is an authorization root, not a network session.

## 12. Typography and Data Presentation

### 12.1 Typography

Use the platform/system sans-serif stack by default unless later implementation needs justify another bundled web-safe choice.

Use monospace only for machine identities and technical literals:

- workspace IDs;
- paths;
- command/tool names;
- short error codes.

Do not render entire pages in monospace simply because the user is a developer.

### 12.2 Text hierarchy

Recommended hierarchy:

- page title;
- section heading;
- primary row/object name;
- normal body/support text;
- secondary metadata;
- captions/help text.

Keep body copy concise. Most help text should be one or two sentences.

### 12.3 Paths

Long paths must truncate gracefully in list contexts while remaining fully available on detail/focus/copy surfaces.

Never allow long paths to force page-level horizontal scrolling.

## 13. Spacing and Density

The UI should use a consistent moderate-density rhythm.

Principles:

- workspace/status rows should be compact enough for 8–15 projects without feeling oversized;
- forms should have more vertical space than lists;
- related metadata stays close together;
- sections are separated primarily by spacing and subtle borders, not nested cards;
- avoid cards inside cards;
- avoid excessive rounded containers around every label or field.

A developer with ten workspaces should be able to scan the list on an ordinary laptop screen without each workspace consuming a large card.

## 14. Responsive Behavior

Desktop is the primary environment, but the local WebUI should remain usable at narrow widths.

### Wide / desktop

- persistent left navigation;
- page actions may align right of title;
- workspace/status rows use horizontal alignment;
- main content column remains bounded.

### Medium

- navigation may remain side-based if practical or collapse;
- metadata/actions wrap naturally;
- no information becomes hover-only.

### Narrow / mobile-like

- navigation becomes compact top/menu form;
- page actions move below title where necessary;
- workspace/status rows stack;
- buttons have touch-friendly hit areas;
- dialogs/forms fit without horizontal scrolling;
- destructive actions remain explicit and separated from ordinary actions.

There is no requirement to make v0.3 feel like a native mobile application; responsive behavior exists so the browser UI remains functional.

## 15. Loading, Empty, Error, and Transition States

### 15.1 Initial loading

Do not blank the entire application while one status request loads.

The shell/navigation should render immediately where possible, with localized skeleton/progress indicators for dynamic content.

### 15.2 Refreshing existing state

Keep the last known state visible but clearly mark it as refreshing only when doing so does not create a false-current impression.

For safety-sensitive configuration state, prefer explicit `Checking` when stale data could mislead the user.

### 15.3 Mutation feedback

For actions such as enable/disable/start/restart:

- show pending state on the initiating control;
- disable duplicate submission;
- update the affected status in place after success;
- provide concise error text adjacent to the failed action;
- avoid forcing a full-page refresh.

### 15.4 Network/control API loss

If the WebUI can no longer reach its local control service, display a persistent high-priority state explaining that the UI itself has lost contact with WorkspaceLens.

Do not mislabel this as `Tunnel disconnected` because those are different layers.

## 16. Accessibility

v0.3 UI must satisfy ordinary keyboard and assistive-technology expectations for a local web application.

Requirements:

- all actions reachable by keyboard;
- visible focus treatment;
- semantic buttons, links, inputs, checkboxes, and headings;
- status changes announced through an appropriate live region when needed;
- form inputs have visible labels;
- error messages are associated with their fields/actions;
- icon-only buttons require accessible labels;
- color is never the sole indication of status;
- tap/click is sufficient for every primary action; hover may enhance but never reveal required controls;
- minimum practical touch target around 44 × 44 CSS px for compact/mobile layouts;
- reduced-motion preference respected.

## 17. Motion

Animation should be minimal and functional.

Allowed examples:

- short spinner/progress indicator during checks;
- subtle disclosure expansion;
- brief status transition.

Avoid:

- animated connection diagrams;
- continuous pulse/glow on healthy status;
- decorative page transitions;
- progress animation that suggests provider verification WorkspaceLens cannot observe.

## 18. Copy and Language Style

UI copy should be direct and factual.

Prefer:

- `Tunnel runtime is stopped.`
- `Start tunnel`
- `Local connection is ready. ChatGPT setup has not been verified.`
- `Remove workspace authorization`

Avoid:

- `Oops! Something went wrong.`
- `Your AI is offline.`
- `Project disconnected.`
- `Delete project`
- `Everything looks amazing!`

Product copy must preserve ownership boundaries. It should distinguish:

- local WorkspaceLens facts;
- local tunnel/integration facts;
- user-confirmed provider facts;
- unknown provider-side facts.

## 19. Explicit UI Non-goals

v0.3 UI does not include:

- overview/dashboard KPI cards;
- charts or usage analytics;
- code editor/browser;
- diff viewer;
- terminal;
- task board;
- chat interface;
- ChatGPT conversation list;
- CR/Plan history;
- review pass/fail indicators;
- prompt library/editor;
- project thumbnails/cover art;
- animated topology map;
- activity timeline beyond current troubleshooting state;
- complex custom theming.

## 20. UI Acceptance Criteria

The v0.3 UI is acceptable when:

1. A user can identify the primary purpose of each page without reading documentation.
2. Workspaces is the clear post-onboarding landing page and remains efficient with multiple projects.
3. Global status communicates actionable product health without claiming unverifiable ChatGPT state.
4. Workspace identity, authorization state, and path are visually distinct and easy to scan.
5. Connection failures are presented by layer with a specific next action rather than as one generic disconnected state.
6. Setup clearly distinguishes machine-verified steps from user-confirmed provider steps.
7. Review/Plan/Project Instructions helpers remain secondary conveniences rather than dominant workflow controls.
8. Destructive configuration actions are clearly separated from ordinary actions and describe their actual effect.
9. Diagnostics prioritize human-readable cause and recovery over raw logs.
10. The interface remains usable with keyboard, without hover, and at narrow viewport widths.
11. The UI does not grow into a dashboard, code browser, workflow manager, or ChatGPT session manager.
12. Healthy normal operation is visually quiet and does not demand routine user attention.

## 22. Inputs to the Technical Architecture RFC

The UI specification assumes several behaviors whose implementation must be decided technically:

- how the browser/local service obtains a workspace folder/path;
- how global and per-layer status are refreshed/pushed;
- how the WebUI remains available relative to the MCP/tunnel processes;
- how start/stop/restart commands are supervised;
- how credentials are submitted/stored/retrieved safely;
- how clipboard fallback is implemented;
- how CLI and WebUI concurrent configuration changes are detected;
- whether the control UI uses polling, event streaming, or another local status transport;
- how autostart and shutdown are surfaced consistently across supported operating systems;
- which frontend/component stack can implement this design with minimal runtime and packaging complexity.

The Technical RFC must satisfy this UI contract without adding product surface area merely to accommodate a framework or process model.

# WorkspaceLens v0.3 Design / Contract Freeze Declaration

Status: **FROZEN FOR IMPLEMENTATION**.

This declaration closes the v0.3 requirements / architecture / interaction / test-design phase and authorizes production implementation under the existing Implementation Plan and executable contracts.

The purpose of the freeze is to stop implementation from continuously reopening solved product questions. From this point forward, code should conform to the frozen contracts unless implementation evidence proves that a contract must be reopened under the rules below.

## 1. Frozen authority set

The following v0.3 documents are frozen as the implementation authority set:

- `version-requirements-v0.2-v0.5.md`
- `v0.3-product-spec.md`
- `v0.3-interaction-spec.md`
- `v0.3-ui-spec.md`
- `v0.3-ui-implementation-contract.md`
- `v0.3-technical-architecture-rfc.md`
- `v0.3-bootstrap-distribution-contract.md`
- `v0.3-control-plane-security-contract.md`
- `v0.3-test-contract.md`
- `v0.3-implementation-plan.md`

An older status label such as "draft" inside one of these documents does not make it implementation-optional after this freeze declaration. The current branch versions are the accepted v0.3 contracts unless this declaration's reopen policy is triggered.

## 2. Execution authority

Local coding harnesses should use:

- `v0.3-goal-mode-prompt.md`

for bounded Goal Mode implementation.

The prompt is an execution wrapper, not a second source of product truth. If it conflicts with a frozen contract, the frozen contract wins.

## 3. What is frozen

The freeze covers:

- v0.3 product scope and non-goals;
- one-service / many-workspaces architecture;
- explicit workspace identity and no hidden current workspace;
- read-only MCP/Core authority boundary;
- local Control Runtime topology;
- Control API vs MCP capability separation;
- browser/control-plane security requirements;
- provider/tunnel integration responsibility boundaries;
- canonical `workspace-lens start` bootstrap behavior;
- UI information architecture and state semantics;
- UI visual/implementation constraints;
- executable behavior/test contracts;
- implementation slice order and dependency boundaries.

Implementation details that are intentionally left open by these contracts remain implementation choices.

## 4. What is NOT frozen

The following are expected to change during implementation and do not require reopening the design phase:

- `docs/v0.3-test-coverage.md` GREEN/RED/BLOCKED/MANUAL-GATE status;
- exact private file/module names where the Implementation Plan says names are approximate;
- implementation-internal helper structure;
- exact semantic token values inside the frozen UI constraints;
- exact lightweight CSS/component organization;
- exact accepted OS credential-store package after Gate C evidence;
- captured Gate B success-path fixtures;
- CI configuration;
- release notes and final v0.3 Getting Started documentation;
- bug fixes that preserve contract semantics.

## 5. Allowed reasons to reopen a frozen contract

A frozen contract may be reopened only for one of these reasons:

1. **Implementation impossibility** — concrete code/runtime evidence shows the requirement cannot be implemented as written.
2. **Verified external dependency behavior** — an official dependency or platform behaves differently from the frozen assumption.
3. **Security defect** — the frozen design creates or misses a material security problem.
4. **Internal contract conflict** — two frozen authorities require mutually incompatible behavior.
5. **Release-blocking product defect** — real E2E evidence shows the frozen interaction cannot satisfy the stated v0.3 product goal.

The following are NOT sufficient reasons:

- the implementation is inconvenient;
- another abstraction feels cleaner;
- a coding agent prefers another framework;
- a test is difficult to satisfy;
- adding extra features is easy while touching the area;
- a visually different UI is more fashionable;
- speculative future v0.4/v0.5 needs.

When reopening is required, use the `CONTRACT BLOCKED` format from the Goal Mode prompt and stop dependent implementation until the owner/reviewer decides.

## 6. Test phase close-out

The pre-implementation executable contract phase is considered **CLOSED** after the current branch changes.

Key properties now established:

- v0.2 regression contracts remain the compatibility baseline;
- required v0.3 behavior is represented as executable GREEN/RED/BLOCKED/MANUAL-GATE evidence rather than prose only;
- known false-green paths identified during independent CR were closed;
- runtime no-restart evidence uses a live `runtime_instance_id`, with a supplemental contract requiring distinct runtime instances to receive distinct IDs;
- external integration tests use injected adapter objects rather than production test-mode strings where practical;
- product E2E follows package / Control API / MCP product surfaces rather than substituting direct service calls.

Do not reopen the whole Test Phase for ordinary implementation-time test maintenance. Add or refine a test only when it protects a frozen contract or fixes a demonstrated test defect.

## 7. Technical gate status at freeze

### Gate A — MCP Streamable HTTP parity

**PASS.**

The currently selected MCP SDK/transport approach has sufficient parity evidence. Do not repeat this spike unless implementation produces contradictory evidence.

### Gate B — official tunnel managed-runtime contract

**ARCHITECTURE DECISION CLOSED / OFFLINE CONTRACT ACCEPTED / REAL SUCCESS PATH MANUAL-GATE.**

The accepted missing-alias rule is narrow Option A classification:

- supported `status`/`stop` context;
- non-zero exit;
- exact frozen verified missing-alias stderr shape;
- normalize to bounded alias-missing state/error;
- all other unknown stderr remains generic external-runtime failure;
- no general log scraping or `pgrep` fallback.

Real connected/healthy/stop success-path fixtures still require real provider credentials before final release PASS.

### Gate C — SecretStore platform viability

**BLOCKED / NOT YET SELECTED.**

This does **not** block GOAL-1 or the earlier workspace/control-runtime slices. It blocks SecretStore-dependent auto-connect/autostart completion until an OS-backed implementation is selected and proven on Node 24. Plaintext automatic fallback remains forbidden.

## 8. UI freeze

`v0.3-ui-implementation-contract.md` is now part of the frozen authority set.

External frontend skills and public design guidance were used only to calibrate implementation constraints. The repository contract, not any external Skill, controls the product.

The frozen UI direction is a restrained developer utility / local control plane. It explicitly rejects generic SaaS-dashboard and AI-flavored decoration where those patterns do not serve the product.

## 9. Implementation entry point

Production implementation may now begin.

Use `v0.3-goal-mode-prompt.md` and start with:

```text
GOAL-1
Slice 0 — Contract Scaffolding and Shared Application Layer
Slice 1 — Safe Mutable Configuration
Slice 2 — Live Workspace Registry / no-restart visibility
```

Rules:

- implement strictly in slice order;
- complete focused verification before moving to the next slice;
- create one focused commit per slice;
- do not begin Slice 3 inside GOAL-1;
- stop after GOAL-1 for independent CR.

## 10. Implementation review mode

From this point, the default loop is:

```text
Frozen Contracts
    -> bounded Goal implementation
    -> focused tests + regression + typecheck + build
    -> independent CR
    -> next Goal
```

Do not return to broad requirements/architecture redesign after every code review. Review should first ask whether the implementation satisfies the frozen contract with minimal complexity.

## 11. Release reminder

Design/Contract Freeze is not Release Freeze.

Before v0.3 release, the remaining release-level gates still include at minimum:

- Gate B real provider success-path evidence;
- Gate C SecretStore viability;
- all release-blocking v0.3 contracts GREEN;
- final package-shaped E2E;
- manual real-ChatGPT verification;
- CI gate established;
- release/getting-started documentation reconciled with implemented behavior.

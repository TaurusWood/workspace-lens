# WorkspaceLens v0.3 Implementation Plan

Status: Implementation-ready plan for v0.3.

Upstream contracts:

- `version-requirements-v0.2-v0.5.md`
- `v0.3-product-spec.md`
- `v0.3-interaction-spec.md`
- `v0.3-ui-spec.md`
- `v0.3-technical-readiness-audit.md`
- `v0.3-technical-architecture-rfc.md`
- `v0.3-bootstrap-distribution-contract.md`
- `v0.3-control-plane-security-contract.md`

This plan is intentionally sliced so each implementation task can be executed and reviewed independently by a coding agent without requiring it to redesign product or architecture decisions.

The governing delivery principle is:

> **One install, one bootstrap, zero daily CLI.**

The governing architecture principle is:

> **Add a local control plane around the existing read-only Core. Preserve the Core/MCP security contract and share application logic between CLI and WebUI.**

---

# 1. Global Rules

Every slice MUST follow these rules.

## 1.1 Preserve existing v0.2 behavior

Unless explicitly changed by this plan:

- existing MCP tool names remain unchanged;
- existing MCP input/output semantics remain unchanged;
- existing read-only AccessPolicy remains unchanged;
- existing Git/file/search bounds remain unchanged;
- `workspace-lens serve` stdio remains supported;
- existing workspace config remains readable;
- users do not re-authorize workspaces during upgrade.

## 1.2 No scope expansion

Do not add:

- repository write tools;
- arbitrary shell execution;
- terminal UI;
- code editor/browser;
- build/test runner;
- ChatGPT conversation/session management;
- CR/Plan workflow state;
- Activity/Access history beyond v0.3 lightweight current-state observability;
- Electron/Tauri/desktop webview shell;
- per-workspace tunnels;
- hidden global active workspace.

## 1.3 Shared business logic

CLI and WebUI MUST call shared application services.

Forbidden end state:

```text
CLI implementation rules
+
WebUI implementation rules
+
MCP implementation rules
all independently duplicated
```

Target:

```text
CLI --------+
             |
Control API -+--> Application Services --> Config/Core/Integrations
```

## 1.4 Test-before-next-slice rule

A slice is complete only when:

1. its focused tests pass;
2. full existing test suite passes;
3. TypeScript typecheck passes;
4. no later slice is required to make the current slice internally correct.

A temporarily hidden UI/API route is acceptable; an internally broken contract is not.

# 3. Pre-implementation Technical Gates

These are bounded spikes. They should produce code/tests or a short documented result, not open-ended research.

## Gate A — MCP Streamable HTTP parity

Goal: prove the currently pinned MCP SDK can expose the existing tool definitions through a local Streamable HTTP endpoint without changing public semantics.

Required proof:

- create a minimal in-test HTTP server;
- mount existing server/tool definitions;
- invoke at least `workspace_list` through an MCP HTTP client;
- compare successful/error envelope behavior with stdio contract;
- close cleanly.

Pass condition:

- no tool contract change;
- no forced MCP SDK major migration.

If the current SDK cannot satisfy this cleanly, stop and write a bounded migration decision before changing the SDK.

Commit boundary:

```text
spike: prove MCP streamable HTTP parity
```

The spike may be retained as an integration test if production-quality.

## Gate B — official tunnel runtime JSON contract

Goal: lock the exact supported command/JSON adapter surface used by WorkspaceLens.

Use the official native managed-runtime commands only. Verify exact production assumptions for:

- `runtimes connect` with stable alias;
- `--mcp-server-url`;
- runtime key by `env:` reference;
- `runtimes status <alias> --json`;
- `runtimes stop <alias> --json` or supported equivalent;
- missing alias;
- unhealthy runtime;
- repair actions/diagnostics fields needed by product status.

Deliverable:

- fixtures representing supported JSON outputs;
- a tiny parser/normalizer test contract.

Do not implement process grep/PID fallback for the normal v0.3 path.

## Gate C — SecretStore platform viability

Goal: verify the chosen OS credential-store dependency/implementation on the initial supported platform(s), especially Node 24 packaging.

Required checks:

- install/build on Node 24;
- set/get/delete round trip in an isolated test/manual fixture;
- no secret in ordinary config;
- failure mode when keychain/service unavailable.

Decision rule:

- if `@github/keytar` or another candidate is reliable, adopt behind `SecretStore`;
- if not, choose another OS-native adapter;
- do not use plaintext automatic fallback.

This gate blocks autostart auto-connect, not earlier workspace/control-server slices.

# 5. Slice 1 — Safe Mutable Configuration

## Goal

Make workspace administration safe for concurrent CLI/WebUI use.

## Implement `ConfigStore.mutate()`

Semantics:

```text
lock
-> load latest config
-> validate
-> apply mutation callback
-> validate result
-> temp write 0600
-> atomic rename
-> unlock
```

Introduce an inter-process lock abstraction using a reviewed atomic lockfile/directory mechanism.

A dependency such as `proper-lockfile` is acceptable after normal dependency/security review.

## Extend workspace administration

Add application operations:

- list;
- add;
- rename display name;
- enable;
- disable;
- remove;
- validate root;
- suggest/validate new identity.

Rules:

- `workspace_id` immutable after creation;
- root immutable after creation in v0.3;
- enabling revalidates root;
- remove affects WorkspaceLens authorization only;
- no whole-config replacement API.

## CLI refactor

Existing `add`, `remove`, `list` should call `WorkspaceAdminService`.

If useful, add advanced CLI commands for enable/disable, but this is not required for the normal user path.

## Tests

Unit:

- each mutation;
- duplicate/overlap behavior preserved;
- immutable ID/root;
- permissions/atomic write.

Multi-process integration:

- two simultaneous independent mutations both survive;
- no partial JSON;
- lock timeout produces explicit error;
- stale lock recovery is bounded.

## Done

No normal product path performs `load -> mutate object -> save` outside the locked config mutation layer.

## Suggested commit

```text
feat: add safe concurrent workspace administration
```

# 6. Slice 2 — Live Workspace Registry / No-restart Authorization

## Goal

Workspace changes become visible to subsequent MCP requests without restarting WorkspaceLens or the tunnel.

## Replace startup-only authorization snapshot

Current problem:

```text
serve startup
-> ConfigStore.load()
-> WorkspaceRegistry(snapshot forever)
```

Target:

```text
MCP request
-> load current validated config snapshot
-> resolve workspace by explicit id
-> use immutable request-scoped workspace snapshot
```

Implementation may introduce:

- `WorkspaceRegistryProvider`;
- `LiveWorkspaceRegistry`;
- equivalent request-scoped resolver.

Keep Core semantics explicit; do not add global active-workspace state.

## Fail closed

Malformed/unreadable current config must produce stable config failure rather than silently serving an old broader authorization snapshot.

## Tests

Required integration flow:

```text
runtime starts with A
-> add B through service
-> next workspace_list sees B
-> disable A
-> next A content request returns disabled
-> no restart
```

Concurrent test:

- issue requests against A/B in parallel;
- prove filesystem roots, Git cwd, and AccessPolicy do not cross;
- one failure cannot redirect another request.

## Done

No-restart workspace add/disable works through both stdio test path and the shared tool context model.

## Suggested commit

```text
feat: make workspace authorization live per request
```

# 27. Definition of Done

WorkspaceLens v0.3 is done when all of the following are true:

1. One packaged installation supports the canonical `workspace-lens start` bootstrap.
2. A healthy existing Control Runtime is reused, not duplicated.
3. WebUI, Control API, and read-only MCP HTTP are available from one WorkspaceLens Control Runtime.
4. Official tunnel-client managed-runtime APIs own tunnel process lifecycle; WorkspaceLens does not use `pgrep`/PID management in the normal path.
5. Multiple enabled workspaces are available through one normal provider connection.
6. Adding/disabling a workspace takes effect on the next MCP request without restarting WorkspaceLens.
7. Concurrent requests to different workspaces remain isolated.
8. CLI and WebUI use the same application services and cannot lose concurrent config updates.
9. Control API satisfies the v0.3 security contract.
10. Runtime provider secrets are not stored in plaintext ordinary config, argv, logs, or diagnostics.
11. Start-at-login enables normal daily use without Terminal interaction.
12. Browser closure does not stop WorkspaceLens.
13. Provider-side state is never overclaimed as machine-verified when WorkspaceLens cannot prove it.
14. Existing `workspace-lens serve` stdio clients remain supported.
15. Existing v0.2 tool/security contracts continue to pass.
16. The clean-environment E2E acceptance scenario passes.
17. High-level documentation has no contradictory active-workspace/connector-scope/process-lifecycle truth sources.

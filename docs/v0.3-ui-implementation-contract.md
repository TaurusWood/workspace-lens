# WorkspaceLens v0.3 UI Implementation Contract

Status: **FROZEN implementation contract for v0.3 UI work**.

This document constrains how the already-defined v0.3 UI is implemented. It does **not** reopen product scope, information architecture, interaction semantics, security behavior, or test contracts.

## 1. Authority and precedence

When implementing UI, use the following precedence:

1. `v0.3-product-spec.md`
2. `v0.3-interaction-spec.md`
3. `v0.3-control-plane-security-contract.md`
4. `v0.3-test-contract.md`
5. `v0.3-ui-spec.md`
6. **this implementation contract**

If this document appears to conflict with a higher-level contract, the higher-level contract wins. Do not silently reinterpret either document; surface a `CONTRACT BLOCKED` report if the conflict affects implementation.

## 2. Why this contract exists

Generic frontend agents often converge on a recognizably templated SaaS/dashboard aesthetic even when the product does not need it. WorkspaceLens is specifically **not** a dashboard, IDE, observability console, chat surface, or marketing site.

The intended result is a calm, technically precise local developer utility whose interface becomes quiet when the system is healthy and makes failures/actions obvious when attention is required.

The design goal is:

> **Intentional, restrained, production-grade utility UI — not generic AI-generated SaaS UI.**

External design skills were reviewed only as research inputs. They are **not runtime dependencies and are not authorities over this repository**. Useful ideas were retained where they fit WorkspaceLens:

- deliberate visual hierarchy and avoidance of generic templated UI;
- consistent spacing, typography and semantic color tokens;
- keyboard/accessibility correctness;
- responsive behavior without horizontal overflow;
- visible labels and localized form/error feedback;
- restrained motion and reduced-motion support;
- calm UI principles that remove decorative complexity.

WorkspaceLens intentionally rejects advice that would push a developer utility toward expressive marketing layouts, visual spectacle, or unnecessary aesthetic risk.

## 3. Visual direction

### 3.1 Product character

The UI MUST feel like a mature desktop developer utility:

- calm;
- compact but readable;
- neutral;
- precise;
- settings/control-plane oriented;
- structurally simple;
- low visual noise;
- trustworthy around authorization, secrets and connection state.

Reference category, not pixel-copy targets:

- modern developer-tool settings surfaces;
- restrained local utilities;
- Linear/Raycast/Vercel-like clarity and density where appropriate.

Do not imitate another product's branding or exact layout.

### 3.2 Explicit anti-patterns

Do **not** introduce any of the following merely to make the UI look modern:

- marketing hero sections;
- KPI/statistic cards;
- bento-grid dashboards;
- glassmorphism or decorative blur;
- gradient-heavy surfaces;
- neon/purple "AI product" styling;
- large decorative illustrations;
- card-inside-card nesting;
- large floating rounded containers around ordinary page content;
- oversized headings used as decoration;
- heavy drop shadows;
- animated page entrances;
- decorative background motion;
- synthetic health scores or percentages;
- charts where a status row communicates the information better;
- emoji used as interface icons;
- hover-only controls;
- color as the sole state indicator.

A UI that is visually quieter than a typical SaaS dashboard is a success, not a deficiency.

## 4. Layout contract

### 4.1 Desktop shell

Follow `v0.3-ui-spec.md`:

- narrow persistent left navigation;
- bounded main content column;
- page title + optional concise description;
- at most one dominant primary action per local context;
- global status in the shell, not repeated as a hero/card on every page.

The content column MUST NOT stretch ordinary forms/text across the full viewport.

Prefer normal document flow over multiple independent scrolling panes.

### 4.2 Responsive behavior

Desktop is primary, but the UI MUST remain operable down to approximately **320 CSS px** without horizontal page scrolling.

At narrow widths:

- collapse persistent side navigation into a compact menu/header treatment;
- stack row metadata where needed;
- keep primary actions reachable without hover;
- allow action groups to wrap or move into a clearly labelled overflow menu;
- keep form controls within viewport bounds;
- never disable browser zoom.

Use a small, systematic breakpoint set. Do not create per-component arbitrary breakpoints unless a real layout failure requires one.

### 4.3 Spacing

Use a coherent **4/8-based spacing rhythm** for page, section and component spacing.

The goal is consistency, not mechanical uniformity. Avoid both extremes:

- cramped infrastructure-console density;
- oversized marketing-site whitespace.

## 5. Surface and component language

### 5.1 Surfaces

Prefer:

- page background;
- one content surface hierarchy;
- thin borders/dividers;
- subtle elevation only when separation genuinely requires it.

Ordinary settings sections SHOULD NOT each become independent floating cards.

### 5.2 Radius and shadow

Use restrained radii consistently. Avoid the "everything is a 16–24px rounded card" aesthetic.

Shadows should be rare and shallow; dialogs/popovers may use elevation, ordinary rows/settings sections usually should not.

### 5.3 Workspace presentation

Workspaces MUST use the list/row model defined in `v0.3-ui-spec.md`, not a card grid.

The default row hierarchy is:

1. display name;
2. enabled/health state;
3. `workspace_id` and root as secondary metadata;
4. detail affordance.

Do not add branch, dirty-file count, activity, CR count, Plan count, or analytics to the v0.3 default list.

### 5.4 Connection / Diagnostics

Use ordered status rows/checks rather than diagrams or metric dashboards.

Failure should be salient. Healthy state should become visually quiet.

Recovery actions belong next to the failing layer/check rather than behind a generic "Fix" action.

## 6. Typography

Use a modern system-oriented sans-serif stack by default. Do not add a remote webfont dependency merely for visual novelty.

Use monospace selectively for technical identity:

- `workspace_id`;
- filesystem paths;
- command/tool names;
- bounded technical values where monospace improves scanning.

Do not render ordinary body copy or navigation in monospace.

Typography MUST establish hierarchy through size, weight, spacing and contrast rather than color alone.

Body text on narrow/mobile layouts should remain large enough to avoid browser auto-zoom and remain comfortably readable.

## 7. Color and tokens

Define semantic design tokens instead of scattering raw color values through components.

At minimum provide roles for:

- background/surface;
- foreground/secondary foreground;
- border/divider;
- accent;
- success;
- warning;
- danger;
- neutral/disabled;
- focus.

Requirements:

- color MUST NOT be the only status channel;
- status always has readable text and/or semantic icon/shape;
- primary text should meet normal WCAG AA contrast expectations (4.5:1 for normal text);
- `Verified` and `User confirmed` MUST have visibly/semantically different treatments;
- light and dark appearance preserve the same information hierarchy.

Prefer system/browser color-scheme support first. A manual appearance selector is optional unless another frozen contract requires it.

## 8. Icons

Use one consistent SVG icon language across the application.

Requirements:

- no emoji as functional icons;
- icon-only interactive controls require accessible labels/tooltips where needed;
- status icons supplement text rather than replace it;
- do not mix multiple icon styles without a product reason.

The exact icon library is an implementation choice and SHOULD remain a replaceable UI dependency.

## 9. Interaction contract

### 9.1 Controls

Use native/semantic controls where practical rather than recreating basic form behavior from divs.

All interactive controls MUST support keyboard operation and a visible focus state.

Do not remove focus outlines without supplying an equally visible replacement.

Touch/narrow layouts should provide comfortable hit areas (approximately 44 CSS px where the interface is expected to be tapped). Desktop visual controls may be more compact as long as the hit area remains practical.

### 9.2 Feedback

Async actions MUST provide visible in-progress state and prevent accidental duplicate invocation.

Persistent failures MUST remain visible near the affected object/section; they MUST NOT exist only as transient toast messages.

Form errors belong near the relevant field. Placeholder text is not a substitute for a visible label.

Destructive actions use precise language. Removing a workspace authorization MUST explicitly state that local files are not deleted or modified.

### 9.3 Motion

Motion is functional, not decorative.

Allowed examples:

- menu/dialog opening;
- disclosure expansion;
- small status transition feedback.

Avoid page entrance choreography, parallax, pulsing healthy states, animated backgrounds, and long decorative transitions.

Respect `prefers-reduced-motion`.

## 10. State semantics

Use the stable product vocabulary from the upstream UI/interaction contracts. Do not invent visually attractive synonyms.

Especially:

- `Verified` means machine-verifiable evidence supports the claim;
- `User confirmed` MUST NOT be styled or worded as equivalent to Verified;
- locally healthy tunnel/runtime state MUST NOT become `ChatGPT connected` unless the product can actually prove that provider state;
- unknown/unverified state should remain explicit rather than being optimistically promoted to success.

## 11. Forms and setup

Setup remains a bounded five-stage flow from the UI spec. It is not a wizard framework to generalize for unrelated future workflows.

Requirements:

- one clear current stage;
- completed/current/incomplete states are semantically distinguishable;
- machine-verified completion and user confirmation do not share identical success treatment;
- setup progress reconstructs from current server state, not a stored page index;
- provider-owned steps remain visually distinct from WorkspaceLens-owned steps;
- secret inputs never redisplay persisted secret values.

## 12. Responsive/accessibility release checks

Before UI slices are considered complete, verify at minimum:

- keyboard reachability for all primary actions;
- visible focus treatment;
- semantic labels for icon-only controls;
- no required hover-only behavior;
- no horizontal page overflow around 320 CSS px;
- labels and validation remain associated with their controls;
- status meaning is understandable without relying on color;
- reduced-motion preference does not break interaction;
- light/dark/system appearance does not make essential text/status illegible;
- dialogs restore/maintain sensible focus behavior;
- destructive confirmation copy remains precise.

Do not treat screenshot resemblance alone as UI correctness.

## 13. Engineering constraints

The UI implementation MUST preserve the technical architecture:

- React + Vite + TypeScript as already selected by the Technical RFC;
- small typed Control API client;
- no Next.js/SSR requirement;
- no Electron/Tauri shell;
- no global state framework unless implementation evidence proves local/component state inadequate;
- no external CDN dependency required for production rendering;
- no duplicated product/business rules in UI components when they belong in Application Services / Control API;
- no direct filesystem, tunnel process, credential-store, or startup-management access from browser code.

Prefer a small component vocabulary and semantic tokens over adopting a large design system prematurely.

## 14. Testing boundary

UI tests are behavior contracts, not visual implementation prescriptions.

The implementation MUST satisfy `UI-001..005` and related product/E2E contracts without introducing production-only test modes or fake production `test-support` APIs.

Tests should mount the real application/root components and fake only the external Control API boundary where appropriate.

Do not weaken assertions to accommodate the chosen component structure.

## 15. Implementation freedom

The coding harness MAY choose within these bounds:

- exact component file structure;
- CSS Modules / plain CSS / another lightweight local styling approach compatible with the repository;
- exact semantic token values;
- exact breakpoint values;
- exact icon package;
- minor spacing/radius values;
- whether compact secondary actions use inline controls or an accessible overflow menu.

It MUST NOT use that freedom to reopen:

- page information architecture;
- product state semantics;
- authorization language;
- security behavior;
- navigation sections;
- dashboard/non-dashboard positioning;
- frozen interaction contracts.

## 16. Research provenance

This contract was informed by current public frontend-agent guidance including:

- Anthropic `frontend-design`: intentional, subject-specific visual decisions and avoidance of generic templated frontend output;
- `ui-ux-pro-max`: accessibility, responsive layout, semantic tokens, keyboard/touch interaction, feedback and reduced-motion guidance;
- `calm-ui` / restrained frontend-skill guidance: suppress decorative overdesign and AI-flavored dashboard patterns.

These sources are inspiration/evidence only. The contents of this repository are the source of truth for WorkspaceLens.

## 17. Done condition

The v0.3 UI implementation is acceptable when:

1. upstream UI/product/interaction/security contracts are satisfied;
2. the UI behavior contracts turn GREEN for real behavior;
3. the interface remains calm and utility-oriented rather than dashboard-like;
4. desktop and narrow layouts remain usable;
5. accessibility checks above pass;
6. no anti-pattern in section 3.2 was introduced without a documented product reason;
7. independent CR finds no material divergence from the frozen contracts.
